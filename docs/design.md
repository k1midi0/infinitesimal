## 0. 一句话

一个以文字为无限精度的世界。玩家在一张俯视地图上移动、观察、说话、行动；世界的状态由代码持有、是唯一的事实；AI 扮演角色、导演剧情、描述观察对象。

「无限精度」的含义是：你可以一直往下看——看桌子，看桌上的杯子，看杯子上的划痕。但**只有被看的地方才生成，而且生成即固化**。

---

## 1. 根决策

### 1.1 世界状态在代码里，是唯一权威

AI 拥有语言与内容，但**不拥有事实**。模型幻觉最多变成一次失败的工具调用并被退回，不会变成世界真相。

### 1.2 改世界必须显式动手

模型想改变世界，只能通过工具调用提出**后果**，由代码校验后提交。这条来自 Pulsus 已验证的「说话必须是一个动作」：不调用工具就等于什么都没发生。

### 1.3 导演提议 → 判定裁定 → 状态提交

三层各有各的权限。导演只能往时间轴和剧本里放**意图**（"第 3 天夜里，北门有一支队伍经过"），不能直接改数值；判定只负责裁定；所有写入汇入唯一的提交层。

### 1.4 便宜的档位没有写权限

快速档**只能追加**，只有思考档能**改写**。追加是最安全的操作（最坏是啰嗦），改写是最危险的操作（最坏是丢掉事实）。

### 1.5 三条「永不」

- **记录永不改写**：要修正只能追加。理由是可回放、可归因。「基本不变」在实现里会退化成「有时候会变」，而那种 bug 查不出来。
- **事实永不靠回忆**：任何喂给决策者的东西都必须来源于结构化事件，不能让模型凭记忆复述。
- **驳回理由不撒谎**：世界内的驳回（够不着）和协议内的失败（我们自己的 bug）绝不能用同一句话呈现。

## 2. 三层分离：事实 / 记录 / 呈现

同一件事在系统里有三种形态，各有各的规则，不互相污染。

| 层 | 内容 | 谁写 | 稳定性 |
|---|---|---|---|
| **事实** | 结构化后果（地形变了、杯子到地上） | 判定系统 → 直接写地图 | 就是当前状态，不需要专门记录 |
| **记录** | 第三人称 + 角色 ID（客观、不含措辞） | 快速模型 | **永不改写**，只能追加 |
| **呈现** | 名字 + 措辞（给玩家和 AI 读） | 渲染器 | 可固化、可细化叠加 |

记录的形态举例：

```
用户id 用胳膊横扫整个桌面，然后愤怒地盯着（矮人角色id）
```

它"基本不会变动"，正是因为它**不含措辞**——它是记录，不是文章。所以呈现层才需要渲染，而渲染层有自己的规则（见第 7 节）。

**呈现文字必须由记录生成，不能与记录平行生成。** 平行生成的两份东西一定会漂移。

## 3. 角色

### 3.1 统一 Actor

代码里只有一种角色类型 `Actor`：有位置、有感知、有属性、能执行同一套动作。玩家和 NPC 的唯一差别是**控制器是人还是 AI**。

判定、渲染、感知、动作接口、存档格式——每样都只需要写一套。

### 3.2 三类控制器

| 类型 | 控制器 | 上下文 | 笔记 | 智能 |
|---|---|---|---|---|
| 玩家 | 人 | 屏幕（人自己记） | 无 | — |
| 剧情 NPC | AI | 持久 | **可以写** | 高（队友、魔王及其左右手） |
| 氛围 NPC | AI（只在被指向时唤醒） | **持久，与剧情 NPC 同** | 活跃时可以 | 低（酒馆里的矮人） |

氛围 NPC 不是"便宜的 AI"，而是**平时根本不是 AI**：

- 它们的位置由**时间轴上的日程**算出——**代码判断什么时候在哪里**，不消耗任何模型调用。
- 只有**被剧情 NPC 或玩家影响**时，模型才**接管**。
- 日程算出的是**基线**（派生量，不存储）；接管产生的是**覆盖层**（存下来的事实）。世界状态 = 基线 + 覆盖。

于是世界可以容纳成百个氛围 NPC 而**成本零增量**——但有一句要说准：

**它们的记忆是常驻的，只是不注入。** 氛围 NPC 有和剧情 NPC 一样的完整上下文与记忆；那些记忆一直在库里，也一直按 §6.1 的规则累积（范围内的广播会追加进它的 id 列表）。省下来的不是记忆，而是**唤醒**——循环中状态下没有任何模型调用，所以那段记忆不装进提示词、不花钱。

**成本来自被唤醒，不来自有记忆。**

#### 3.2.1 活跃氛围 NPC

被指向之后，氛围 NPC 转化为**活跃氛围 NPC**——功能上等同剧情 NPC（有持久上下文、能写笔记、能主动行动），但**保留它的循环计划**。

转化的同时**直接唤起思考档导演**，由导演统筹三件事：

1. **人设的追加**：这次事件给它添了什么设定
2. **归宿**：升为剧情 NPC，还是事件结束后回归循环
3. **是否生成支线剧情，甚至主线剧情**

如果只是小事，导演不必动剧情，只给活跃 NPC 一个**目标**：**以循环中的某一节点为目标，达到后回归循环**。这比"等一段时间"高明——回归条件是一个**世界内的、有意义的判据**，不是一个计时器。一个被揍了的矮人不是"30 分钟后消气"，而是"回到酒馆自己的位置上"。

回归时，它的经历**归档成人设追加**（上面第 1 件事），笔记保留但不注入。于是它下次被激活时带着"上次那件事"的影子——**世界因此会缓慢地记住，而不需要让所有角色常驻**。

回归意味着回到**当前时刻**日程规定的节点，不补演错过的部分。

#### 3.2.2 循环与角色绑定，死亡只是停止

循环是**角色自身的属性**，不是独立的一层。角色死亡后：

- **信息全部保留**（人设、记忆、笔记、循环定义）
- **循环停止**——日程不再为它产出位置，它不再出现在世界上

之所以是"停止"而不是"删除"：**死亡不一定不可逆**。亡灵法术、复活之类的剧情需要那个角色和它的循环回来；删除会让这类故事无法实现。

同一条兜底也适用于活跃 NPC：**目标永远达不到**（玩家把它锁起来、带走了）需要一条超时规则，重新唤起导演裁定。

#### 3.2.3 知识不是分发的，是当场授予的

导演补出来的世界事实（"东街有个木匠"）写进**地图**，但**不写进所有氛围 NPC 的记忆**。

原因很实在：**无法快速判断哪些 NPC 该知道、哪些不该知道**——那是语义判断，而循环中的氛围 NPC 没有任何模型在场，代码做不了这件事。这时的正确做法是**不做**，而不是用代码近似：代码近似出来的知识分布会**静默地错**，而错的方式没人看得出来。

于是分工是：

| 谁 | 什么时候获得新知识 |
|---|---|
| 世界 | 事实一产生就有 |
| 活跃 NPC | **被指向的那一刻**，由导演按需授予 |
| 循环中的氛围 NPC | 不处理 |

好处是**"谁知道什么"不是被维护的状态，而是每次交互现场决定的**——没有知识图谱，没有传播机制。

代价是循环中的氛围 NPC 认知会过时；但它们在**被指向的瞬间就转成活跃**，导演接着会补上它需要的知识，所以系统会自愈。

**授予多少由导演自行裁决**，不写死规则——补一个点还是补一批常识，视当时情境而定。设计只需要给它这个能力。

#### 3.2.4 没有事实表，地图就是事实库

世界**没有独立的事实记录**，只有地图本身。所以"东街有个木匠"这件事**必须物化成实体**——一个木匠角色加一个作坊地点，落在地图上。

直接后果：**导演补事实 = 往地图里放实体**，而不是往某个事实表里写一行。查询"哪里有木匠"就是查地图上有哪些类型为木匠的实体。

这关掉了"事实表与地图不一致"这类 bug 的可能性——**根本没有第二份可以走偏的数据**。

### 3.3 玩家的宿主元能力

玩家身上挂着一层 NPC 不该有的东西：**存档、读档、时间快进、查看器**。这些不是世界观里的动作，是宿主能力。

别把「存档」做成世界观里 NPC 也能做的动作——否则世界会自相矛盾：一个 NPC 凭什么能读档？

### 3.4 三种输入通道

- **地图点选**：结构化的，不需要任何模型解析。
- **说**：一个输入框。
- **做**：一个输入框。

NPC 拿到的是同一套东西的 AI 版本：一份格式化的地图视图，加上「说」和「做」两个工具。

## 4. 输入与裁定

### 4.1 一次提交 = 一个意图

玩家可以在地图上多选对象（桌上的物品、桌边的矮人），然后在动作框里写一句话：

```
用胳膊横扫整个桌面，然后愤怒地盯着矮人
```

这**是一句话、一个意图、多条后果**，整体裁定一次。

驳回粒度 = 提交粒度，而提交粒度由**玩家的输入单位**决定，不由后果数量决定。如果按后果逐条驳回，这句话的后半句会因为前半句被驳而莫名其妙地消失，玩家会觉得系统听不懂人话。

### 4.2 判定 = 模型段 + 代码段

**动作描述不能穷尽**，纯代码的规则表永远写不完"用胳膊横扫整个桌面"。所以判定必须是两段：

- **模型段**：读「动作描述 + 当时的环境」，决定成不成立、该有什么后果。一次调用产出三样东西：**合不合理 + 后果清单 + 驳回理由**。
- **代码段**：校验模型提议的后果是否合法（对象在不在、在不在范围内、数值合不合理），然后提交。

**这两段不能是两次模型调用。** "想干什么"和"能不能成立"依赖同一份环境上下文；拆成两次就是两次延迟、两次成本，中间还多出一个没人消费的半成品状态（解析成功了但判定说不行，这个中间产物谁都不需要）。

### 4.3 驳回有两个层次

| 层 | 谁判 | 内容 | 呈现 |
|---|---|---|---|
| **世界内** | 模型 | "你够不到整张桌子，你只能够到半边" | 写成自然语言给玩家看 |
| **协议内** | 代码 | 模型提议的后果非法（越界、对象不存在） | **退回给模型重试，绝不示给玩家** |

混淆这两层的代价是：将来出了 bug，玩家看到的是"你的操作不合理"，而实际上是我们的代码或模型的提议坏了——你会在错误的层次上排查很久。

被驳回的操作**不产生任何记录行**（Pulsus 已验证的做法）。

### 4.4 后果的去向

判定通过后由判定系统执行：桌面上的物件移到地上，玩家在地图视图里直接看到图标变化。

**地图是数据的视图，不经过任何模型。** 渲染器只管文字描述。

## 5. 信息传递

### 5.1 对话

按范围广播给范围内所有玩家。UI 上表现为对应角色上的一个气泡，**仅存在当前回合**。对 AI 玩家，收到的是「角色 id + 角色说的话」，话不做任何处理——就像现实一样。

**有指向性的**：玩家选中矮人后输入"你好"，矮人的 AI 会收到带专门标识的「指向自己的角色 id + 话」。

### 5.2 动作

判定模型在裁定时就**同时判定影响对象**，被影响的角色自然是被指向者，本来就会收到定向信息。

快速模型把动作转成第三人称记录并储存，直接发给被指向的 AI 玩家；其他未被指向的 AI 玩家也可以查看。

### 5.3 UI 呈现

| 内容 | 位置 |
|---|---|
| 被指向的动作 | 观察窗口里直接显示 |
| 未被指向的动作 | 地图视口里角色标识上的提示，可点开查看 |
| 对话 | 角色上的气泡（仅当前回合） |

### 5.4 未解决的漏洞：「在范围内」不等于「能听见」

范围是几何的，感知不是。两个 NPC 在角落低声密谋，站在旁边三步的玩家按范围也会收到全部内容——**现在没法说悄悄话**。

两条路：(i) 广播分「公开」与「低声」两档，低声只投递给被指向者；(ii) 代码先按范围粗过滤省成本，"听没听见"再由判定模型裁。

倾向 (i)：它便宜、确定、立刻可用；而 (ii) 会把一次广播变成一次模型调用。

## 6. 记忆

### 6.1 短时：滚动窗口

保存**最近若干回合的话与事**。第三人称记录里已经生成了客观描述，所以不需要再单独做一份摘要。

#### 装什么

装的是**客观记录**（第三人称 + 角色 id），**不装角色的内心与计划**——那些属于它自己的笔记（§6.3）。窗口是**世界对它的广播记录**，不是它的日记。

#### 粒度：一份事件流 + 每角色的 id 列表

不是"全局一份"或"每角色一份"二选一，而是第三种：

- 只有**一份事件流**，append-only，措辞唯一
- 每个角色有一个**指向该流的 id 列表**，装它感知到的那些
- 注入时按 id 取最近若干条，加上当前地图视图与人设

这样同时拿到两边的好处，且没有"每角色一份"的两个缺点：

| 方案 | 写入成本 | 措辞一致性 | 信息隔离 |
|---|---|---|---|
| 全局一份 | 1 | 一致 | **被捅穿**：不在场的 NPC 也读到 |
| 每角色一份 | O(M) 放大 | **可能漂移** | 成立 |
| **事件流 + id 列表** | 1 条记录 + M 个 id | 一致 | 成立 |

另外它**可审计**：出问题时你能回答"这个 NPC 当时到底收到了什么"，因为 id 列表就是证据。这也是 Pulsus 验证过的形状——一份数据，两种读法（全局读法给导演，按 id 过滤的读法给角色）。

#### 怎么裁

Pulsus 的三条规则直接搬过来：

1. **只按整轮裁剪。** 在这里的含义是：**一次提交产生的全部后果不可切开**——掀桌子产生的"桌翻、杯落、酒洒"必须一起进出。切开会让角色形成矛盾认知：它看到杯子在地上，却没看到桌子被掀。
2. **最新一轮无论多大都保留。** 丢掉它等于丢掉正在被回应的东西，那不是更小的请求，是另一个请求。
3. **先落库，再裁窗口。** 库是记录，窗口只决定下次请求带多少。

加一条本项目特有的：**双约束**——token 预算是硬约束，回合数 N 是上限，两者谁先到就按谁裁。

#### 多大

- N 由 spike 实测定，不由拍脑袋：观察 NPC 在多少轮之后开始重复或自相矛盾。
- token 估算：中文 1 字 ≈ 1 token（留余量；接口实测约 0.6）。
- **参与者不同，N 不同**：氛围 NPC 与剧情 NPC 同一档，导演更长（它低频、用思考档）。

#### 子问题

- **氛围 NPC 有完整记忆**（已定）。玩家昨天骂了酒馆矮人，今天它记得。范围广播照常追加进它的 id 列表——**投递总是发生，唤醒才是例外**。
- **玩家自己要不要一份窗口**：要，但性质不同——那是**查看器**，给玩家看的，不是给模型看的。它属于玩家的宿主元能力。

#### 一条叙事上的确认

角色离开再回来，它没感知到的那些事**不在它的窗口里**，所以它看到的历史是跳跃的。这是**正确的**：它应该通过观察发现变化，而不是通过记忆。时间轴和导演知道中间发生了什么。

### 6.2 长时 A：摘要系统（导演专有）

面向**流**的压缩。输入是最近发生的事，由系统在导演被唤醒时触发。是**被动整理**。

### 6.3 长时 B：笔记系统（剧情 NPC 可用）

面向**点**的主动记录。NPC 自己决定"这件事我得记住"，通过工具写一条。是**主动写入**。

两者**存储形状相同**（所有者 + 内容 + 标签 + 时间），共用一个表；但**工具与触发完全不同**，所以是两个工具。导演如果按统一 `Actor` 建模，它的摘要就只是"它自己名下的笔记"。

### 6.4 可变性必须分开

两类内容必须分节（分表）：

- **发生过的摘要 / 记录**：append-only，历史不会变。
- **注意事项**：**会被推翻的**。"玩家欠矮人一笔钱"，在他还清之后必须失效。

混在一起，"注意事项"会退化成一堆互相矛盾的历史陈述，而模型会**同时相信它们**。这种错不报错、不崩，只表现为**导演偶尔作出基于过期事实的决定**——最难查的一类 bug。

失效用**追加 + 显式 supersede 标记**，永不删除。理由和「记录永不改写」一模一样：你要能在事后回答"导演当时为什么这么决定"。

### 6.5 检索方式

沿用已经定过的那套两层结构：

- **注意事项常驻注入**（必须小，设字符预算与可见的截断标记）
- **摘要按关键词检索**（中文 bigram 分词 + LIKE 转义 + 字符预算）

NPC 笔记量小，可以全量注入并设上限。

### 6.6 权限与容量

- NPC **只能读自己的笔记**，不能读别人的。
- 只能追加 + supersede，不能删除。
- 需设容量与频率上限（每角色 N 条 / 每回合至多 1 条），否则 NPC 会把笔记写爆。

## 7. 渲染（观察器）

渲染器**不是旁白者**，它是观察器：`观察(X) → 描述(X)`。没有剧情、没有语气、没有"你走进房间，一股霉味扑面而来"。旁白性的文字来自导演，而且低频。

### 7.1 固化，以及两种「变化」

**描述一旦落库就不再改变——除非物体本身变了。** 而"变了"有两种，性质完全不同：

| | 仅仅外表变化<br>（桌子被擦干净） | 彻底改变<br>（桌子被劈开） |
|---|---|---|
| **身份 id** | 不变 | **新的 id** |
| **体素形状** | 不变 | **新建模** |
| 属性 | 可能变 | 全新 |
| 描述 | **作废，重新渲染** | 新物体的新描述 |

**分界线是形状（建模）。** 几何没变，就还是同一个物体，只是外表不同——重渲染即可；几何变了，它就不是原来那个东西了——新物品、新形状、新描述。

为什么必须分开：

- **全都换 id** → id 爆炸，而且玩家认知里"那张桌子"在不断换身份，引用与记录都碎掉
- **全都只重渲染** → 形状变了却只改文字：地图上还是一张完整的桌子，文字却说它被劈成两半，**俯视图与文字打架**

所以**判定系统要判定的不是"变没变"，而是"变到哪一层"**：未变 / 外表变化 / 彻底改变。这是后果清单里的一种操作，而不是一个布尔值。

**代码能守住这一条**（附录 A.6 的分工线）：判定系统声明"这只是外表变化"时，它提议的体素形状**必须与旧形状相同**；声明"彻底改变"却交回同一个形状，就是自相矛盾。**这个一致性检查是结构性的，代码做得了**——退回重试，不当成玩家的错。

**「把 A 换成 B」因此是一种后果操作**，与"移动""改属性"并列：删掉一个物体、加上一个物体。旧 id 从此不在世界态里，但它的记录**不删除**（§1.5 记录永不改写）——否则"你记得它原来是什么样"就无从谈起。

背景（地点的）不变，见 §7.5。

### 7.2 细化只叠加

玩家已经读过的粗描述是承诺。细化只能**增加**细节，**不得推翻已有描述**。所以每次细化请求都必须带上现有描述，并要求"只补充，不矛盾"。

「覆盖」只允许作为「世界真的变了」的结果（走失效条件 1 或 2），不能作为细化的默认行为。

### 7.3 何时调用模型

| 场景 | 是否调模型 |
|---|---|
| 普通移动 | 不调，回显已固化的描述 |
| 首次进入某节点 | 调，生成并固化 |
| 玩家主动「查看」某物 | 调，生成或叠加细化 |
| **声音事件** | **不调**：由代码按几何快速判断影响角色 |
| 其他事件 | 调：由判定模型判断影响对象 |

#### 被动感知不是独立的一层

没有单独的"被动感知系统"。事件的影响对象只有两个来源：

- **声音** → **代码**判断。声音是唯一可以用纯几何确定的类型——距离、音量、遮挡，不需要理解语义；而且它必须**即时**，因为在没有旁白的世界里它是唯一的"打断"，不能等模型三秒。
- **其他事件**（视觉、物理、社交）→ **判定模型**判断。这与第 5.2 节动作的投递是同一条路径：判定模型本来就要输出影响对象，"角色指向"就是它的输出。

措辞层按模板处理（"你听到远处一声闷响"），要展开必须玩家主动观察。

两条路径的代价不同，必须分清：**代码路径不会泄露玩家不该知道的细节；模型路径能理解语义，但模型很乐意告诉你隔壁房间发生了什么**——所以模型路径的输出必须先过感知过滤再投递。

**声音的传播规则挂在世界结构上**（按距离，还是沿相邻边），所以它依赖第 12 节的待定项 1。

### 7.4 结构从预设来，文字只在被看时生成

预设库给的是**结构**（数值、标签、名称、拓扑），非模型驱动；渲染器给的是**文字**，模型驱动、且固化。

### 7.5 渲染器的输入是三段，背景由导演提供

```
[规则]  观察器该怎么做 —— 全局静态，逐字不变
[背景]  这是哪里、什么时期、出了什么事 —— 导演写，每地点稳定
[对象]  被观察的东西本身 —— 每次都变
```

**背景由导演系统提供**，写在**地点实体**上（`world/` 里通常是 `parent` 链的根），物体沿链继承。它因此落在**地图**里，而不是另立一张"背景表"——世界只有地图这一份事实（§3.2.4）。渲染器**只读**它，这与"导演是世界的补写者"（§8.3）是同一条。

前两段必须拼成**一段**不可变前缀（不是两条 system 消息）：缓存按 token 前缀匹配，分成两条只会在中间多出 role 标记，对命中没有任何好处，却让"前两层"变成两个要各自维护的东西。

**背景带来的是"不脱离世界"，不是"命中缓存"。** 实测：加上背景后渲染器前缀约 277 token，同地点连续观察四个不同物体**命中全为 0**；而 2799 token 的长前缀能稳定命中 2560。这条规则见 §14.5——**缓存只对上下文本来就很长的系统（NPC、导演）有意义。**

**背景不会变**（已定，见 §7.1）：导演为某地点写下背景之后就固定下来。所以"背景变了、地点里已固化的描述过时了"这种情况不存在，那条顾虑整个消失。

### 7.6 描述只讲物体自身，而且这一点要落在输入上

观察到的描述**只能讲这个物体的外表**：不写它周围有什么，不写它与别的东西的位置关系。

这不是风格偏好，是**固化能成立的前提**。因为关系会变、而物体自身没变：旁边的酒杯被拿走后，一句"一侧对着吧台"就过时了——可 §7.1 的两种变化**都不包含"邻物改变"**，于是那条描述会**静默地过时**，永远没人发现。把周边写进描述，等于给每个物体塞进一堆它管不着、也不会因此重渲染的依赖。

**处置不是"在提示词里叫它别写"，而是输入里压根不给。** 渲染器的输入原来带着坐标与"所在"，模型于是忠实地把它们用上了：

> 它靠大厅中央立柱横向摆着，一侧对着吧台，另一侧留出较宽的通行走道。

去掉坐标与"所在"之后（`parent` 链仍然用来取地点背景，但**不再告诉它"你在哪"**），实测输出变干净了：

- 基线：「橡木桌呈深褐色，表面打磨得光滑，木纹清晰而紧密地延展。」「四条桌腿厚实笔直，支撑着两米长、一米宽的桌板，整体高约零点八米。」
- 工具插入的新句：「桌面中央泛着一层薄薄的油光，是被常年擦拭摩挲出来的温润包浆。」
- FIM 插入的新句：「桌面边缘有一道浅浅的弧形磨损，像是常年被手肘倚靠留下的痕迹。」

**没有素材，就写不出来**——这与"写操作的限制要落在数据模型上"（§14.2）是同一条原则，只是这里限制的是**输入**。

配套一个**开发期抽查**：扫关系词（旁边、一侧、搁在、对着…）。它**不是可靠的判定办法**——词表永远不全，而"桌子对着吧台"完全可以用词表里没有的说法讲出来。真正起作用的是输入裁剪，抽查只用来验证"裁掉之后输出真的干净了"。

## 8. 导演

后台运行，不直接接触玩家。

### 8.1 时间轴

导演设计时间轴：火山什么时候爆发、魔王什么时候苏醒、酒馆里的矮人一天的循环。所有未来可能发生的事都要有到期时刻，快进才能算出"最早该停下的时刻"。

**没有时间轴就必然漏事**——你睡觉时邻居家着火，是没有任何定时器能预告的。

### 8.2 两个触发器，性质完全不同

| 触发 | 谁检测 | 性质 |
|---|---|---|
| 时间轴**到期** | **代码** | 确定性、可复现 |
| 剧情**跑偏** | **快速模型** | 语义判断 |

快速模型只能**发现**偏离，**不能改时间轴**；改时间轴只有思考模型能做。这是「便宜档位没有写权限」在导演内部的延伸。

### 8.3 职责

生成剧本、埋伏笔、给 NPC 分发日程、生成 NPC、加入突发事件、维护自己的摘要与注意事项。

还有一条容易被漏掉、但在实现上最先撞到的：**导演是世界的补写者**。

玩家问酒馆里的矮人"镇上哪里有木匠"——**这件事不会预先写在矮人的认知里**。如果让矮人先回答，它会现场编一个；两个 NPC 就可能给出两个不同的木匠。所以**导演必须先决策**：把这个事实补出来（镇上有个木匠、叫什么、在哪条街），再让矮人回答。

这条和 §7 的「渲染即固化」是**同一条原则**，只是对象不同：

| 谁 | 输入 | 产出 | 之后 |
|---|---|---|---|
| 渲染器 | 被观察的物体 | 文字描述 | **固化**，下次直接读 |
| 导演 | 被问到的未定义事实 | 世界事实 | **固化**，所有角色此后共用 |

**按需生成，立即固化**——这是整个系统里最反复出现的一条模式。

代价是延迟：每次指向性交互都要等一次导演。所以要把它做窄——这次调用的任务是**判定"是否需要补事实、补什么"**，不是重新规划剧情。窄任务 = 短输出 = 快，而且**必须显式设 `max_tokens`**（思考档默认输出预算是 64K，不能按默认走）。

#### 8.3.1 决策同步，生成异步

这两件事的时机不同，必须分开：

| 阶段 | 同步性 | 产出 |
|---|---|---|
| **决策** | **同步阻塞** | 足够回答当前问题的事实（有个木匠、叫老张、在东街） |
| **生成** | **异步** | 完整的实体与它的循环日程 |

矮人的回答只需要决策的产出；生成慢多久都不影响这一句。反过来，把生成也做成同步，玩家就得为一次完整建模等下去。

#### 8.3.2 导演任务排队

导演在同一时刻只处理一个任务，新任务**排队**。

这不只是省事——**串行是避免并发写冲突最省事的手段**。两个导演任务同时跑，就可能各自补出一个木匠，而且谁都发现不了。

代价是队列会积压，延迟变成"排队长度 × 单次时长"。所以：

- 队列是**全局一个**（世界只有一个权威，串行写最安全）
- 界面上必须有**"世界中…"的指示**。Pulsus 已经踩过这条：生成阶段没有任何文字出现时，玩家会认为程序卡住了

## 9. 生成系统

导演通过工具调用生成系统这个子系统来完成。分为：

- **地形生成**
- **物品生成**
- **角色生成**
- **建模**：生成新物品的体素模型（见附录 A.9）

它们调用**预设库**，简单修改后放进地图，不需要模型从零雕琢每个细节。

### 9.1 预设库（非模型驱动）

类似数据库，存地形 / 物品 / 角色的模板。默认通用包只给**基本描述**（"杯子"就只是杯子），具体细节按情况具体渲染。

允许**人为导入预设包**。比如一个「西幻世界冒险包」里的啤酒杯可以写成：

```
深色木制的带把手的杯子，直径一分米，把手上下有铁环箍着，杯口有深浅不一的划痕
```

默认通用包不提供这种丰度——它靠导入。

## 10. 模型分档与平台约束

### 10.1 三档

| 档位 | 参数 | 用途 |
|---|---|---|
| **快速** | `thinking: disabled` | 动作解析与第三人称化、摘要、偏离检测、氛围 NPC 问答 |
| **思考** | `thinking: enabled` + `reasoning_effort: high\|max` | 导演重规划、剧情 NPC |
| **图片** | flash + `image_url` | 视觉理解 |

「快速响应 / 深度思考 / 图片识别」在这家 API 上是**同一个模型的三套参数**，不是三个模型。

### 10.2 平台硬约束（DeepSeek API，2026-09 核对）

- 只绑 `deepseek-flash`：`deepseek-v4-pro` 正在退场，且**图像理解只有 flash 支持**。
- 上下文 1M、最大输出 384K。不设 `max_tokens` 时思考默认只给 64K，**输出预算要自己留**。
- **思考模式下 `temperature` 不生效**，能动只有 `top_p`（夹在 0.95–1.0）；只有关闭思考的快速档才有 `temperature`。想要文字多样性，就只有快速档。
- **带 `tools` 时，每条 assistant 消息必须回传 `reasoning_content`**，没有思考时给 `""`（不能是 null），否则 400。
- 思考模式下 `tool_choice` **不支持 `required` 与具名**（400）。**没法强制模型"这轮必须调这个工具"**。
- `strict: true` 需 base_url 换成 `/beta`，且每个 function 都要设。object 的所有属性必须进 `required` 且 `additionalProperties: false`；不支持 `minLength`/`maxItems` 等。
- 并行工具调用**关不掉**。一回合可能同时回来多个工具调用，且顺序由模型决定——所以状态改动层必须**一次性校验 + 提交**。
- 缓存按 token 前缀**完整匹配**，尽力而为，几小时到几天清空；隔离旋钮是 `user_id` 而不是 API key。
- **动静分层**：不动的东西（世界观、规则、人设）放最前，每回合在变的东西（血量、位置、状态）放最后。**但它有前提，见 §14.5：短前缀根本命中不了缓存**，所以这条只对上下文超过一个缓存单元的系统（NPC、导演）才有收益；渲染器那种 170 token 的请求，做了也白做。
- 并发是**账户级、与 key 无关**（flash 2500）。多配 key 不会多出并发；要加并发走扩容工单，且不加价。
- 成本（flash，元/百万 token，高峰/空闲）：输入命中 0.04/0.02、未命中 2/1、输出 8/4。**约 1.2 分/回合（高峰），100 回合约 1 元**——成本不是第一性问题，**延迟才是**。
- 没有 embeddings、没有 fine-tuning、没有 Batch、没有 TTS。**不存在 RAG 这条路**。

### 10.3 配置分层

客户端按**供应商 → 模型 → 档位**三层抽象，只实现 DeepSeek 一家，但保留扩展空间。

**每个模块可单独覆盖** `{baseUrl, apiKey, model, thinking, reasoningEffort, userId}`。理由是：多账户轮换（故障隔离）、**计费归因**（哪个模块烧了钱）、不同模块走不同 base_url。

注意：**界面文案不要宣称这能提高缓存命中**——那会变成又一次「界面一个词、行为另一个词」。

### 11.1 Gradle 层

与 Pulsus 同形，已验证可用：

  shared/        commonMain 装全部逻辑 + Compose UI

### 11.2 shared 内的包分区

依赖方向自下而上，`world` 不依赖任何人。

```
llm/        协议层：SseParser、ChatModels、WireMessages、LlmClient…     ← 移植 Pulsus
tools/      工具声明 / 参数校验 / 注册表                                ← 移植 Pulsus
memory/     QueryTerms：中文 bigram 分词 + LIKE 转义                    ← 移植 Pulsus（仅此一文件）
config/     供应商 → 模型 → 档位；每模块可覆盖凭据
world/      世界状态：Actor、地点、物体、事实、时间轴                    ← 唯一权威
presets/    预设库（非模型驱动，DB 式）
rules/      判定：模型段（解释任意动作 → 提议后果）+ 代码段（校验 + 提交）
render/     观察(X) → 描述；固化、细化叠加、失效
notes/      笔记与摘要：一个表，两个工具
director/   剧本、伏笔、日程、突发事件、时间轴；读窗口与笔记
generate/   生成系统：地形 / 物品 / 角色
control/    控制器：人类 / 剧情 NPC（持久）/ 氛围 NPC（无状态）
session/    回合推进、时间快进、事件结算、存档
ui/         地图（俯视、以玩家为中心、可多选）、两个输入框、观察周围、查看器
```

`world` 不依赖任何人；`rules`/`render`/`notes` 读 `world`；`director` 读窗口与笔记、写时间轴；`generate` 读 `presets`、经提交层写 `world`；`control` 调 `tools` → 经 `rules` 裁定 → 走提交层。

## 14. 实测发现（spike 一、二轮）

下面是**量出来的**，不是推测的。跑法见 §13，代码在 `D:\fatfish\Infinitesimal` 的 `shared/src/jvmTest/.../spike/`。

### 14.1 「渲染即固化」成立，延迟约 1 秒，成本可忽略

三轮共 10 次整段渲染：首次 **1354 / 1466 / 1918 ms**，命中固化 **0 ms**（零请求，断言钉住）。平均约 1.1 秒。

单次观察约 **0.0007 元（高峰）**，1000 次约 0.7 元。**成本不是第一性问题，延迟才是**——玩家点一次"查看"要等约 1 秒。

### 14.2 「只增不改」不能靠提示词，必须靠数据模型

第一轮把描述存成一整段文本，细化时把旧描述喂回去并明确要求"只增不改、不得矛盾"，模型照样矛盾：

> 原描述：表面光滑，**几乎不见划痕**
> 细化后：桌面边缘可摸到**几处细微的刻痕**

而且细化后的文本里，原描述的桌腿、气味、尺寸**全部消失**——它不是叠加，是换写了一篇。

第二轮改成**描述按句存储**，唯一写操作是在两句之间插入，同一实验通过：**去掉新插的那一句，剩下的与基线逐字相同**（断言）。

**结论：写操作的限制要落在数据模型上，不能落在提示词上。**

### 14.3 插入一句话：工具可靠，FIM 不稳定

同一个基线、同一个插入点：

| 机制 | 结果 |
|---|---|
| **工具调用** | **2/2 成功**，843 ms。产出「桌面中央留着一圈年深日久的浅色圆痕，是无数酒盏底沿磨出的印记。」位置由模型自选（建议第 1 句后，它选了第 2 句后），句子依然自然 |
| **FIM** | **5 次里只有 2 次可用**。失败方式有三种：假标记 `<cont=12>。`、**空返回**、以及 §14.4 那条 |

FIM 在**极简提示词**下（一句指令 + 描述前缀）3/3 成功；一旦把"物体信息 + 规则清单"叠上去就开始不稳，而且**同一条形状也会时好时坏**（同一个形状，一次成功、一次空返回）。

**所以 FIM 是可选加速，工具是必备能力**——已按此定：接口一个，实现两个，数据模型共用。

### 14.4 一个必须写下来的危险：FIM 会泄漏端点的安全审核标记

把物体信息压成一行的那次，FIM 原样返回了端点的内部审核文本：

```
<ds_safety>[用户未成年]否
[分类]其他
[判定]用户请求为木桌补充细节，内容属于一般家具描写，未涉及政治人物、敏感事件或分裂主张。
[规则]无</ds_safety>Safe
```

**这段东西如果直接落库，就会变成玩家读到的一段世界描述。** 它落在 `finish_reason=stop` 上，看起来完全正常。

两条处置：

1. **任何模型输出在落库前必须过守卫**（非空、长度上限、只含一句、不得与已有句子重复）。上面这段 94 字且含多个句末标点，会被"含 N 个句子"拦下。
2. FIM 这条路**必须带重试与回退**，回退目标是工具路径。

### 14.5 缓存有长度门槛（已定论）

**短请求永远不命中。** 约二十次 54–198 token 的请求里，`prompt_cache_hit_tokens` 恒为 0——包括 system 提示词逐字不变、只隔几秒的连续请求，也包括**完完全全相同的请求隔 6 秒重发**。

先要排除一个陷阱：那个 0 会不会只是我们模型里的默认值？绕开客户端看端点返回的原文：

```json
"usage":{"prompt_tokens":54, "completion_tokens":48, "total_tokens":102,
         "prompt_tokens_details":{"cached_tokens":0},
         "prompt_cache_hit_tokens":0, "prompt_cache_miss_tokens":54}
```

**字段确实返回了，值就是 0。** 不是读数被掩盖。

然后是关键的一步——把**长度**这一个变量单拎出来（2799 token 的静态前缀）：

| | 命中 |
|---|---|
| ① 首发 | 0 / 2799 |
| ② 相同问题 | **2560** / 239 |
| ③ 换个问题 | **2560** / 247 |
| ④ 回到第一问 | **2560** / 239 |

**缓存是正常工作的，只是它有门槛。** 命中数三次恒为 2560，正对应文档第三条落盘时机（"按固定 token 间隔落盘"）——2799 token 刚好只凑得出一个完整单元。而 2560 = 5 × 512 = 20 × 128。

**由此得出设计规则，它比"动静分层是唯一手段"具体得多：**

> **动静分层只在上下文超过一个缓存单元的系统上才有收益。**

- **渲染器**：system（约 130）+ user（约 40）= **170 token，够不着门槛，永远不可能命中**。所以不要为它做任何缓存优化——纯属白做。它的成本本来就低到 0.0007 元一次（§14.1）。
- **NPC / 导演**：上下文必然超过门槛，**会命中**。动静分层在那里才值得下功夫。

**精确间隔未定**（512 还是 128）。但它不影响上面这条规则——无论哪个，渲染器那 170 token 都够不着。

**补充一组数据：导演给了背景之后，能不能把渲染器推过门槛？** 把地点背景（约 150 token）加进渲染器的静态前缀，前缀从 170 涨到 277。同一地点下连续观察四个不同物体：

| | 命中 |
|---|---|
| ① 木桌 | 0 / 277 |
| ② 酒杯 | 0 / 264 |
| ③ 木凳（判决点） | 0 / 263 |
| ④ 油灯 | 0 / 261 |
| ⑤ 另一地点的木桌（背景不同） | 0 / 192 |

**全部为 0。** 而完全相同请求重发时能命中 **128**（占总量的 46%）。对照 §14.5 上面的长前缀实验：2799 token 下**换一个后缀也照样命中 2560**。

于是这条规则可以说得更硬：

> **缓存只在"前缀本身已经很长"的系统上生效，与"有没有共享的前缀段"关系不大。**

渲染器（约 170–280 token）不在其中，**加了导演的背景也不在**。文档描述的"公共前缀检测落盘、第三次命中"这套机制，在 260 这个量级上没有在我们身上发生。

背景介绍的价值因此回到它原本的那一件事：**让描述不脱离世界**。这一条实测是有效的——描述里出现了"陈年酒渍"，插入句里出现了"靠大厅中央立柱横向摆着，一侧对着吧台"，而背景原文并没有提立柱和吧台，那是模型在背景约束下作出的合理推断。

### 14.6 后缀是锚：没有它，模型会编造

FIM 不给 `suffix` 时，模型在酒馆的木桌上摆了一只**苹果手机**，还编了一整套"布局松散且不对称""屏幕朝下""摄像头略突出于桌面"，最后撞上 token 上限。

**没有锚，模型不是"描述得更细"，而是"编造得更远"。** 观察器必须给它边界——而 FIM 的 `suffix` 恰好是**协议级**的锚，比提示词里写"不得编造"硬得多。这是 FIM 唯一无法被工具替代的价值。

同一现象的另一面：FIM **无指令**时会返回空，或只补出"木桌"两个字。所以它必须有指令。

### 14.7 输入成本对比

| 路径 | 输入 token |
|---|---|
| chat（含观察器 system 提示词） | 169–198 |
| FIM（无 system 提示词） | 71–151 |

FIM 省下的主要是那段 system 提示词（约 130 token）。但它一旦需要重试，这点优势就没了。

### 14.8 每个系统一个缓存池（`user_id` 分层）

**决定：每个系统一个 `user_id`，因此一个独立的缓存池。**

端点的 `user_id` 有三项功能（官方《限速与隔离》原文）：**内容安全隔离**、**KVCache 隔离**、**调度隔离**。所以这不是我们发明的分层，是端点已有的那一层。字段平铺在请求体里，约束是 `[a-zA-Z0-9\-_]+`、最长 512、不得含隐私信息。

落地为闭合枚举 `SystemId`（`inf-renderer` / `inf-director` / `inf-npc` / `inf-judge` / `inf-summarizer`），**用枚举而不是裸字符串**：`user_id` 写错一个字母不报错，只静默换一个池——命中率掉下去，没有地方看起来不对。

**代价几乎为零**：缓存按"前缀单元"完整匹配，而各系统的 system 提示词本来就完全不同，它们之间没有任何可共享的前缀，隔离不损失命中。

买到的三样：**隔离**（一个系统不挤掉另一个的缓存）、**归因**（哪个系统的命中率可以分开算）、以及**可诊断**——"命中恒为 0"这类问题，有分层才分得清是"同一池内也不命中"还是"跨池本就不该命中"。§14.5 的定论正是靠这一层做出来的。

### 14.9 一条实现纪律：`thinking` 必须显式关，不能靠默认

写原始 `usage` 探针时忘了带 `thinking` 字段，端点的默认是**开启**——那两次请求各烧了 29 和 48 个 reasoning token，**接近输出的一半**。

推而广之：**所有影响计费或输出的开关都必须显式写进请求体**，不依赖端点默认。这条与"配置里没有默认值、缺字段按名报错"是同一个原则，只是发生在协议层。

## 附：空间与物体

这一节是 v0.1 定稿之后补的，尚未并入正文，等它自己稳定下来再重排编号。

### A.1 空间用坐标，不用区域树

**地形和物体有精确坐标**，能解析成俯视图，也能转成文字准确描述给模型。

「分层区域树、不引入坐标」的提案已被推翻。推翻的理由是它混淆了两个独立的轴：

| 轴 | 由什么解决 |
|---|---|
| **空间精度**（东西在哪、隔多远） | **坐标** |
| **描述精度**（杯子上的划痕） | 懒生成 + 固化 + 细化只叠加 |

「无限精度」指的是后者，不是前者。

### A.2 一份数据，两个投影

坐标数据是唯一的源，两个投影都是**确定性的、不需要模型**：

- **投影 A**：俯视图（图形，给玩家）
- **投影 B**：文本网格（给模型）

这与正文 §4.4「地图是数据的视图，不经过任何模型」是同一条原则——模型和玩家看到的是同一份真相同一个源。

**表示法已定：体素。**

| 参数 | 结论 |
|---|---|
| 离散 vs 连续 | **离散**——体素天然是整数坐标 |
| 维度 | **3D** |
| 给模型的格式 | **按层切片的 ASCII 网格 + 物体清单**：网格让模型看出形状与空间关系，清单给它 id 与精确坐标 |

体素带来的三个好处：

1. **「在桌上」变成几何事实**——杯子的体素落在桌子顶面的体素上方，不需要额外字段去声明这个关系。
2. **俯视图天然可解析**——沿 z 切片就是俯视图。
3. **材质有地方放**——每个体素带材质，描述层就有据可依。

代价是规模：

- **必须稀疏存储**（只存非空体素），否则一个 100×100×20 的世界就是 20 万格。
- **给模型的网格必须是局部视窗**，不能是全图。一个 40×40 的 1 米网格已是 1600 字符量级。
- 主视图要**按层切片**：体素是 3D 的，"俯视"必须指定看哪一层，默认角色所在层。

### A.3 物体与物体之间的关系

**物体可以包含物体**：桌子是物体，桌上的酒杯是物体。

所以世界模型有三个组件，而不是两个：

1. **坐标**——空间位置，精确
2. **关系**——物体与物体的语义关联
3. **描述**——懒生成、固化、可细化

### A.4 空间与物体不由代码模拟，由模型处理

现实无法用代码模拟。把桌子掀了，杯子该滚到哪、会不会碎、酒洒成什么形状——**这不是规则能写尽的**，只能由模型推理。

所以这一层的设计目标不是"适合代码计算"，而是：**适合模型修改、不易出错、又能被俯视角解析**。

代码在这里只有一件事要管：**守住结构合法性**，不守物理。

### A.5 结构：一张实体表 + 针对性编辑

每个物体一行：

| 字段 | 内容 |
|---|---|
| `id` | 稳定标识，其他字段和工具参数都引用它 |
| `类型` | 名词（桌、酒杯、门） |
| `坐标` | 精确坐标 + 层 |
| `parent` | 上位物体 id（可空）——**由模型维护的数据，不是代码算出来的变换** |
| `属性` | 结构化键值（杯子里有没有酒、门开没开） |
| `描述` | 固化文字，走正文 §7 的渲染规则 |

**模型不重写整张表，只发针对性编辑**：新增、移动、改属性、改 `parent`、删除。

这一条是"不易出错"的关键。重写整张表意味着 token 爆炸，而且**每次改动都可能顺手改坏别处，改坏的后果还不可检测**。针对性编辑让"改动范围"和"意图"一一对应，代码才有东西可校验。

**俯视图只画 `parent` 为空的顶层物体**；子物体在观察窗口里展开。这条规则是纯结构的，不需要判断语义——在盒子里的戒指自然不画。

### A.6 分工线

| 情形 | 谁判 | 结果 |
|---|---|---|
| **结构非法**（id 不存在、坐标越界、`parent` 成环、批量提交失败） | **代码** | 协议内失败，**退回模型重试**，不给玩家看 |
| **物理不合理**（够不着、搬不动、位置被占着） | **模型** | 世界内驳回，写成话告诉玩家 |

这条分工正好落实正文 §4.3 的两层驳回。

**关系不存成事实。**「酒杯在桌上」由**坐标共位 + 层**表达，语义关系由模型推理——不做代码推导的场景图，那会逼着代码去理解物理。

### A.7 一致性靠纪律，不靠机制

模型维护世界，就没人守着一致性了：模型忘了把杯子移走，杯子就会飘在已经被掀翻的桌子上。这是这套方案的代价，靠四条兜住：

1. **一次意图 = 一次提交**（正文 §4.1）。判定模型裁定"掀桌子"时，必须在**同一次提交里给出桌子和杯子的全部编辑**——这是纪律，不是机制。
2. 代码守结构、不守物理，所以它**不会**因为"杯子还挂在桌上"而报错——它根本不知道那不合理。
3. **矛盾在读取时暴露**：被改动的物体描述会失效并重新渲染，届时模型读到的是"桌子已翻、杯子仍在桌上"这个不一致的状态，由它自己纠正。
4. 另加一个**开发期自检工具**（列出悬空 `parent`、坐标重叠、越界），不进游戏。

### A.8 无限精度的一条纪律

**每次只看一层。**

容器链可以无限深（口袋里的盒子里的戒指），但每次观察只展开被看的那一层。这样"无限精度"是无限的，而每次生成的成本是常数。

### A.9 物体与体素表

**实体表是真相，体素是它的形状语言。** 每个物体有**自己单独的一份**体素模型，标识它放进世界会占用多少体素；**具体操作的单位仍然是物体**，不是体素。

**不能互相引用。** 引用会让形状变成可变共享状态：打破一个杯子，所有引用同一形状的杯子一起碎。而且这种 bug 平时不出现——只在有人编辑了共享形状时才炸，排查代价极高。

所以：**预设库是工厂，不是引用。** 从小屋预设生成一个具体小屋，是把形状**拷贝**一份，再改尺寸与材质；之后这个小屋与预设再无关系，改它不影响任何别的物体。管理因此变成局部的——每个物体的形状只属于它自己。

代价是存储：一千个杯子就是一千份形状。但这个代价很便宜——体素是稀疏的，一个杯子几十到几百格，几千个物体的量级仍然只有几 MB。

### A.10 建模：把雕刻隔离出去

生成系统新增一个**建模**功能，用来生成新物品的体素模型。

它比"禁止雕刻"更好，因为雕刻没有被禁掉，而是被**隔离**了：

- **低频**：只在需要新形状时发生，不是每次操作都能雕
- **专门**：有独立的工具与校验，不混进普通动作
- **产物归属**：生成结果直接成为**那个物体自己的**模型（按 A.9，实例化即拷贝）

已定的四个参数：

| 参数 | 结论 |
|---|---|
| 输出格式 | **分层 ASCII 网格**——模型画图，代码解析（见 A.11） |
| 适用范围 | **通用形状服务**：物品、角色、地形块都调它，代码只写一份 |
| 最低粒度 | **1 厘米**。基准单位是厘米整数，地形 1 米格、家具 0.2 米、餐具 0.05 米 |
| 产物去向 | 先存**单局缓存**；**被重复用到时**提升进**全局缓存** |

缓存分层要分清：缓存里存的是**模板**，实例化永远是**拷贝**——所以它不是 A.9 拒绝掉的那种共享可变状态，一旦拷贝出去就与缓存再无关系。

于是普通操作永远只面对"放置 / 变换 / 替换 / 破坏"，可靠性不被雕刻污染；而世界又不会缺形状。

建模的合法性仍按 A.6 的分工线：**代码校验结构**（体素是否连续、包围盒是否合理、是否为空），**模型负责好看与合理**。

### A.11 读写同一种表示法

体素进出模型用的是**同一种文本形式**：切片 ASCII 网格。

- **读世界**：给模型一层层的地形网格
- **写形状**：让模型画出分层网格（就像它画像素画那样），代码解析成体素表

模型只需要学一种表示法。而且这比让它输出体素坐标列表可靠得多——一张 8×8 的图里画个矩形，几乎不可能画错；用坐标列表描述同一张桌子，几乎不可能不出错。
