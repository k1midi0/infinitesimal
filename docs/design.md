## 0. 一句话

一个以文字为无限精度的世界。玩家在一张俯视地图上移动、观察、说话、行动；世界的状态由代码持有、是唯一的事实；AI 扮演角色、导演剧情、描述观察对象。

「无限精度」的含义是：你可以一直往下看——看桌子，看桌上的杯子，看杯子上的划痕。但**只有被看的地方才生成，而且生成即固化**。

---

## 1. 根决策

### 1.1 世界状态在代码里，是唯一权威

AI 拥有语言与内容，但**不拥有事实**。模型幻觉最多变成一次失败的工具调用并被退回，不会变成世界真相。

### 1.2 改世界必须显式动手

模型想改变世界，只能通过工具调用提出**后果**，由代码校验后提交。这条来自 Pulsus 已验证的「说话必须是一个动作」：不调用工具就等于什么都没发生。

### 1.3 导演提议 → 判定裁定 → 状态提交

三层各有各的权限。导演只能往时间轴和剧本里放**意图**（"第 3 天夜里，北门有一支队伍经过"），不能直接改数值；判定只负责裁定；所有写入汇入唯一的提交层。

### 1.4 便宜的档位没有写权限

快速档**只能追加**，只有思考档能**改写**。追加是最安全的操作（最坏是啰嗦），改写是最危险的操作（最坏是丢掉事实）。

这条在导演身上落成了具体形状（§8.5）：**快速档唯一的写权限是批注**，剧本、时间轴、地图、NPC 的循环只有思考档改得动。

### 1.5 三条「永不」

- **记录永不改写**：要修正只能追加。理由是可回放、可归因。「基本不变」在实现里会退化成「有时候会变」，而那种 bug 查不出来。
- **事实永不靠回忆**：任何喂给决策者的东西都必须来源于结构化事件，不能让模型凭记忆复述。
- **驳回理由不撒谎**：世界内的驳回（够不着）和协议内的失败（我们自己的 bug）绝不能用同一句话呈现。

## 2. 三层分离：事实 / 记录 / 呈现

同一件事在系统里有三种形态，各有各的规则，不互相污染。

| 层 | 内容 | 谁写 | 稳定性 |
|---|---|---|---|
| **事实** | 结构化后果（地形变了、杯子到地上） | 判定系统 → 直接写地图 | 就是当前状态，不需要专门记录 |
| **记录** | 第三人称 + 角色 ID（客观、不含措辞） | 快速模型 | **永不改写**，只能追加 |
| **呈现** | 名字 + 措辞（给玩家和 AI 读） | 渲染器 | 可固化、可细化叠加 |

记录的形态举例：

```
用户id 用胳膊横扫整个桌面，然后愤怒地盯着（矮人角色id）
```

它"基本不会变动"，正是因为它**不含措辞**——它是记录，不是文章。所以呈现层才需要渲染，而渲染层有自己的规则（见第 7 节）。

**呈现文字必须由记录生成，不能与记录平行生成。** 平行生成的两份东西一定会漂移。

## 3. 角色

### 3.1 统一 Actor

代码里只有一种角色类型 `Actor`：有位置、有感知、有属性、能执行同一套动作。玩家和 NPC 的唯一差别是**控制器是人还是 AI**。

判定、渲染、感知、动作接口、存档格式——每样都只需要写一套。

### 3.2 三类控制器

| 类型 | 控制器 | 上下文 | 笔记 | 智能 |
|---|---|---|---|---|
| 玩家 | 人 | 屏幕（人自己记） | 无 | — |
| 剧情 NPC | AI | 持久 | **可以写** | 高（队友、魔王及其左右手） |
| 氛围 NPC | AI（只在被指向时唤醒） | **持久，与剧情 NPC 同** | 活跃时可以 | 低（酒馆里的矮人） |

氛围 NPC 不是"便宜的 AI"，而是**平时根本不是 AI**：

- 它们**无人值守时在干什么**，由**状态循环**（一张周期表：时刻 → 状态，§3.2.5）查出——**代码查表**，不消耗任何模型调用。
- 只有**被剧情 NPC 或玩家影响**时，模型才**接管**。
- 循环排出的是**基线**（派生量，不存储）；接管产生的是**覆盖层**（存下来的事实）。世界状态 = 基线 + 覆盖。

**位置不在循环里**（2026-09-26 定）：NPC **待在被放下、或被挪到的地方**——那是一个存下来的值，不是派生量。原设计那句"位置由时间轴上的日程算出"因此作废，理由在 §3.2.5。

于是世界可以容纳成百个氛围 NPC 而**成本零增量**——但有一句要说准：

**它们的记忆是常驻的，只是不注入。** 氛围 NPC 有和剧情 NPC 一样的完整上下文与记忆；那些记忆一直在库里，也一直按 §6.1 的规则累积（范围内的广播会追加进它的 id 列表）。省下来的不是记忆，而是**唤醒**——循环中状态下没有任何模型调用，所以那段记忆不装进提示词、不花钱。

**成本来自被唤醒，不来自有记忆。**

#### 3.2.1 活跃氛围 NPC

被指向之后，氛围 NPC 转化为**活跃氛围 NPC**——功能上等同剧情 NPC（有持久上下文、能写笔记、能主动行动），但**保留它的状态循环**。

转化的同时**直接唤起思考档导演**，由导演统筹三件事：

1. **人设的追加**：这次事件给它添了什么设定
2. **归宿**：升为剧情 NPC，还是事件结束后回归循环
3. **是否生成支线剧情，甚至主线剧情**

如果只是小事，导演不必动剧情，只给活跃 NPC 一个**目标**：**以循环中的某一节点为目标，达到后回归循环**。这比"等一段时间"高明——回归条件是一个**世界内的、有意义的判据**，不是一个计时器。一个被揍了的矮人不是"30 分钟后消气"，而是"回到酒馆自己的位置上"。

回归时，它的经历**归档成人设追加**（上面第 1 件事），笔记保留但不注入。于是它下次被激活时带着"上次那件事"的影子——**世界因此会缓慢地记住，而不需要让所有角色常驻**。

回归意味着回到**当前时刻**状态循环规定的那一格，不补演错过的部分。

#### 3.2.2 循环与角色绑定，死亡只是停止

循环是**角色自身的属性**，不是独立的一层。角色死亡后：

- **信息全部保留**（人设、记忆、笔记、循环定义）
- **循环停止**——它不再出现在世界上

之所以是"停止"而不是"删除"：**死亡不一定不可逆**。亡灵法术、复活之类的剧情需要那个角色和它的循环回来；删除会让这类故事无法实现。

同一条兜底也适用于活跃 NPC：**目标永远达不到**（玩家把它锁起来、带走了）需要一条超时规则，重新唤起导演裁定。

#### 3.2.3 知识不是分发的，是当场授予的

导演补出来的世界事实（"东街有个木匠"）写进**地图**，但**不写进所有氛围 NPC 的记忆**。

原因很实在：**无法快速判断哪些 NPC 该知道、哪些不该知道**——那是语义判断，而循环中的氛围 NPC 没有任何模型在场，代码做不了这件事。这时的正确做法是**不做**，而不是用代码近似：代码近似出来的知识分布会**静默地错**，而错的方式没人看得出来。

于是分工是：

| 谁 | 什么时候获得新知识 |
|---|---|
| 世界 | 事实一产生就有 |
| 活跃 NPC | **被指向的那一刻**，由导演按需授予 |
| 循环中的氛围 NPC | 不处理 |

好处是**"谁知道什么"不是被维护的状态，而是每次交互现场决定的**——没有知识图谱，没有传播机制。

代价是循环中的氛围 NPC 认知会过时；但它们在**被指向的瞬间就转成活跃**，导演接着会补上它需要的知识，所以系统会自愈。

**授予多少由导演自行裁决**，不写死规则——补一个点还是补一批常识，视当时情境而定。设计只需要给它这个能力。

#### 3.2.4 没有事实表，地图就是事实库

世界**没有独立的事实记录**，只有地图本身。所以"东街有个木匠"这件事**必须物化成实体**——一个木匠角色加一个作坊地点，落在地图上。

直接后果：**导演补事实 = 往地图里放实体**，而不是往某个事实表里写一行。查询"哪里有木匠"就是查地图上有哪些类型为木匠的实体。

这关掉了"事实表与地图不一致"这类 bug 的可能性——**根本没有第二份可以走偏的数据**。

#### 3.2.5 状态循环与待办是两样东西

（2026-09-26 定）氛围 NPC 的时间结构有**两套**，而它们的**消费者不同**：

| | 状态循环 | 待办（日程） |
|---|---|---|
| 回答 | 无人值守时它在干什么 | 它打算在某个时刻做什么 |
| 形状 | **周期表：时刻 → 状态** | **时刻清单：时刻 + 一件事** |
| 谁读 | **状态机（代码）**，零模型调用 | **模型**，进提示词 |
| 谁写 | 生成时由导演写 | 生成时导演写；**NPC 自己也能写** |
| 例子 | 07:00 开门 / 12:00 吃饭 / 23:00 打烊 / 次日 07:00 又开门 | 「明天去修铠甲」；路边受伤的法师有一条「等待救援」，起于它诞生、**止于无限** |

分开的理由是**消费者不同，代价就不同**：

- 周期表由代码查，所以氛围 NPC 可以有成百个（这是"成本零增量"的全部来源）。
- 待办要进提示词，所以它只能属于少数几个。
- **NPC 能写的是待办，不是循环。**「明天去修铠甲」是它自己的一件打算；把循环交到它手里，等于让它改自己的作息——那件事归导演（§8.3）。

待办**到点之后提醒模型**：它是"时刻 + 一回事"，不是"到点自动发生"。

**位置既不在循环里、也不在待办里。** NPC 待在被放下或被挪到的地方。这一条推翻的是原设计那句"位置由日程算出"——它要求循环知道地点，而"在哪儿"是判定随时会改的事实，两者迟早会打架。活跃期的目标是**回到循环上**（§3.2.1），不是"等一段时间"。

### 3.3 玩家的宿主元能力

玩家身上挂着一层 NPC 不该有的东西：**存档、读档、时间快进、查看器**。这些不是世界观里的动作，是宿主能力。

别把「存档」做成世界观里 NPC 也能做的动作——否则世界会自相矛盾：一个 NPC 凭什么能读档？

### 3.4 三种输入通道

- **地图点选**：结构化的，不需要任何模型解析。
- **说**：一个输入框。
- **做**：一个输入框。

NPC 拿到的是同一套东西的 AI 版本：一份格式化的地图视图，加上「说」和「做」两个工具。

### 3.5 角色卡（已定；卡已进提示词，写卡时的换算未做）

形状抄 Pulsus（`D:\fatfish\Pulsus\shared\src\commonMain\kotlin\io\github\k1midi0\pulsus\config\CharacterCard.kt`）：**一张卡 = 一个命名字段**，不是「角色卡」这个整体。

```kotlin
data class CharacterCard(title: String, content: String)
```

- **标题永不进提示词**，只有内容进；按数组顺序取内容、去掉两头空白、跳过空串。
- **预设几种，其余自己起名拓展**——这就是「可拓展属性」的意思：加一项不是加一个字段，是加一张卡。Pulsus 那边预设七种（角色名 / 背景 / 性格 / 场景 / 开场白 / 示例对话 / 历史后指令），这边按玩法自己取。
- **它不在世界实体表里。** `Entity.attributes` 是模型能通过 `SetAttribute` 改的**世界状态**（「两手空着」）；角色卡是人设，**判定改不到它**，改它要走导演或界面那条路。这与 §2 的「事实 / 记录 / 呈现」是同一个分法。
- **挂在 `Entity` 上**（`cards: List<CharacterCard>`）：角色就是物体的一种，不必为它另开一个类型，也不必另开一张要同步的表。NPC 各有一张。
- **给判定的范围**：发起者 + 这次动作指向的其它角色（§4.6 第一步的结果）。第二步才知道指向谁，所以这一段只能拼在**两步共用的前缀之后**——前缀本身不变，缓存才仍然命中（§8 的动静分层）。

**距离在卡里已经换算好。** 有的故事会写明确的交互范围（伸手够得着多远），有的没有。换算发生在**写卡 / 导入卡的那一步**，和 §5.2 的第三人称化是同一个位置：入库时改写一次，之后所有人都读同一份。卡里存的是「伸得着 1 格」这样的字（基准见附录 A.12：1 格 = 1 米），**判定不做算术**。卡里没有这一项时**不给这一行**，由模型按情境判——A.6 那条分工线。

## 4. 输入与裁定

### 4.1 一次提交 = 一个意图

玩家可以在地图上多选对象（桌上的物品、桌边的矮人），然后在动作框里写一句话：

```
用胳膊横扫整个桌面，然后愤怒地盯着矮人
```

这**是一句话、一个意图、多条后果**，整体裁定一次。

驳回粒度 = 提交粒度，而提交粒度由**玩家的输入单位**决定，不由后果数量决定。如果按后果逐条驳回，这句话的后半句会因为前半句被驳而莫名其妙地消失，玩家会觉得系统听不懂人话。

### 4.2 判定 = 模型段 + 代码段

**动作描述不能穷尽**，纯代码的规则表永远写不完"用胳膊横扫整个桌面"。所以判定必须是两段：

- **模型段**：读「动作描述 + 当时的环境」，决定成不成立、该有什么后果。一次调用产出三样东西：**合不合理 + 后果清单 + 驳回理由**。
- **代码段**：校验模型提议的后果是否合法（对象在不在、在不在范围内、数值合不合理），然后提交。

**「解析」与「判定」不能是两次模型调用。** "想干什么"和"能不能成立"依赖同一份环境上下文；拆成两次就是两次延迟、两次成本，中间还多出一个**没人消费**的半成品状态（解析成功了但判定说不行，这个中间产物谁都不需要）。

**判据不是"调了几次"，而是中间产物有没有人消费。** 所以这条只禁止"没有消费方的拆分"——它**不**禁止 §4.6 那个两步：那里第一步输出的对象集，是第二步的必需输入。

### 4.3 驳回有两个层次

| 层 | 谁判 | 内容 | 呈现 |
|---|---|---|---|
| **世界内** | 模型 | "你够不到整张桌子，你只能够到半边" | 写成自然语言给玩家看 |
| **协议内** | 代码 | 模型提议的后果非法（越界、对象不存在） | **退回给模型重试，绝不示给玩家** |

混淆这两层的代价是：将来出了 bug，玩家看到的是"你的操作不合理"，而实际上是我们的代码或模型的提议坏了——你会在错误的层次上排查很久。

被驳回的操作**不产生任何记录行**（Pulsus 已验证的做法）。

### 4.4 后果的去向

判定通过后由判定系统执行：桌面上的物件移到地上，玩家在地图视图里直接看到图标变化。

**地图是数据的视图，不经过任何模型。** 渲染器只管文字描述。

---

### 4.5 判定的两面：提议与裁定

**后果有一份固定的词汇表**，模型只能通过工具调用提出它们，不能直接写字数（§1.2）：

| 工具 | 含义 | 变化等级 |
|---|---|---|
| `move` | 挪位置 | **不动描述** |
| `reparent` | ~~换归属（杯子从桌上到了手里）~~ **已删**（A.13：没有关系要存） | — |
| `set_attribute` | 改一个结构化属性 | 外表变化（描述作废） |
| `change_appearance` | 只是看起来不一样了 | 外表变化（描述作废） |
| `destroy` | 消失了 | — |
| `spawn` | 凭空多出一个东西 | 新物品 |
| `replace` | 彻底变了，是另一个东西 | 新物品（**必须换新 id**） |
| `affect` | 记下影响了哪个角色 | — |
| `reject` | 这次动作不成立 | — |

**最要紧的一条：变化等级不是模型填的枚举，是从它调用哪个工具推出来的。**

`change_appearance` **没有形状参数**，`replace` **必须给新 id**。于是"声明只是外表变化、却交回一个新形状"这种自相矛盾**无法被表达**——不是"表达了再被校验"，是根本没有那个字段可填。这与 §7.2 是同一条原则：**写操作的限制要落在数据模型上，不落在提示词上。**

两条容易被忽略的推论：

- **`move` 不动描述。** 这是 §7.6「描述只讲物体自身」白拿的好处：把杯子从桌上挪到地上，杯子本身没变，**不烧一次渲染**。（`reparent` 已随 `parent` 一起删掉，A.13。）
- **`set_attribute` 算外表变化**，所以它作废描述。属性变化通常正是"擦干净桌子"那一路；保守地重渲染一次，比留着一条已经过时的描述便宜——**过时的描述是更坏的失败**。

**驳回与后果互斥**，而这是代码能验的结构约束：同时给出驳回理由和后果时，代码**不选边**，而是当成一次协议内失败退回重试。默默选一边正是那种会把 bug 藏起来的事——两边都自洽，谁都不会报错。

#### 驳回的两层，落地形态

| | 谁判 | 表现 |
|---|---|---|
| **世界内** | 模型调 `reject` | 理由**原样给玩家看**，措辞要像这个世界在说话 |
| **协议内** | 代码校验不过 | **退回重试**（最多两次模型调用），失败也绝不示给玩家 |

协议内失败包括：id 不存在、`replace` 的新 id 与旧 id 相同、新 id 撞上已存在的、祖先链成环、一批里后面的后果引用了已被收走的东西。**校验用一份影子状态在落库之前做完**——所以"一批里第 3 条非法"不会让前两条先写进去。

#### 一次意图、多条后果

一次提交 = 一个意图，可以作用于多个被选中的对象，产出**多条**后果，整体裁定、**原子提交**（§4.1）。实测里"用胳臂横扫整个桌面"产出了四条（酒杯和油灯各两条）。

**穷尽是判定的职责**，所以 `Scene`（给模型的地图视图）必须标出**谁挂在谁下面**——第一版没标，模型就漏掉了桌上的第二样东西（只有酒杯被扫下去，油灯还在桌上）。这与 §7.6 不冲突：那条禁的是**渲染器的输出**里出现位置关系，不是判定看不到归属。

---
### 4.6 两步：先对齐对象，再算后果

判定**分两步**——它们依赖的输入不同，失败的补救方式也不同。

| | 输入 | 输出 | 档位 |
|---|---|---|---|
| **第一步 对齐指向对象** | 动作 + 场景 + **玩家选的** | 修正后的对象集；或驳回 | **快速档** |
| **第二步 列出后果** | 动作 + 场景 + **对齐后的对象** | 后果清单；或世界内驳回 | 思考档 |

玩家在界面上选中的东西**只是一个猜测**：动作说的是"桌上的东西"而他只点了桌子；或者他点了三样、动作只碰其中一样。第一步的职责就是把这个对齐全。

#### 「能不能拆」的判据

§4.2 原来写的是"这两段不能是两次模型调用"。**那句话太粗，正确的判据是：看中间产物有没有人消费。**

- 反对的拆法：**解析玩家想做什么** vs **判定它成不成立**。两者输入几乎相同、依赖同一份判断，那个中间产物**没有任何人消费**——拆开只是多一次延迟。
- 采用的拆法：**对齐对象** vs **计算后果**。前者输出的对象集是后者的**必需输入**。

所以 §4.2 那句话应当读成：**没有消费方的中间产物，不该被拆出来。**

#### 驳回因此有了两个阶段

`Stage.ALIGN` 的驳回是「**你选错了**」——玩家改一下选择就能重来；`Stage.EFFECT` 的驳回是「**这样做不成立**」，那是终局的。混在一起时，模型会把"你选错了"说成"不成立"，而玩家**没有任何机会改他的选择**。

#### 实测（`spike/JudgeProbeSpike`）

| 案例 | 第一步对齐 | 用时 |
|---|---|---|
| 「我拿起桌上那杯麦酒」，玩家**什么都没选** | 补出 `wine_cup` | 2723 ms |
| 「我把杯里的酒一口喝掉」，玩家**多选了油灯** | 剔成 `wine_cup` | 2816 ms |
| 「我掏出抹布把桌面擦干净」 | 加上 `rag`（抹布确实会脏） | 4482 ms |
| 「我把桌子劈成两半」 | `oak_table` | 11219 ms |
| 「我伸手把三条街外的杯子拿过来」 | — | **997 ms** |

三条结论：

1. **延迟没有变差。** 两步全跑 2.5–4.5 秒，单步时是 4–6 秒——第一步很快，而且对齐之后目标更少、第二步的输出更短。
2. **驳回快得多，而且更准。** 最后一条在**第一步就拦下了**（997 ms）：动作指向的东西根本不在场景里。以前它要在第二步被驳回，理由是"你的手伸不出去"——那说的是另一件事。
3. **两步共享前缀**：`system` 与「情境 + 发起者 + 动作」逐字相同，只有工具集与末尾指令不同。第二步的缓存命不命中还没单独量过（门槛见 §14.5）。

#### 一个暴露出来的词汇表问题：`Replace` 不够用

同一个"劈成两半"跑两次，模型一次用 `Replace`，一次用 `Destroy + Spawn×2`。**两种在世界状态上都对**，而后者更准——桌子劈开确实变成了**两个**东西，`Replace` 只支持"一变一"。

**暂不处理。** `Replace` 保留，因为它是"一变一"的显式表达，且带一条 `Destroy + Spawn` 没有的保证（新 id 必须与旧 id 不同，逼调用方承认这不是外表变化）。代价是模型有时绕开它——**但绕开并不危险**：`Destroy + Spawn` 的语义明确，没有可矛盾之处。**要断言的是世界级的结果，不是它挑了哪只工具。**

---
### 4.7 纠正预览：对齐结果回到玩家手上

§4.6 的两步判定一度是一口气跑完的：对齐 → 算后果 → 提交，中间不停。现在中间停一次。

**对齐出来的目标集合与玩家勾选的不一致时**（按集合比，勾选的先后不算），这一轮在第一步之后停下，把纠正后的指向标在界面上。**停下来的代价是零**——第一步只对齐、不改世界，所以这时世界一个字都还没动，没有要回滚的东西。

界面上是三样：**一句话 + 两个按钮 + 地图上发光的边框**。

- 那句话：「判定认为这次动作作用在：木桌、酒杯　——和你勾的不一样。世界还没动。」
- **应用**：接受纠正后的指向，接着跑第二步（算后果）并**直接提交到世界**，只在日志里报结果。
- **改动作**：把这一次丢掉，那句话说回输入框——多数时候玩家要改的只是勾选，话还是同一句。
- 地图上，被纠正后的那几个目标**带一圈发光的边框**（`ui/GameScreen.kt` 的 `PendingPanel` 与 `MapPane` 里那两处 `drawCircle`）。玩家一眼看到"它以为我要动的是那个"。

一致时**不出预览**，直接往下——不让勾对了的玩家每一次都多按一下。

驳回不走预览：它没有「纠正后的指向」可标。但**驳回理由必须是范围内的**：「这一片里没有扫帚」，不是「没有扫帚」——模型拿到的只是一小片，不是整个世界，这件事写在提示词里（`Judge.sharedPrefix`），也写在 `reject_targets` 的说明里。它原来会撒谎不是因为它想撒谎，是因为没人告诉它手里那片不是全部（§14.12）。

它同时兜住了另一件事：玩家什么都没勾、判定只能猜的那种局面（§14.12 采样里的甲、乙、丁三个场景全是这个形状）。猜错了会在界面上被看见，而不是直接改掉世界——丁那两轮「拿手边的酒杯顶替」正是它该拦下的。

**实现上的形状**（`judge/Judge.kt`）：`beginTurn(world, request)` 开一次判定，返回一个 `Turn`；`turn.align()` 跑第一步，`turn.finish(targets)` 跑第二步并提交。`Turn` 攥着那个 `ViewBudget`——**扩大的预算是一次动作的属性，不是某一步的属性**，所以玩家确认完再跑第二步时拿到的是同一个（已经扩大过的）框（`JudgeTurnTest` 钉着这一条）。一次性的 `judgeAndCommit` 与它共用同一份实现，所以"停了再走"没有长出一条只在预览那条路上才有的分叉。

## 5. 信息传递

### 5.1 对话

按范围广播给范围内所有玩家。UI 上表现为对应角色上的一个气泡，**仅存在当前回合**。对 AI 玩家，收到的是「角色 id + 角色说的话」，话不做任何处理——就像现实一样。

**有指向性的**：玩家选中矮人后输入"你好"，矮人的 AI 会收到带专门标识的「指向自己的角色 id + 话」。

### 5.2 动作

判定模型在裁定时就**同时判定影响对象**，被影响的角色自然是被指向者，本来就会收到定向信息。

快速模型把动作转成第三人称记录并储存，直接发给被指向的 AI 玩家；其他未被指向的 AI 玩家也可以查看。

### 5.3 UI 呈现

| 内容 | 位置 |
|---|---|
| 被指向的动作 | 观察窗口里直接显示 |
| 未被指向的动作 | 地图视口里角色标识上的提示，可点开查看 |
| 对话 | 角色上的气泡（仅当前回合） |

### 5.4 未解决的漏洞：「在范围内」不等于「能听见」

范围是几何的，感知不是。两个 NPC 在角落低声密谋，站在旁边三步的玩家按范围也会收到全部内容——**现在没法说悄悄话**。

两条路：(i) 广播分「公开」与「低声」两档，低声只投递给被指向者；(ii) 代码先按范围粗过滤省成本，"听没听见"再由判定模型裁。

倾向 (i)：它便宜、确定、立刻可用；而 (ii) 会把一次广播变成一次模型调用。

## 6. 记忆

### 6.1 短时：滚动窗口

保存**最近若干回合的话与事**。第三人称记录里已经生成了客观描述，所以不需要再单独做一份摘要。

#### 装什么

装的是**客观记录**（第三人称 + 角色 id），**不装角色的内心与计划**——那些属于它自己的笔记（§6.3）。窗口是**世界对它的广播记录**，不是它的日记。

#### 粒度：一份事件流 + 每角色的 id 列表

不是"全局一份"或"每角色一份"二选一，而是第三种：

- 只有**一份事件流**，append-only，措辞唯一
- 每个角色有一个**指向该流的 id 列表**，装它感知到的那些
- 注入时按 id 取最近若干条，加上当前地图视图与人设

这样同时拿到两边的好处，且没有"每角色一份"的两个缺点：

| 方案 | 写入成本 | 措辞一致性 | 信息隔离 |
|---|---|---|---|
| 全局一份 | 1 | 一致 | **被捅穿**：不在场的 NPC 也读到 |
| 每角色一份 | O(M) 放大 | **可能漂移** | 成立 |
| **事件流 + id 列表** | 1 条记录 + M 个 id | 一致 | 成立 |

另外它**可审计**：出问题时你能回答"这个 NPC 当时到底收到了什么"，因为 id 列表就是证据。这也是 Pulsus 验证过的形状——一份数据，两种读法（全局读法给导演，按 id 过滤的读法给角色）。

#### 怎么裁

Pulsus 的三条规则直接搬过来：

1. **只按整轮裁剪。** 在这里的含义是：**一次提交产生的全部后果不可切开**——掀桌子产生的"桌翻、杯落、酒洒"必须一起进出。切开会让角色形成矛盾认知：它看到杯子在地上，却没看到桌子被掀。
2. **最新一轮无论多大都保留。** 丢掉它等于丢掉正在被回应的东西，那不是更小的请求，是另一个请求。
3. **先落库，再裁窗口。** 库是记录，窗口只决定下次请求带多少。

加一条本项目特有的：**双约束**——token 预算是硬约束，回合数 N 是上限，两者谁先到就按谁裁。

#### 多大

- N 由 spike 实测定，不由拍脑袋：观察 NPC 在多少轮之后开始重复或自相矛盾。
- token 估算：中文 1 字 ≈ 1 token（留余量；接口实测约 0.6）。
- **参与者不同，N 不同**：氛围 NPC 与剧情 NPC 同一档，导演更长（它低频、用思考档）。

#### 子问题

- **氛围 NPC 有完整记忆**（已定）。玩家昨天骂了酒馆矮人，今天它记得。范围广播照常追加进它的 id 列表——**投递总是发生，唤醒才是例外**。
- **玩家自己要不要一份窗口**：要，但性质不同——那是**查看器**，给玩家看的，不是给模型看的。它属于玩家的宿主元能力。

#### 一条叙事上的确认

角色离开再回来，它没感知到的那些事**不在它的窗口里**，所以它看到的历史是跳跃的。这是**正确的**：它应该通过观察发现变化，而不是通过记忆。时间轴和导演知道中间发生了什么。

### 6.2 长时 A：摘要系统（导演专有）

面向**流**的压缩。输入是最近发生的事，由系统在导演被唤醒时触发。是**被动整理**。

### 6.3 长时 B：笔记系统（剧情 NPC 可用）

面向**点**的主动记录。NPC 自己决定"这件事我得记住"，通过工具写一条。是**主动写入**。

两者**存储形状相同**（所有者 + 内容 + 标签 + 时间），共用一个表；但**工具与触发完全不同**，所以是两个工具。导演如果按统一 `Actor` 建模，它的摘要就只是"它自己名下的笔记"。

### 6.4 可变性必须分开

两类内容必须分节（分表）：

- **发生过的摘要 / 记录**：append-only，历史不会变。
- **注意事项**：**会被推翻的**。"玩家欠矮人一笔钱"，在他还清之后必须失效。

混在一起，"注意事项"会退化成一堆互相矛盾的历史陈述，而模型会**同时相信它们**。这种错不报错、不崩，只表现为**导演偶尔作出基于过期事实的决定**——最难查的一类 bug。

失效用**追加 + 显式 supersede 标记**，永不删除。理由和「记录永不改写」一模一样：你要能在事后回答"导演当时为什么这么决定"。

### 6.5 检索方式

沿用已经定过的那套两层结构：

- **注意事项常驻注入**（必须小，设字符预算与可见的截断标记）
- **摘要按关键词检索**（中文 bigram 分词 + LIKE 转义 + 字符预算）

NPC 笔记量小，可以全量注入并设上限。

### 6.6 权限与容量

- NPC **只能读自己的笔记**，不能读别人的。
- 只能追加 + supersede，不能删除。
- 需设容量与频率上限（每角色 N 条 / 每回合至多 1 条），否则 NPC 会把笔记写爆。

## 7. 渲染（观察器）

渲染器**不是旁白者**，它是观察器：`观察(X) → 描述(X)`。没有剧情、没有语气、没有"你走进房间，一股霉味扑面而来"。旁白性的文字来自导演，而且低频。

### 7.1 固化，以及两种「变化」

**描述一旦落库就不再改变——除非物体本身变了。** 而"变了"有两种，性质完全不同：

| | 仅仅外表变化<br>（桌子被擦干净） | 彻底改变<br>（桌子被劈开） |
|---|---|---|
| **身份 id** | 不变 | **新的 id** |
| **体素形状** | 不变 | **新建模** |
| 属性 | 可能变 | 全新 |
| 描述 | **作废，重新渲染** | 新物体的新描述 |

**分界线是形状（建模）。** 几何没变，就还是同一个物体，只是外表不同——重渲染即可；几何变了，它就不是原来那个东西了——新物品、新形状、新描述。

为什么必须分开：

- **全都换 id** → id 爆炸，而且玩家认知里"那张桌子"在不断换身份，引用与记录都碎掉
- **全都只重渲染** → 形状变了却只改文字：地图上还是一张完整的桌子，文字却说它被劈成两半，**俯视图与文字打架**

所以**判定系统要判定的不是"变没变"，而是"变到哪一层"**：未变 / 外表变化 / 彻底改变。这是后果清单里的一种操作，而不是一个布尔值。

**代码能守住这一条**（附录 A.6 的分工线）：判定系统声明"这只是外表变化"时，它提议的体素形状**必须与旧形状相同**；声明"彻底改变"却交回同一个形状，就是自相矛盾。**这个一致性检查是结构性的，代码做得了**——退回重试，不当成玩家的错。

**「把 A 换成 B」因此是一种后果操作**，与"移动""改属性"并列：删掉一个物体、加上一个物体。旧 id 从此不在世界态里，但它的记录**不删除**（§1.5 记录永不改写）——否则"你记得它原来是什么样"就无从谈起。

背景（地点的）不变，见 §7.5。

### 7.2 细化只叠加

玩家已经读过的粗描述是承诺。细化只能**增加**细节，**不得推翻已有描述**。所以每次细化请求都必须带上现有描述，并要求"只补充，不矛盾"。

「覆盖」只允许作为「世界真的变了」的结果（走失效条件 1 或 2），不能作为细化的默认行为。

### 7.3 何时调用模型

| 场景 | 是否调模型 |
|---|---|
| 普通移动 | 不调，回显已固化的描述 |
| 首次进入某节点 | 调，生成并固化 |
| 玩家主动「查看」某物 | 调，生成或叠加细化 |
| **声音事件** | **不调**：由代码按几何快速判断影响角色 |
| 其他事件 | 调：由判定模型判断影响对象 |

#### 被动感知不是独立的一层

没有单独的"被动感知系统"。事件的影响对象只有两个来源：

- **声音** → **代码**判断。声音是唯一可以用纯几何确定的类型——距离、音量、遮挡，不需要理解语义；而且它必须**即时**，因为在没有旁白的世界里它是唯一的"打断"，不能等模型三秒。
- **其他事件**（视觉、物理、社交）→ **判定模型**判断。这与第 5.2 节动作的投递是同一条路径：判定模型本来就要输出影响对象，"角色指向"就是它的输出。

措辞层按模板处理（"你听到远处一声闷响"），要展开必须玩家主动观察。

两条路径的代价不同，必须分清：**代码路径不会泄露玩家不该知道的细节；模型路径能理解语义，但模型很乐意告诉你隔壁房间发生了什么**——所以模型路径的输出必须先过感知过滤再投递。

**声音的传播规则挂在世界结构上**（按距离，还是沿相邻边），所以它依赖第 12 节的待定项 1。

### 7.4 结构从预设来，文字只在被看时生成

预设库给的是**结构**（数值、标签、名称、拓扑），非模型驱动；渲染器给的是**文字**，模型驱动、且固化。

### 7.5 渲染器的输入是三段，背景由导演提供

```
[规则]  观察器该怎么做 —— 全局静态，逐字不变
[背景]  这是哪里、什么时期、出了什么事 —— 导演写，每地点稳定
[对象]  被观察的东西本身 —— 每次都变
```

**背景是每样东西自己那一份**，写在实体上（`Entity.background`）——生成这样东西时由导演写下，用来控制渲染风格。它因此落在**地图**里，而不是另立一张"背景表"——世界只有地图这一份事实（§3.2.4）。渲染器**只读**它，这与"导演是世界的补写者"（§8.3）是同一条。

> 2026-09-24 改了：早先是"写在**地点实体**上、物体沿 `parent` 链继承"。`parent` 删掉之后（A.13），
> 背景跟着变成每样东西自己的一份——**酒馆的酒杯与皇宫的酒杯的差别就在这里**。

前两段必须拼成**一段**不可变前缀（不是两条 system 消息）：缓存按 token 前缀匹配，分成两条只会在中间多出 role 标记，对命中没有任何好处，却让"前两层"变成两个要各自维护的东西。

**背景带来的是"不脱离世界"，不是"命中缓存"。** 实测：加上背景后渲染器前缀约 277 token，同地点连续观察四个不同物体**命中全为 0**；而 2799 token 的长前缀能稳定命中 2560。这条规则见 §14.5——**缓存只对上下文本来就很长的系统（NPC、导演）有意义。**

**背景不会变**（已定，见 §7.1）：导演为某地点写下背景之后就固定下来。所以"背景变了、地点里已固化的描述过时了"这种情况不存在，那条顾虑整个消失。

### 7.6 描述只讲物体自身，而且这一点要落在输入上

观察到的描述**只能讲这个物体的外表**：不写它周围有什么，不写它与别的东西的位置关系。

这不是风格偏好，是**固化能成立的前提**。因为关系会变、而物体自身没变：旁边的酒杯被拿走后，一句"一侧对着吧台"就过时了——可 §7.1 的两种变化**都不包含"邻物改变"**，于是那条描述会**静默地过时**，永远没人发现。把周边写进描述，等于给每个物体塞进一堆它管不着、也不会因此重渲染的依赖。

**处置不是"在提示词里叫它别写"，而是输入里压根不给。** 渲染器的输入原来带着坐标与"所在"，模型于是忠实地把它们用上了：

> 它靠大厅中央立柱横向摆着，一侧对着吧台，另一侧留出较宽的通行走道。

去掉坐标与"所在"之后（`parent` 链仍然用来取地点背景，但**不再告诉它"你在哪"**），实测输出变干净了：

- 基线：「橡木桌呈深褐色，表面打磨得光滑，木纹清晰而紧密地延展。」「四条桌腿厚实笔直，支撑着两米长、一米宽的桌板，整体高约零点八米。」
- 工具插入的新句：「桌面中央泛着一层薄薄的油光，是被常年擦拭摩挲出来的温润包浆。」
- FIM 插入的新句：「桌面边缘有一道浅浅的弧形磨损，像是常年被手肘倚靠留下的痕迹。」

**没有素材，就写不出来**——这与"写操作的限制要落在数据模型上"（§14.2）是同一条原则，只是这里限制的是**输入**。

配套一个**开发期抽查**：扫关系词（旁边、一侧、搁在、对着…）。它**不是可靠的判定办法**——词表永远不全，而"桌子对着吧台"完全可以用词表里没有的说法讲出来。真正起作用的是输入裁剪，抽查只用来验证"裁掉之后输出真的干净了"。

## 8. 导演

后台运行，不直接接触玩家。

### 8.1 时间轴

导演设计时间轴：火山什么时候爆发、魔王什么时候苏醒、酒馆里的矮人一天的循环。所有未来可能发生的事都要有到期时刻，快进才能算出"最早该停下的时刻"。

**没有时间轴就必然漏事**——你睡觉时邻居家着火，是没有任何定时器能预告的。

### 8.2 两个触发器，性质完全不同

| 触发 | 谁检测 | 性质 |
|---|---|---|
| 时间轴**到期** | **代码** | 确定性、可复现 |
| 剧情**跑偏** | **快速模型** | 语义判断 |

快速模型只能**发现**偏离，**不能改时间轴**；改时间轴只有思考模型能做。这是「便宜档位没有写权限」在导演内部的延伸。

### 8.3 职责

生成剧本、埋伏笔、给 NPC 分发日程、生成 NPC、加入突发事件、维护自己的摘要与注意事项。

还有一条容易被漏掉、但在实现上最先撞到的：**导演是世界的补写者**。

玩家问酒馆里的矮人"镇上哪里有木匠"——**这件事不会预先写在矮人的认知里**。如果让矮人先回答，它会现场编一个；两个 NPC 就可能给出两个不同的木匠。所以**导演必须先决策**：把这个事实补出来（镇上有个木匠、叫什么、在哪条街），再让矮人回答。

这条和 §7 的「渲染即固化」是**同一条原则**，只是对象不同：

| 谁 | 输入 | 产出 | 之后 |
|---|---|---|---|
| 渲染器 | 被观察的物体 | 文字描述 | **固化**，下次直接读 |
| 导演 | 被问到的未定义事实 | 世界事实 | **固化**，所有角色此后共用 |

**按需生成，立即固化**——这是整个系统里最反复出现的一条模式。

代价是延迟：每次指向性交互都要等一次导演。所以要把它做窄——这次调用的任务是**判定"是否需要补事实、补什么"**，不是重新规划剧情。窄任务 = 短输出 = 快，而且**必须显式设 `max_tokens`**（思考档默认输出预算是 64K，不能按默认走）。

#### 8.3.1 决策同步，生成异步

这两件事的时机不同，必须分开：

| 阶段 | 同步性 | 产出 |
|---|---|---|
| **决策** | **同步阻塞** | 足够回答当前问题的事实（有个木匠、叫老张、在东街） |
| **生成** | **异步** | 完整的实体与它的循环日程 |

矮人的回答只需要决策的产出；生成慢多久都不影响这一句。反过来，把生成也做成同步，玩家就得为一次完整建模等下去。

#### 8.3.2 导演任务排队

导演在同一时刻只处理一个任务，新任务**排队**。

这不只是省事——**串行是避免并发写冲突最省事的手段**。两个导演任务同时跑，就可能各自补出一个木匠，而且谁都发现不了。

代价是队列会积压，延迟变成"排队长度 × 单次时长"。所以：

- 队列是**全局一个**（世界只有一个权威，串行写最安全）
- 界面上必须有**"世界中…"的指示**。Pulsus 已经踩过这条：生成阶段没有任何文字出现时，玩家会认为程序卡住了

### 8.4 剧本池

（2026-09-26 定）**一份剧本 = 一条完整的剧情，用自然语言写。** 一局里有多份，放在**剧本池**里。

池子里每份只露三样给导演查阅：**标题 + 摘要 + 状态**；正文要打开才看。

| 状态 | 意思 |
|---|---|
| 未安排 | 写好了，但舞台还没搭（地图、NPC、时间轴都还没按它生成） |
| 已安排 | 舞台搭好了，等着玩家撞上来 |
| 运行 | 玩家已经进来了，正在演 |
| 中断 | 暂停——玩家跑去干别的了，**以后可能接回来** |
| 完结 | 终态——这条线不会再发生 |

**"中断"与"完结"的差别是"以后还会不会发生"**，不是"谁结束了它"：

| 例子 | 事情 | 记成 |
|---|---|---|
| 哥布林里的混血儿 | 玩家跑去救法师了，据点还在 | **中断** |
| 结识魔法师队友 | 玩家把法师补了几刀、收走了财宝 | **完结** |

（早先还有一态"放弃"，2026-09-26 去掉；"结束"改名"完结"。）

**剧本是给导演安排环境用的，不是舞台戏。** 它只用来丰富玩家的探索波折，而**探索才是主体**。导演照着剧本设计环境——哪里有个镇子、公告上贴着"圣剑拔出的日子到了"、而圣剑只认勇者——玩家看见公告**自己去拔**；也可能根本不拔，直接走掉。走了就是偏离，导演改剧本。

同一个世界里还会有互相冲突的剧本：有两个仇人，玩家**帮其中一方**，探索就有了深度。

#### 批注

导演除了改正文，还能往剧本上写**批注**：

- 批注是**只追加、永不改写**的一条条记录（`时刻 + 正文`），与正文**分开存**。
- 分工：**改正文 = 改计划**（随时可改）；**写批注 = 记发生了什么**（只追不改）。
- 分开的理由是 §1.5：混在一个字段里，"这条到底是改了还是发生过"就又变成一个读不出来的状态。

### 8.5 两级导演

（2026-09-26 定）导演**每回合都在**，而且**完整上下文不缺**。它由**同一个模型的两套参数**承担——这个项目只绑 `deepseek-flash`（§10.1），"用一个小模型盯、大模型干"在这里没有可能：

| | 快速档 | 思考档 |
|---|---|---|
| 参数 | `thinking: disabled` | `thinking: enabled` + `reasoning_effort: high` |
| 什么时候跑 | **每回合一次**（玩家每做一个动作） | 快速档把它叫起来的时候 |
| 工具 | **两只**：唤醒思考档、剧本标注 | **一次给全**：改剧本 / 建剧本 / 改时间轴 / 生成地图与 NPC / 改 NPC 的状态循环 |
| 干什么 | 看着。发现要动手，就把思考档叫起来 | **主要的工作都由它做** |

**切档就是换参数，历史不重建。** 两级共用**一段 messages**——切档只改 `thinking` 与 `reasoning_effort`，不另起一段历史。理由是缓存：DeepSeek 的缓存按 token 前缀完整匹配，共用前缀才命中（§14.5、§14.8）。

代价是一条要更小心守的纪律：**带 `tools` 的请求，后续所有 assistant 消息必须完整回传 `reasoning_content`**（空思考给 `""`，不能给 null，§10.2）。两级共用历史而工具表不同，这一条比单级时更容易破。

**思考档觉得稳定了，就调工具切回快速档。** 于是"什么时候该想"没有被写成数字（每隔几回合、每隔几分钟），而是**由思考档自己判断**——与 §3.2.1 那条"回归条件是世界内的判据，不是计时器"是同一条理由。

§1.4 那条在这里落成具体形状：**快速档只能追加**——它唯一的写权限是批注（状态改不了，那是改写）；**只有思考档能改写**（剧本、时间轴、地图、NPC 的循环）。

成本上要知道的一件事：**每回合多一次模型调用**。估算约 0.34 分/回合（导演上下文一万 token 上下、大部分命中缓存，叠在判定那 1.2 分上，§14.22）。买到的不是更快的回答，而是**不漏事**。

## 9. 生成系统

导演通过工具调用生成系统这个子系统来完成。分为：

- **地形生成**（**按 chunk 按需生成**、读区划层当地貌输入——A.15、A.16）
- **物品生成**
- **角色生成**
- **建模**：生成新物品的体素模型（见附录 A.9）

它们调用**预设库**，简单修改后放进地图，不需要模型从零雕琢每个细节。

### 9.1 预设库（非模型驱动）

类似数据库，存地形 / 物品 / 角色的模板。默认通用包只给**基本描述**（"杯子"就只是杯子），具体细节按情况具体渲染。

允许**人为导入预设包**。比如一个「西幻世界冒险包」里的啤酒杯可以写成：

```
深色木制的带把手的杯子，直径一分米，把手上下有铁环箍着，杯口有深浅不一的划痕
```

默认通用包不提供这种丰度——它靠导入。

## 10. 模型分档与平台约束

### 10.1 三档

| 档位 | 参数 | 用途 |
|---|---|---|
| **快速** | `thinking: disabled` | 动作解析与第三人称化、摘要、**导演快速档（每回合一次，§8.5）**、氛围 NPC 问答 |
| **思考** | `thinking: enabled` + `reasoning_effort: high\|max` | 判定两步、**导演思考档**、剧情 NPC、建模 |
| **图片** | flash + `image_url` | 视觉理解 |

「快速响应 / 深度思考 / 图片识别」在这家 API 上是**同一个模型的三套参数**，不是三个模型。

### 10.2 平台硬约束（DeepSeek API，2026-09 核对）

- 只绑 `deepseek-flash`：`deepseek-v4-pro` 正在退场，且**图像理解只有 flash 支持**。
- 上下文 1M、最大输出 384K。不设 `max_tokens` 时思考默认只给 64K，**输出预算要自己留**。
- **思考模式下 `temperature` 不生效**，能动只有 `top_p`（夹在 0.95–1.0）；只有关闭思考的快速档才有 `temperature`。想要文字多样性，就只有快速档。
- **带 `tools` 时，每条 assistant 消息必须回传 `reasoning_content`**，没有思考时给 `""`（不能是 null），否则 400。
- 思考模式下 `tool_choice` **不支持 `required` 与具名**（400）。**没法强制模型"这轮必须调这个工具"**。
- `strict: true` 需 base_url 换成 `/beta`，且每个 function 都要设。object 的所有属性必须进 `required` 且 `additionalProperties: false`；不支持 `minLength`/`maxItems` 等。
- 并行工具调用**关不掉**。一回合可能同时回来多个工具调用，且顺序由模型决定——所以状态改动层必须**一次性校验 + 提交**。
- 缓存按 token 前缀**完整匹配**，尽力而为，几小时到几天清空；隔离旋钮是 `user_id` 而不是 API key。
- **动静分层**：不动的东西（世界观、规则、人设）放最前，每回合在变的东西（血量、位置、状态）放最后。**但它有前提，见 §14.5：短前缀根本命中不了缓存**，所以这条只对上下文超过一个缓存单元的系统（NPC、导演）才有收益；渲染器那种 170 token 的请求，做了也白做。
- 并发是**账户级、与 key 无关**（flash 2500）。多配 key 不会多出并发；要加并发走扩容工单，且不加价。
- 成本（flash，元/百万 token，高峰/空闲）：输入命中 0.04/0.02、未命中 2/1、输出 8/4。**约 1.2 分/回合（高峰），100 回合约 1 元**——成本不是第一性问题，**延迟才是**。
- 没有 embeddings、没有 fine-tuning、没有 Batch、没有 TTS。**不存在 RAG 这条路**。

### 10.3 配置分层

客户端按**供应商 → 模型 → 档位**三层抽象，只实现 DeepSeek 一家，但保留扩展空间。

**每个模块可单独覆盖** `{baseUrl, apiKey, model, thinking, reasoningEffort, userId}`。理由是：多账户轮换（故障隔离）、**计费归因**（哪个模块烧了钱）、不同模块走不同 base_url。

注意：**界面文案不要宣称这能提高缓存命中**——那会变成又一次「界面一个词、行为另一个词」。

## 11. 工程结构

### 11.1 Gradle 层

与 Pulsus 同形，已验证可用：

```
rpg/
  shared/        commonMain 装全部逻辑 + Compose UI
  androidApp/    薄入口
  desktopApp/    薄入口
```

桌面先行，Android 复用同一份 shared。

### 11.2 shared 内的包分区

依赖方向自下而上，`world` 不依赖任何人。

```
llm/        协议层：SseParser、ChatModels、WireMessages、LlmClient…     ← 移植 Pulsus
tools/      工具声明 / 参数校验 / 注册表                                ← 移植 Pulsus
memory/     QueryTerms：中文 bigram 分词 + LIKE 转义                    ← 移植 Pulsus（仅此一文件）
config/     供应商 → 模型 → 档位；每模块可覆盖凭据
world/      世界状态：Actor、物体、时间轴、**地形层、材质表、区划层**     ← 唯一权威
spatial/    空间：体素格、米格换算、空间框（射线 + 凸包）、地形的显示字符
presets/    预设库（非模型驱动，DB 式）
rules/      判定：模型段（解释任意动作 → 提议后果）+ 代码段（校验 + 提交）
render/     观察(X) → 描述；固化、细化叠加、失效
notes/      笔记与摘要：一个表，两个工具
director/   **剧本池、两级导演**、时间轴、突发事件；读窗口与笔记
generate/   生成系统：地形 / 物品 / 角色；chunk 按需生成
control/    控制器：人类 / 剧情 NPC（持久）/ 氛围 NPC（无状态）
session/    回合推进、时间快进、事件结算、存档
ui/         地图（俯视、以玩家为中心、可多选）、两个输入框、观察周围、查看器
```

`world` 不依赖任何人；`rules`/`render`/`notes` 读 `world`；`director` 读窗口与笔记、写时间轴与剧本池；`generate` 读 `presets` 与区划、经提交层写 `world`；`control` 调 `tools` → 经 `rules` 裁定 → 走提交层。

**地形的写入走的是同一条提交层**：地形后果是第八种 `Consequence`（A.15），所以"地形归 `world/`、提交归 `rules/` 的代码段"这条分界不需要为它破例。

## 14. 实测发现（spike 一、二轮）

下面是**量出来的**，不是推测的。跑法见 §13，代码在 `D:\fatfish\Infinitesimal` 的 `shared/src/jvmTest/.../spike/`。

### 14.1 「渲染即固化」成立，延迟约 1 秒，成本可忽略

三轮共 10 次整段渲染：首次 **1354 / 1466 / 1918 ms**，命中固化 **0 ms**（零请求，断言钉住）。平均约 1.1 秒。

单次观察约 **0.0007 元（高峰）**，1000 次约 0.7 元。**成本不是第一性问题，延迟才是**——玩家点一次"查看"要等约 1 秒。

### 14.2 「只增不改」不能靠提示词，必须靠数据模型

第一轮把描述存成一整段文本，细化时把旧描述喂回去并明确要求"只增不改、不得矛盾"，模型照样矛盾：

> 原描述：表面光滑，**几乎不见划痕**
> 细化后：桌面边缘可摸到**几处细微的刻痕**

而且细化后的文本里，原描述的桌腿、气味、尺寸**全部消失**——它不是叠加，是换写了一篇。

第二轮改成**描述按句存储**，唯一写操作是在两句之间插入，同一实验通过：**去掉新插的那一句，剩下的与基线逐字相同**（断言）。

**结论：写操作的限制要落在数据模型上，不能落在提示词上。**

### 14.3 插入一句话：工具可靠，FIM 不稳定

同一个基线、同一个插入点：

| 机制 | 结果 |
|---|---|
| **工具调用** | **2/2 成功**，843 ms。产出「桌面中央留着一圈年深日久的浅色圆痕，是无数酒盏底沿磨出的印记。」位置由模型自选（建议第 1 句后，它选了第 2 句后），句子依然自然 |
| **FIM** | **5 次里只有 2 次可用**。失败方式有三种：假标记 `<cont=12>。`、**空返回**、以及 §14.4 那条 |

FIM 在**极简提示词**下（一句指令 + 描述前缀）3/3 成功；一旦把"物体信息 + 规则清单"叠上去就开始不稳，而且**同一条形状也会时好时坏**（同一个形状，一次成功、一次空返回）。

**所以 FIM 是可选加速，工具是必备能力**——已按此定：接口一个，实现两个，数据模型共用。

**默认值因此是「只有工具路」，FIM 要显式打开**（`DetailInserters.of(config, useFim = false)`）。默认该选稳的那一条——FIM 的失败方式全都是"看起来正常"的那种。它有一样东西工具给不了（`suffix` 是协议级的锚，§14.6），但那是一个值得**主动开启**的收益，不该是一个默认承担的风险。

**第四种失败方式：结构合法但没意义。** 后来一次实测里 FIM 通过了全部守卫，产出是：

> 知道尺寸是2米乘1米乘0.8米。

它是一句话、不超过 120 字、不与已有句子重复——**守卫查的是结构，不是它有没有意义**。而这句话的形状像是在**续写紧挨在补全点前面的那段属性清单**，而不是续写描述。

**这一条没有修。** 它属于一条默认关闭的路径，不值得在它上面继续投。若要重新启用 FIM，第一处该试的是**段落顺序**：把物体信息放到指令之前，让补全点前面紧贴的是描述本身而不是元数据。

### 14.4 一个必须写下来的危险：FIM 会泄漏端点的安全审核标记

把物体信息压成一行的那次，FIM 原样返回了端点的内部审核文本：

```
<ds_safety>[用户未成年]否
[分类]其他
[判定]用户请求为木桌补充细节，内容属于一般家具描写，未涉及政治人物、敏感事件或分裂主张。
[规则]无</ds_safety>Safe
```

**这段东西如果直接落库，就会变成玩家读到的一段世界描述。** 它落在 `finish_reason=stop` 上，看起来完全正常。

两条处置：

1. **任何模型输出在落库前必须过守卫**（非空、长度上限、只含一句、不得与已有句子重复）。上面这段 94 字且含多个句末标点，会被"含 N 个句子"拦下。
2. FIM 这条路**必须带重试与回退**，回退目标是工具路径。

### 14.5 缓存有长度门槛（已定论）

**短请求永远不命中。** 约二十次 54–198 token 的请求里，`prompt_cache_hit_tokens` 恒为 0——包括 system 提示词逐字不变、只隔几秒的连续请求，也包括**完完全全相同的请求隔 6 秒重发**。

先要排除一个陷阱：那个 0 会不会只是我们模型里的默认值？绕开客户端看端点返回的原文：

```json
"usage":{"prompt_tokens":54, "completion_tokens":48, "total_tokens":102,
         "prompt_tokens_details":{"cached_tokens":0},
         "prompt_cache_hit_tokens":0, "prompt_cache_miss_tokens":54}
```

**字段确实返回了，值就是 0。** 不是读数被掩盖。

然后是关键的一步——把**长度**这一个变量单拎出来（2799 token 的静态前缀）：

| | 命中 |
|---|---|
| ① 首发 | 0 / 2799 |
| ② 相同问题 | **2560** / 239 |
| ③ 换个问题 | **2560** / 247 |
| ④ 回到第一问 | **2560** / 239 |

**缓存是正常工作的，只是它有门槛。** 命中数三次恒为 2560，正对应文档第三条落盘时机（"按固定 token 间隔落盘"）——2799 token 刚好只凑得出一个完整单元。而 2560 = 5 × 512 = 20 × 128。

**由此得出设计规则，它比"动静分层是唯一手段"具体得多：**

> **动静分层只在上下文超过一个缓存单元的系统上才有收益。**

- **渲染器**：system（约 130）+ user（约 40）= **170 token，够不着门槛，永远不可能命中**。所以不要为它做任何缓存优化——纯属白做。它的成本本来就低到 0.0007 元一次（§14.1）。
- **NPC / 导演**：上下文必然超过门槛，**会命中**。动静分层在那里才值得下功夫。

**精确间隔未定**（512 还是 128）。但它不影响上面这条规则——无论哪个，渲染器那 170 token 都够不着。

**补充一组数据：导演给了背景之后，能不能把渲染器推过门槛？** 把地点背景（约 150 token）加进渲染器的静态前缀，前缀从 170 涨到 277。同一地点下连续观察四个不同物体：

| | 命中 |
|---|---|
| ① 木桌 | 0 / 277 |
| ② 酒杯 | 0 / 264 |
| ③ 木凳（判决点） | 0 / 263 |
| ④ 油灯 | 0 / 261 |
| ⑤ 另一地点的木桌（背景不同） | 0 / 192 |

**全部为 0。** 而完全相同请求重发时能命中 **128**（占总量的 46%）。对照 §14.5 上面的长前缀实验：2799 token 下**换一个后缀也照样命中 2560**。

于是这条规则可以说得更硬：

> **缓存只在"前缀本身已经很长"的系统上生效，与"有没有共享的前缀段"关系不大。**

渲染器（约 170–280 token）不在其中，**加了导演的背景也不在**。文档描述的"公共前缀检测落盘、第三次命中"这套机制，在 260 这个量级上没有在我们身上发生。

背景介绍的价值因此回到它原本的那一件事：**让描述不脱离世界**。这一条实测是有效的——描述里出现了"陈年酒渍"，插入句里出现了"靠大厅中央立柱横向摆着，一侧对着吧台"，而背景原文并没有提立柱和吧台，那是模型在背景约束下作出的合理推断。

### 14.6 后缀是锚：没有它，模型会编造

FIM 不给 `suffix` 时，模型在酒馆的木桌上摆了一只**苹果手机**，还编了一整套"布局松散且不对称""屏幕朝下""摄像头略突出于桌面"，最后撞上 token 上限。

**没有锚，模型不是"描述得更细"，而是"编造得更远"。** 观察器必须给它边界——而 FIM 的 `suffix` 恰好是**协议级**的锚，比提示词里写"不得编造"硬得多。这是 FIM 唯一无法被工具替代的价值。

同一现象的另一面：FIM **无指令**时会返回空，或只补出"木桌"两个字。所以它必须有指令。

### 14.7 输入成本对比

| 路径 | 输入 token |
|---|---|
| chat（含观察器 system 提示词） | 169–198 |
| FIM（无 system 提示词） | 71–151 |

FIM 省下的主要是那段 system 提示词（约 130 token）。但它一旦需要重试，这点优势就没了。

### 14.8 每个系统一个缓存池（`user_id` 分层）

**决定：每个系统一个 `user_id`，因此一个独立的缓存池。**

端点的 `user_id` 有三项功能（官方《限速与隔离》原文）：**内容安全隔离**、**KVCache 隔离**、**调度隔离**。所以这不是我们发明的分层，是端点已有的那一层。字段平铺在请求体里，约束是 `[a-zA-Z0-9\-_]+`、最长 512、不得含隐私信息。

落地为闭合枚举 `SystemId`（`inf-renderer` / `inf-director` / `inf-npc` / `inf-judge` / `inf-summarizer`），**用枚举而不是裸字符串**：`user_id` 写错一个字母不报错，只静默换一个池——命中率掉下去，没有地方看起来不对。

**代价几乎为零**：缓存按"前缀单元"完整匹配，而各系统的 system 提示词本来就完全不同，它们之间没有任何可共享的前缀，隔离不损失命中。

买到的三样：**隔离**（一个系统不挤掉另一个的缓存）、**归因**（哪个系统的命中率可以分开算）、以及**可诊断**——"命中恒为 0"这类问题，有分层才分得清是"同一池内也不命中"还是"跨池本就不该命中"。§14.5 的定论正是靠这一层做出来的。

### 14.9 一条实现纪律：`thinking` 必须显式关，不能靠默认

写原始 `usage` 探针时忘了带 `thinking` 字段，端点的默认是**开启**——那两次请求各烧了 29 和 48 个 reasoning token，**接近输出的一半**。

推而广之：**所有影响计费或输出的开关都必须显式写进请求体**，不依赖端点默认。这条与"配置里没有默认值、缺字段按名报错"是同一个原则，只是发生在协议层。

### 14.10 「看大一点」的重复采样：预算不该改，框外那句话该改

`ViewBudget` 不封顶，只记数。这条决定的直接后果是「三条街外」那条驳回从 ALIGN 步 997 ms 退到了 EFFECT 步 5270 ms——但那是**一次**读数，不能当结论。`spike/JudgeWidenProbe` 把它变成样本：4 个场景 × 5 轮，每轮开一个全新的世界（判定会改世界，不隔离的话第二轮问的就不是同一件事）。20 次判定，总 113 秒。

| 场景 | 扩过 | 驳回@ALIGN | 驳回@EFFECT | 成立 | 耗时中位/最大 |
|---|---|---|---|---|---|
| 甲 三条街外（目标不存在） | 4/5 | 4 | 1 | 0 | 2183 / 4311 ms |
| 乙 差一格在框外 | 4/5 | 0 | 3 | 2 | 5550 / 16892 ms |
| 丙 手边（对照） | 0/5 | 0 | 0 | 5 | 3393 / 4140 ms |
| 丁 八格开外 | 2/5 | 0 | 4 | 1 | 8288 / 15933 ms |

三件事定下来了。

第一，**ALIGN 步的驳回没有丢**。甲 4/5 仍在 ALIGN 步拦下，中位 2183 ms，只有 1/5 漏到 EFFECT。先前那次 5270 ms 是尾部而不是常态——**预算不动**。

第二，**「不封顶」没有失控**。20 次里最多扩 2 次，累计 12 次；而对照组丙（目标就在手边）0/5 扩过。模型不会没事乱扩。

第三，**真正的缺口是「框外只说一句」**，丁把它暴露了：

- 5 次里没有一次对齐到 `well_cup`。
- 3/5 根本没扩——井在 (20,8)，默认那一片是 x 9..15 / y 0..6，井在框外。
- 其中一次**拿桌上的酒杯顶替**：对齐到 `wine_cup`，落库 2 条后果，世界被改错了。
- 另一次在驳回理由里写「井边光秃秃的，根本没有放着什么杯子」——而 `well_cup` 就在世界里。`farLine`（`spatial/RegionView.kt`）只报最近的那一样：在 `max(|dx|, |dy|)` 度量下井与杯子都是 8 格，`minByOrNull` 取了先出现的「街心的水井」。模型看不见那只杯子，于是把「看不见」说成了「没有」。
- 剩下的 2/5 扩了两次（当时射线长是 3 → 6 → 12，档位已在 §14.11 改掉）才把井带进框，然后按距离驳回——这两次是对的。

所以「一样都不提」和「全给坐标」之外还有第三条路：**框外按方向聚成几行，每行给方向与距离，把那几样的名字列出来，但不给坐标**。名字不是坐标，不会让框白框；可少了名字，模型就会替世界编。

「够得着」至今没有一条线。乙（扫帚在东 4 格）同一输入 2/5 成立、3/5 驳回，本轮最大延迟 16892 ms 也出在这一格。按 A.6 那条分工，这条线不该由代码划——但它现在是每次现算的，稳定性就等于抽样的稳定性。

### 14.11 射线数改成按 k² 长：空间密度守恒

§14.10 的数据里藏着一条没被问出来的毛病：射线**条数固定 18**，长度随扩大增长。于是每一档相邻两条射线摊到的间距是：

| 档 | 射线长 | 射线数 | 相邻间距 |
|---|---|---|---|
| 第一眼 | 3 | 18 | 2.5 格 |
| 扩 1 次 | 6 | 18 | 5.0 格 |
| 扩 2 次 | 12 | 18 | 10.0 格 |
| 扩 3 次 | 24 | 18 | 20.0 格 |

**扩得越远，缝越大**——远的东西反而比近的更容易从缝里漏掉。这与"看大一点"的目的正好相反。

### 改法

方向从**整数向量**换成球面均匀采样，**再把球面切成十个扇区**（`spatial/Direction.kt`）：八个罗盘方向各占方位 45°、仰角 ±45°，上/下两个极冠各占半角 45°。十个扇区的立体角加起来正好是 `4π`（有测试钉住）。每个扇区在第 k 档的条数是 `round(6Ωk²/π)`，这条式子保证每一条射线摊到的球面面积恒定（约 4.71 格²，间距 2.17 格）。**整体抬一档 24 → 92 → 216 条；只抬一个扇区（东南）24 → 30 条。**

扩大一次 = **k 加一**（长 3 → 6 → 9 → 12），不是长度翻倍。长度再翻倍的话 k 得跟着翻，条数就是每扩一次乘四，k=8 时 1530 条。

**取整不会跳格。** `|u| = 1`，每步每个坐标的变化不超过 1，取整后不可能越过一整格——所以不需要体素遍历（DDA），逐格判等就够了。

### 单层的墙只挡得住一半（同一条量过三次，三个数）

附录里记过一条「单摆一件家具挡不住射线，框几乎总是 ±3 的方块」。这一条在三次方向集上量出三个不同的数，**三个都记下来**：

| 方向集 | `maxX` | 单层的墙 |
|---|---|---|
| 整数 18 向（6 轴向 + 12 棱对角） | 15 | 一点没挡住 |
| 全局斐波那契 18 条 | 13 | 完全挡住 |
| 十个扇区 × 各 2 条 | **14** | 挡住一半 |

原因很清楚：EAST 扇区在第 1 档只有 **2 条**射线。第一条正好落在 `(1,0,0)`，撞在墙上；第二条仰角 32.7°，从墙上方飞了过去。要挡住它得有贴着地面走的射线——那是密度问题，不是算法问题。

**跨层的东西（墙、地形）挡得住全部方向**：跨层墙那个探针里 `maxX` 是 13，与方向集无关。

中间那一行（13）是全局斐波那契那一次恰好采到一个 `ux = 0.9352, uz = 0.0556` 的点才有的结果，换成扇区划分之后就不成立了。**一次读数不能当结论**——这条和 §14.10 的教训是同一个。

### 定向扩大：`widen_view(方向)`

`farLine` 早就说过「最近的是「街心的水井」，在**东南** 8 格外」——而模型拿到这句话之后**没有办法响应它**：唯一的表达方式是让四面八方一起变远，烧掉三倍多的射线只为看一个方向。

现在 `widen_view` 多了一个**可选**参数 `direction`（十个词，和 `farLine` 用的是同一张表）。填了只把那个扇区抬一档；不填仍然整体抬一档。认不出来的词按整体扩处理——它"想看得更远"这个愿望是明确的，只有"哪边"没说清楚，为这个退回重说不值得。

`RegionView` 的档位那一行因此会变成「射线长：东南 6、上 6；其余 3」这种形状：**模型得知道自己上一眼往哪边看过了**，否则它会一遍遍要求看同一个方向。

为了让可选参数能表达出来，`JudgeTools.tool()` 加了一个 `optional` 口子——原先它把**所有**属性一股脑塞进 `required`，可选参数根本写不出来。

### 代价

k=1 不再等于老的 18 向（现在是 24 条），所以 §14.10 那次采样（在老算法下做的）只能当历史看。它的结论——ALIGN 步的驳回没丢、"不封顶"没失控——仍然成立，但数字是旧档位的。

单次扩大的跨度小了：原来扩两次到 25×26，现在到 19×20。要够到同样远的地方，现在要多扩一次——**除非它用定向扩大**，那正是这个口子存在的理由。

### 14.12 换档之后重采一遍：方向会填，但「框外只说一句」没修好

换档之后 §14.10 那张表就作废了（射线数从 18 变 24，档位含义也变了）。同一支探针（`spike/JudgeWidenProbe`，补了「填的方向」一列，4 个场景 × 5 轮，每轮开新世界）在新档位下重跑，20 次判定、总 149 秒、单次 806–21475 ms。

| 场景 | 扩过 | 填了方向 | 驳回@ALIGN | 驳回@EFFECT | 成立 | 协议失败 | 中位/最大 |
|---|---|---|---|---|---|---|---|
| 甲 三条街外（目标不存在） | 3/5 | 3/5 | 3 | 1 | 0 | 1 | 4007 / 21475 ms |
| 乙 差一格在框外（扫帚在东 4 格） | 3/5 | 3/5 | 1 | 4 | 0 | 0 | 7553 / 15126 ms |
| 丙 手边（对照） | 0/5 | 0/5 | 0 | 0 | 5 | 0 | 4477 / 5455 ms |
| 丁 八格开外（井边那只杯子） | 2/5 | 2/5 | 2 | 1 | 2 | 0 | 7505 / 21258 ms |

§14.11 结尾那个「没量过」的问题有答案了：**模型会填方向，但不是默认。** 13 次扩大里 8 次填了真方向（东南 3、西北 3、东 2），另外 5 次是整体。它填的都是**自己在某一眼里读到过的那个词**（`wherePhrase` 用的就是这十个词）——两张词表是通的。

第一件，**乙从「2/5 成立」变成「0/5 成立」，而且现在驳回的理由是对的**。有 2 轮模型填了「东」——扫帚正在东边。它读到「在正东 4 格外」，就拿同一个词要求往东看，然后写「扫帚靠在四步开外的墙上，你站在原地伸长了胳膊也够不到它——得先走过去」。这正是定向扩大要买到的东西：**距离信息真的到了模型手里**。

第二件，**甲多了一个新的失败模式：协议失败**。第 3 轮烧了 21475 ms——第二步连试两次都零工具，既没有后果也没有驳回。20 次里 1 次，但它是全部样本里最慢的一次。

第三件，也是**这条要更正的一条**：乙那 2 轮「没有扫帚」的驳回理由，**错不在模型**。`spike/FrameProbe`（离线、不需要密钥）把判定实际拿到的那段文字打了出来：

> 框外还有 2 样东西；最近的是「酒馆大厅」，在西北 3 格外。

**扫帚根本没有出现在提示词里。** `farLine`（`spatial/RegionView.kt`）只报最近的那一样，而最近的那样是**玩家自己所在的酒馆大厅**——它的坐标 (10,0) 落在参差凸包之外（默认框是 x 9..15 / y 0..5，但 y=0 那一行凸包只盖住 x=12 一格），于是这个「房间」被当成了框外 3 格外的一件东西，还排在扫帚（东 4 格）前面。丁那边一模一样：报出来的还是酒馆大厅，**井与粗陶杯一个字都没有**。

所以模型不是把「这一片里没有」读成了「世界里没有」——**它手里真的只有这一片**。两个毛病也因此分开：

- **房间被算成框外的东西。** 玩家 `parent` 链上的东西不可能是身外之物。这是纯缺陷，不涉及取舍。它还有第二重代价：乙 r3/r5 那两轮第一次扩大填的方向是「西北」，顺序上正是在追那句「西北 3 格外的酒馆大厅」——**一行假的目标骗走了一次扩大**。
- **框外只报最近的一样，第二样就永远看不见。** 这一条才是要挑形状的设计决定。

第四件，**丁的顶替没有修掉**。5 轮里 0 次对齐到 `well_cup`；其中 2 轮对齐到手边的 `wine_cup` 并且**落库 2 条后果**——玩家说「把街心那口井边的杯子拿过来」，世界动的是手边那杯麦酒。原因见第三件：`farLine` 报的是酒馆大厅，**井和杯子都没进提示词**，模型看不到那只杯子，只好拿手边的同类顶替。

第五件，**「够得着」仍然每次现算**。乙同一句话 5 轮里 1 次在 ALIGN 步驳回、4 次在 EFFECT 步驳回；丙（手边）稳定 5/5。§14.10 已经说过这条线不该由代码划，但它的稳定性就等于抽样的稳定性。

延迟中位 4.0–7.5 秒、尾部 21.5 秒，比 §14.10 那一次没有改善。**正确性还没钉住，先不动延迟。**

### 14.13 删掉框外那一句之后：丁的顶替没了，总耗时减半

附录 A.12 那条决定（**框外一样都不提**）改完之后，同一支探针再跑一遍，同样 4 个场景 × 5 轮、同样每轮开新世界。两次的对照（「成立」那一列是关键，因为成立就是世界被改）：

| 场景 | 改前 成立 / 中位 | 改后 成立 / 中位 | 改后 驳回@ALIGN / @EFFECT |
|---|---|---|---|
| 甲 三条街外（不存在） | 0 / 4007 ms | 0 / 3170 ms | 3 / 2 |
| 乙 差一格在框外 | 0 / 7553 ms | **1** / 3579 ms | 2 / 2 |
| 丙 手边（对照） | 5 / 4477 ms | 5 / 3683 ms | 0 / 0 |
| 丁 八格开外 | **2** / 7505 ms | **0** / 3250 ms | **5** / 0 |

三件事。

第一，**丁的同类顶替消失了**。改前 5 轮里有 2 轮对齐到手边的 `wine_cup` 并**落库改了世界**；改后 5 轮**全部在对齐步驳回**，理由是对的（「这一片里没有井，井边也没有杯子——你眼前这片只有酒馆大厅里的一张木桌」）。它得先扩一次才知道，而扩一次的代价比改错世界便宜得多。这是「模型看不见框外」从缺点变成优点的那个转折：看不见，就不会拿近的顶替。

第二，**总耗时 149 秒 → 72 秒**，单次尾部 21475 → 12453 ms，四格的中位全降。协议失败 1 次 → 0 次。原因大概是提示词短了，而且模型不再追那行假目标。

第三，**多了一个新的反面案例**：乙第 3 轮**成立**——模型扩了一次、看到扫帚、对齐 `broom`、落库 2 条后果。扫帚在 4 格外，这一轮**该驳回**。这是「够得着」那条线还缺着的直接后果（第五件），不是新毛病。

**还有一条要处理的**：乙 5 轮里有 3 轮**一次都没扩就断言「这附近没有扫帚」**。框外那句删掉之后模型确实无从知道扫帚存在——但它也没有先扩一次去找。丁那边 4/5 会先扩，乙这边只有 2/5。所以「找不到就先扩，扩完还是没有才说没有」这条规则得写进提示词。

**这一条后来没有加**，理由是用户提的那个问题：**为什么会要找框外的物体？** 框的中心本来就是「发起者 + 这次动作指向的东西」——东西在框外，说明玩家没指向它，那就该走 §4.7 的纠正预览让玩家指一下，而不是让模型去猜外面有什么。`widen_view` 的用途因此收窄成一种：**后果把东西送出了框**（被打飞），那时模型扩的是"这次动作需要的那片范围"。

### 14.14 角色卡在「分界」那一格上真的起作用

§3.5 的角色卡接进判定之后，`spike/ReachProbe` 量它到底值不值。做法是**勾选**目标——勾上之后它成为框的中心，一定在框里、一定有坐标，于是这一趟里唯一的变量就是**判定读没读那张「交互范围」卡**。同一句话、同一个世界跑两版：一版带卡，一版把玩家那张卡摘掉、其余一字不动。4 轮 × 3 个场景 × 2 版。

| 场景 | 有卡 成立 | 无卡 成立 |
|---|---|---|
| 甲 够不着（扫帚 4 格外） | 0/4 | 0/4 |
| 乙 够得着（酒杯 1 格） | 4/4 | 4/4 |
| **丙 分界（酒壶 2 格外）** | **0/4** | **2/4** |

三件事。

第一，**两头那两格，卡是多余的**。4 格外与 1 格内都太悬殊，模型光看坐标就判对了，有没有卡一样。所以拿这两格去证明卡有用是证明不了的——这也是一次"读数选错了地方"的教训：**要验一条规则，得先在它该起作用的地方量**。

第二，**分界那一格上卡是决定性的**。酒壶在 2 格外（2 米）：无卡时模型觉得"两步远伸伸手就够"，4 轮里 **2 轮真的让玩家隔空把酒壶拿走、落库 2 条后果**；有卡时 **4/4 驳回**，理由直接引用卡里的词——「指尖离它还有一格」「还差着整整一格有余」「你伸长了胳膊也只够到一臂之遥」。**模型确实在读那张卡**，这一点从它的措辞就能看出来，不必靠结果反推。

第三，有卡那一版在丙上还**更快**：中位 2239–2812 ms，无卡 3648–10030 ms。给了规则，它就不必自己估「两步算不算够得着」。

（`spike/ReachProbe` 保留在手边：以后改「交互范围」的措辞，先在这儿跑一遍。）

### 14.15 整轮验收：预览真的停在改世界之前

`spike/TurnProbeSpike` 压的是界面调的那几条路。它现在多验一件事——**纠正预览停在改世界之前**：

```
▸ ① 看了「你」：4 句，2437 ms，花了 1 次请求
▸ ② 又看了一眼：4 句，0 ms，请求数仍是 1 ← 固化生效
▸ ③a 停在纠正预览上：判定认为作用在 wine_cup——世界还没动
▸ ③b 点了「应用」：第二步跑完，世界动了
▸ ④a 停在预览上、点「改动作」：桌子还在，描述也还在 ← **停下来是免费的**
▸ ④b 这次点了「应用」：oak_table 没了，它的描述也从界面状态里作废了
```

断言钉住的是三件不许含糊的事：预览期间酒杯的高度仍是 80 厘米（在桌面上）、且日志里**没有**「成立」那一行；`dismissPending()` 之后桌子还在、它的描述也没被作废；`applyPendingNow()` 之后桌子变成「劈成两半的木桌」。

整场 8 次模型调用。④b 那一次判定花了 14348 ms（劈桌子用了两次尝试）——延迟仍然是那个没有解决的问题（§14.12 第五件）。

### 14.17 把「东西不在这里」写成驳回条件之后：早驳 19/20，总耗时减半

改动只有一处提示词（`shared/src/commonMain/kotlin/io/github/k1midi0/infinitesimal/judge/Judge.kt` 的 `targetingPrompt`）：把「一个都不报」从「不作用在任何东西上」**收窄**到「确实不指向也不牵涉任何东西」，并明确写出「动作点名了一样东西、而这一片里没有它 → 调 `reject_targets`，**别报空**」。

| 丁 八格开外 | 0/5 | 4 | 1 | 0 | 863 / 4286 ms |

20 次判定、**总耗时 37 秒**、单次 596–5127 ms。与 §14.16 那张表对照：

唯一的漏网是丁的第 2 轮：第一步把「井边那只杯子」对齐成了手边的 `wine_cup`（老毛病「同类顶替」），第二步才驳回。这条路没断，只是从 3/5 掉到 1/5。

探针新增一列「第一步报的」（读 `Judge.alignedTargets`），它顺带回答了另一件事：**20 次里一次「报空」都没有**，`（无）` 一格没出现。查下去发现原因是代码把那句话堵死了：

```kotlin
if (calls.isEmpty()) return TargetAlignment.Malformed(listOf("第一步没有调用任何工具"))
```

`calls` 非空时，每一条要么是 `target`（加一个目标），要么是 `reject_targets`（给一个理由），要么直接 `Malformed`——所以**「一个都不报」在代码里等于「协议内失败」**。模型照着提示词办事（「我环顾四周」），拿到的是 `Malformed` → 重试一次 → `FailedProtocol` → 界面上显示「协议内失败——按设计不给玩家看」。

**提示词允许的那条路，协议里没有出口。** 因此 `Turn.finish()` 里那条「空目标就跳过第二步」的守卫，在当前提示词下是**够不到的代码**——它是对的，但先要有东西能走到它面前。这条要挑形状，记在 §12 第 11 项。

### 14.18 「发起者本人也是对象」：报空这条路被删掉

§14.17 结尾那条「提示词允许报空、协议里没有出口」的矛盾，处理方式是**把提示词那一句删掉**，而不是给协议加出口：**任何动作至少落在发起者身上**——「我理了理衣襟」「我环顾四周」只有它一个人，那就报它自己，照常走完两步。`targetingPrompt` 现在明写「永远不要一个工具都不调」，`alignTargets` 里 `calls.isEmpty() → Malformed` 保留，但重试说明改成可执行的（报发起者，或说明这一片里为什么没有它点的东西）。

`Turn.finish()` 里那条「空目标跳过第二步」的守卫留着：发起者永远是对象之后它**够不到**，但「够不到」和「不可能」是两回事。

探针加了第五个场景「戊 只落在自己身上」（「我低头理了理衣襟。」），5 场景 × 5 轮：

| 场景 | 扩过 | 驳回@ALIGN | 驳回@EFFECT | 成立 | 中位 / 最大 |
|---|---|---|---|---|---|
| 甲 三条街外（不存在） | 0/5 | 4 | 1 | 0 | 1253 / 7669 ms |
| 乙 差一格在框外 | 0/5 | 5 | 0 | 0 | 765 / 1258 ms |
| 丙 手边（对照） | 0/5 | **1** | 0 | **4** | 2702 / 4189 ms |
| 戊 只落在自己身上 | 0/5 | 0 | 0 | **5** | **6669 / 13578 ms** |
| 丁 八格开外 | 2/5 | 5 | 0 | 0 | 1118 / 3558 ms |

25 次判定、总 77 秒、单次 487–13578 ms。

第一条，**规则成立**：戊 5 轮里第一步全部报 `player`（「第一步报的」那一列五次都是 `player`），5/5 成立，每次 1 条后果，没有一次走成「报空 → 协议内失败」。

第二条，两个代价，都还没处理：

- **对照场景出现了一次假驳回。** 丙「我拿起桌上那杯麦酒」在 §14.17 那次是 5/5 成立，这一次 4/5——有一次第一步直接驳回了。n=5 太小，不能就此说是回归；但「把驳回条件放宽」最该防的正是这个方向：驳回是**安全**的失败（玩家改一下勾选就能重来），代价却是把一次本来能成的动作挡掉。
- **「只落在自己身上」的动作慢一倍。** 中位 6669 ms、最慢 13578 ms（全场最慢），而对照丙是 2702 ms。它的请求数是 2–3 次，多出来的那次是重试——这类动作的第二步要硬造一条后果出来（5 轮各造了 1 条）。

### 14.19 规则书真的在裁冲突；`no_change` 是最干净的成果；而 `effort` 那一格这一轮没量出来

规则书模块（§12 第 12 项）、`no_change` 与 `calc` 的联机验收。`spike/RulebookProbe.kt`，四个场景 × 4 轮、每轮开一个新世界，2026-09-24。

跑法：

```
.\gradlew.bat :shared:jvmTest --tests "*RulebookProbe*" --rerun -PinfinitesimalLiveKeyFile="<密钥文件>"
```

换第二步的思考强度加 `-PinfinitesimalEffort=LOW`；不传就用产品默认，表头印的是 `judge.effort`。

#### 五轮采样

同一支探针、同一批场景，只在三个地方变过：

| 跑 | 第二步上限 | `effort` | 坐标进变量表 | 总耗时 | 单次最慢 | 被截断 | 用了 `calc` | 符合预期 |
|---|---|---|---|---|---|---|---|---|
| ① | 2000 | high | 否 | 150 秒 | 22.3 秒 | 没记 | 0/16 | — |
| ② | 8192 | high | 否 | 215 秒 | 75.7 秒 | 0/16 | 4/16 | 12/16 |
| ③ | 8192 | low | 否 | 109 秒 | 35.9 秒 | 0/16 | 1/16 | 13/16 |
| ④ | 8192 | high | **是** | 236 秒 | 81.0 秒 | 1/16 | 4/16 | 12/16 |
| ⑤ | 8192 | low | **是** | 276 秒 | 80.0 秒 | 1/16 | 6/16 | 12/16 |

①那一跑探针还没记 `finish_reason` 与 `reasoning_tokens`，所以那一列的空白是当时看不见，不是没有。

#### 一、规则书进得去，而且**被引用了**

乙（「我伸手去拿靠在墙根的那把扫帚」，扫帚在 (14,3)、玩家在 (12,3)、规则里写着"够得着约一格"）**五轮 20 次判定全部驳回**，理由一律点名了那条规则：

> 扫帚靠在两格开外的墙根上（14,3），你站在（12,3）——按「你」这条（优先级 30）里写的「你伸得着大约一格以内的东西」，你这一伸手够不着。

**连优先级那个数字都被读进去了。** 这不是"提示词里多了几行字"，是模型把条目当依据用了。

甲那一边也有一条硬的：有一轮它驳回了点桌子，理由是

> 油灯的火苗凑到桌面，也点不着这张桌子——它上过一层防火的漆，火燎上去只会留下烟痕。

世界规则（10）说"火会烧起来"，桌子规则（30）说"点不着"，**它采信了数字大的那条，并在理由里点出来了**。

#### 二、`no_change`：五轮 20 次，一次都没走岔

丁（「我低头理了理衣襟」）**20 次全部是「成立·没改变」，恒定 2 次请求**，中位分别是 2165 / 2305 / 2467 / 2704 / 3354 ms。§14.18 那次是 **6669 ms、请求 2–3 次**——多出来的正是"第二步必须硬造一条后果"的那次重试。

它同时把两件事分开了：**「世界没变」与「协议失败」**。加它之前这两种在结果表上都是"第二步一个工具都没调"。

#### 三、`max_tokens` 2000 会让第二步空转——抬到 8192 修掉了它

①那一跑里 **16 次有 4 次第二步一个工具都没调**，每次白烧 20 秒。抬到 8192 之后那 4 次全部消失。

间接证据在②③④⑤报出来的推理 token 尾部上：**7041 / 7382 / 8192** —— 全都远超 2000。凡是模型进入"想很久"那一档，2000 必定截断。这条正好印证 §14.5 记下的那条教训（Pulsus 的输出预留写 8192，与思考档默认 64K 对不上）。

**但 8192 也会撞满**：④⑤ 各出现一次 `finish_reason=length` + `reasoning_tokens=8192` + 单次 80 秒。上限与预算是一件事的两面，这一轮没解决它（§12 第 16 项）。

#### 四、`effort` 这一格**没量出来**——所以默认值保持 `high`

我中途按③那个读数把默认值从 `high` 降成了 `low`，看完④⑤又改回去了。理由是四个读数之间的差别**全在噪声里**：

| | ②（high） | ③（low） | ④（high） | ⑤（low） |
|---|---|---|---|---|
| 总耗时 | 215 秒 | **109 秒** | 236 秒 | **276 秒** |
| 单次最慢 | 75.7 秒 | **35.9 秒** | 81.0 秒 | 80.0 秒 |
| 符合预期 | 12/16 | 13/16 | 12/16 | 12/16 |
| 推理 token 中位（甲/乙/丁） | 950 / 48 / 137 | 969 / 55 / 98 | **1926 / 59 / 112** | **5733 / 22 / 47** |

`low` 有一轮最快、也有一轮最慢；中位推理量忽高忽低。n=4、每轮还开一个新世界，这种方差下**任何"降档更快"的结论都是过度解读**。拿一次读数去改产品默认值，是把噪声当结论（§12 第 17 项）。

#### 五、`calc` 有人用，而且用的正是它该被用的地方

五轮合计 **15 次调用，全部出现在乙**——也就是"要算隔多远"那个场景。式子从 `14 - 12` 一路长到：

```
((broom.x - player.x)^2 + (broom.y - player.y)^2)^0.5
```

由此得出两条改动，两条都是被实测逼出来的：

- **坐标必须进变量表。** ②那一跑模型写的是 `broom.x - player.x`，而当时变量表里只有规则书数值与属性词条 → **那一次白调**（它自己回退、换了个写法找对了答案，但那是运气）。加上 `x`/`y`/`z` 之后，④⑤的式子直接就用上了它们。
- **求值器要认 `^`。** 模型自己发明了幂与开方（`^2`、`^0.5`）；当时只认四则，那几次调用全废。加一个右结合的 `^` 比写一句"禁止平方"便宜得多——**平方与开方本来就是这一层最常用的两种运算。**

同时要如实记一条：**当前世界里没有任何"多个数合起来算"的场景**，所以 `calc` 现在只在算距离。它值不值，要等数值系统（负重、时间、加成）进来才判得出来（§12 第 15 项）。

#### 六、甲丙那组对照**没有原先设想的那么干净**

甲与丙的差别只有规则书那一行，本来想让"桌子有没有被点着"来证明规则在起作用。但甲那一组里模型往往**先因为够不着驳回**（灯在 (12,5)、玩家在 (12,3)，两格），或者只把灯挪开——于是"点不点得着"这条差别被稀释了。丙有一次也判成"符合"（移动了油灯、没动桌子）。

**干净的证据是引用，不是后果**（第一、二节那两条）。这一点值得记住：用"结果差异"当对照时，**先确认那条差异真的被触发过**。

#### 七、`max_tokens` 被拿掉了：不限制思考

第三节把上限从 2000 抬到 8192，修掉了那 4/16 的空转；**但 8192 自己在④⑤里各撞满过一次**（`reasoning_tokens=8192`、单次 80 秒）。用户看完这些读数之后的裁定是：

> 不要限制思考，防止逻辑出错，包括导演系统同理。

所以判定现在**全程不设 `max_tokens`**——发 `null` 就是这一项根本不发，端点用思考档默认的 64K。`reasoning_effort` 也保持 `high` 不降档。三条由此：

- **"上限该设多大"这个问题不再存在。** 它本来就不该是一个需要调的数：那个数字唯一的用处是让模型在想得久的那一次**闭嘴**，而想得久恰恰是它遇到了难的那一次。
- **代价是尾部。** 想得久的那一次会真的想完，单次比 80 秒更长是可能的（本文档里量到过 122 秒）。方向是**用时间换判对**——与 §14.1 那句"成本不是第一性问题，延迟才是"并不冲突：那是说"别为了省钱牺牲体验"，这是说"别为了几秒钟判错"。
- **这条同时是给导演系统定的**：那边将来也不为了快而限制思考预算。

失败时那两个诊断字段（`finish_reason` / `reasoning_tokens`）留着。它们的价值不是调参，是**分清"它没话说"与"被谁打断了"**——这一轮就是靠它们才把 2000 那个上限认出来的。

### 14.20 形状接进几何：射线从此看"占哪几格"，而 §14 那条读数没被推翻——它有了原因

在形状表（A.13）之上接的那一步：射线与 `covers` 从"看这样东西坐标上那一个米格"改成"看它**占**哪几个米格"（`spatial/Cells.kt` 的 `occupiedCells`）。有形状时是形状里每个格换算过去；**没有形状时仍然占它自己那一格**——`shape == null` 的意思是"还没建模"，不是"没有体积"，少了这条兜底，所有还没建模的东西会一起从框里消失。

开局那个世界补上了手写形状（`world/Shapes.kt` 提供盒子、桌子、壳子三个骨架）。端到端读数（`spike/RegionProbe`，离线、确定性）：

| | 格子数 | 参考点（打空） | 被射线打中的 |
|---|---|---|---|
| ⑤ 目标在 (40,30) 米 · 接形状前 | 250 | 48（47） | **1 样**：oak_table |
| ⑤ 目标在 (40,30) 米 · 接形状后 | 250 | 48（**45**） | **2 样**：oak_table、oil_lamp |

框的范围一格没变，**被打中的多了**——那张 200 厘米长的桌子现在压在 (12,4,0) 与 **(13,4,0)** 两个米格上，第二格是新的。

**而 §14 里那条「单层家具挡不住射线」没有被推翻，它现在有原因了。** 这张桌子 80 厘米高，**不满一米**，所以它在米格上只占 z=0 那一层；斜着往上走的射线从 z=1 穿过去，那是对的——桌子就那么高。要让斜射线被挡住，得有个**跨到第二米层**的东西（墙、地形），这一点 §14.11 早就量到过。

一句话：**形状改变的是"一样东西占多大"，不是"一米格有多粗"。** 后者是附录 A.12 定的，没动。

### 14.21 建模：网格语言它学会了；而一次建模 2–72 秒

四句要求跑一遍（`spike/ShapeModelerProbe`，2026-09-24，`deepseek-flash`，思考 high；`docs/design.md` 这一节写的是**改提示词之前**那一批）：

| 要求 | 结果 | 格数 | 请求 | 用时 |
|---|---|---|---|---|
| 橡木方桌 120×120×80，桌面厚 5 厘米 | ✓ | 816 | 3 | 19.3 s |
| 深色木酒杯，口径 8 厘米、高 10 厘米 | **画成了实心块** | 8 | 2 | **100.2 s** |
| 被劈开的方桌的一半，断面粗糙 | ✓ | 260（含 3 个质点格） | 4 | 54.9 s |
| 蓝莓，直径 1 厘米 | ✓ | 1 个质点格 | 2 | 2.2 s |

#### 一、网格学得比预期好

方桌那张图**逐格对得上**：四条腿各 2×2 格、从 z=0 到 z=70，桌面正好一层 24×24（`z=75`），——"桌面厚五厘米"被照做了，没有一个多余层。合计 816 = 4×4×15 + 576。

**稀疏也是真的**：包围盒 24×24×16 = 9216 格，实际占 816（**8.9%**）。A.9 那句"体素是稀疏的，几千个物体也只有几 MB"在这一张图上成立了。

蓝莓那一格同样对：直径一厘米画不出来，它交了一个质点格。A.13 那条"比 5 厘米更小的用质点"第一次被真的走通。

#### 二、劈开那一张是它自己找到的表达方式

断面靠**网格边缘的一格参差**画出来（同样是那一片，有的行 10 个 `#`、有的 11 个），木刺用**质点**（`1`、`2`）。这两样提示词都没教——它自己找到了"粗糙"在这个媒介里怎么画。值得留着：以后要表达磨损、碎裂、毛边，这是一条现成的路。

#### 三、当时以为"空心的东西没学会"——**后来被推翻了，见第九节**

酒杯那句要求说得够清楚（口径、高度都给了），它交了一个 3×3×2 的**实心块**。当时的判断是"提示词没教它挖空"，于是补了两条：**里面是空的东西要挖空**、**壁厚至少一格**。

**这个判断是错的。** 用户 2026-09-24 指出：**形状是它的碰撞体积**。一个口径 8 厘米的杯子，里面那点空腔在 5 厘米的精度下根本表达不出来（壁厚会不到一格），**2×2 的实心柱体就是正确的**。那两条提示词是把外观混进了几何，已删除；实测见第九节。

#### 四、缓存按预期命中

四个来回里，**第二次起** `prompt_cache_hit_tokens` 分别是 11520 / 13696 / 1152，未命中都是 170–260。system（整段网格语法 + 工具 schema，约 **1150 token**）确实是每次都逐字相同的那一段——A.14 那次"独占一个 `user_id`"因此有了凭据。

#### 五、用时是这一轮最难看的一栏

2.2 秒到 **100 秒**，而它整个跑在判定的关键路径上（判定调 `model_shape` 时是同步等的）。杯子那 100 秒只有 **2 个来回**——也就是一个来回烧掉了一分半。这与判定那边是同一种尾延迟（§14.17 量过：中位秒级、尾部二十秒级），而建模**没有 `reject` 那样的早退出口**：它必须把图交出来，交不出来只能说"画不出来"。

要治它，可用的手段与判定那边是同一套（都是一次模型调用）。现在**先记着**：正确性那一半还刚起步，而 100 秒只出现了一次。

#### 六、顺带确认：一层一个来回不是瓶颈

方桌 16 层只用了 **3 个请求**——模型会**在一个来回里一次交好几层**（端点的并行工具调用）。所以 A.14 定的 `MAX_ROUNDS = 40` 不是瓶颈，它只是在兜底"模型一次只交一层"那种最坏情况。

#### 七、那一版"挖空"提示词下的读数（**结论已被推翻，数字留着**）

### 14.22 延迟就是思维链：一次调用 ≈ 半秒 + 输出 token ÷ 200

**为什么必须拆开量。** 在 §14.17 手里关于延迟只有一个数："这一轮一共几秒"（中位 3–7 秒、尾部 21 秒）。那是个总数，它把三种病因混成一样——**排队与预填充**、**模型在想**、**重试**。三种病三种治法，而总数回答不了任何该动手的问题。

**第一版拆法是错的。** `judge/TimingLog.kt` 记在 `Judge.call()` 里，每一次模型调用恰好一条。第一版把它拆成「等」（发请求 → 第一个事件）与「生成」。26 次调用加起来**「生成」只有 88 毫秒**——也就是整条回复是**攒到最后一次吐出来**的。流式确实开着（`llm/LlmClient.kt` 的 `streamChat` 用 `preparePost(...).execute()` 再 `bodyAsChannel()` 逐块读，是服务端这么发的），所以那个二分法量的是一个假的分界：所谓「等 8.3 秒」里同时装着排队、预填充和整条思维链。

**加进 token 才拆开。** 用量本来就在响应里（`Usage.completionTokensDetails.reasoningTokens`），把它一起记进账本之后，答案没有任何含糊。3 场景 × 4 轮 = 12 次判定、26 次调用（`spike/TimingProbe`）：

| 调用 | 共 | 输出 token | 思维链 | 实测吞吐 |
|---|---|---|---|---|
| 甲 第一步 `target` | 985 ms | 36 | 0 | 36.5 token/s |
| 甲 第二步 `no_change` | 1185 ms | 145 | 73 | 122.3 |
| 乙 第二步 `move+set_attribute` | 8297 ms | 1734 | 1584 | 208.9 |
| 乙 第二步 `calc` | 12520 ms | 2575 | 2513 | 205.6 |
| 丙 第二步 `calc` → 第二来回 `reject` | **22073 ms** | **4371** | **4309** | 198.0 |

**一、整条曲线是一个固定开销加一个线性项。** 每一条都落在

    墙钟 ≈ 0.4–0.7 秒  +  输出 token（含思维链）÷ 200

上。思维链与正文**同等计价**——吞吐一样，都是 174–218 token/s。第一步那几条吞吐看着低（36.5）只是因为它们输出太少、固定开销占了大头。

**二、排队不是瓶颈，预填充也不是。** 入 1741 token 的调用与入 7332 token 的调用，每 token 的吞吐一样。输入端 67427 token 里 61056 命中缓存（**90%**），本来就已经很便宜。

**三、第一步不慢，第二步占 87%。** 第一步 11195 ms / 13 次 ≈ 860 ms，思维链**恒为 0**（`ThinkingMode.Never`），每次输出约 100 token。第二步 76865 ms。

**四、真正花钱的是第二步"想多久"，而它想多久完全不受控。** 同一件事（乙，拿起桌上的酒杯）四轮的思维链是 1263 / 1584 / 2346 / 2513 token，**两倍方差**。最贵的一次是丙第 1 轮：第二步为一个距离论证烧掉 **4309 个思维 token（22 秒）然后驳回**。

**五、`calc` 是思维链放大器。** 两次超过 12 秒的调用都调了它（2513 / 4309），而且都出现在"证明够不着"这件事上。

**六、驳回早一步就便宜一个量级。** 丙第 4 轮第一步直接 `reject_targets` → 第二步 0 ms，全轮 **1577 ms**；而第 1/2/3 轮第一步都报了 `target`、把驳回推到第二步 → 3121 / 5117 / **23805** ms。**§14.17 量到的"驳回@ALIGN 19/20"没有保持住**，这一轮是 1/4。n=4 太小不足以下结论，但它与"永远不要一个工具都不调"那一段改写的时间点吻合，值得单独量。

**代价与待定。** 用户定的是**不限制思考**（"防止逻辑出错，包括导演系统同理"）。所以这里不能靠关掉第二步的思考来治，只能靠**让它少想一点**——而"哪一类动作不值得想这么久"是个内容问题，不是参数问题。已记入 §12。

**记账的规矩。** 每个读数都来自 `Judge.timing`，而 `timing.record` 唯一的位置就是 `Judge.call()` 里发请求的那一行。**"这一轮发了几次请求"与"这一轮记了几条"因此永远是同一个数**，两边不会各说各话。

### 14.23 把驳回放回第一步：一处互相打架的提示词

**症状。** §14.22 量到「丙 三条街外那家店里的杯子」在第一步就地驳回只有 1/4；另三轮都报了个目标交差，把驳回推给第二步——第二步手里有 `calc`，会认真地算一遍距离（一次烧 **4309 个思维 token、22 秒**）才驳回。同一次动作，第一步驳掉是 **1577 ms**。

**病根是一处打架，不是模型不听话。** `sharedPrefix` 里那句"这一片里没有的东西，不等于世上没有"（为"驳回理由不撒谎"加的，§14.12）与 `targetingPrompt` 里"动作点名了一样东西而这一片里没有它 → `reject_targets`"**互相抵消**。前一句在两步都出现、写得斩钉截铁，模型于是不敢驳回；而"任何动作至少落在发起者身上"正好给了它一个体面的出口——报发起者，交差。

**改了两处。**

1. 那句话绑到**措辞**上，而不是绑到"敢不敢驳"上：理由里只能说「这一片里没有」，不能说「世上没有」；**但动作点的东西不在这片里，就该在这一步驳回，不要把它推给下一步**。
2. `targetingPrompt` 里把**优先级写出来**，不靠两句话的先后：先看动作的名字有没有点到某样东西——点了而这片里没有它 → `reject_targets`，**这一条优先于"至少落在发起者身上"**，不要用报发起者来代替它。

**读数**（同 3 场景 × 4 轮）：

| | 改之前 | 改之后 |
|---|---|---|
| 丙 就地驳回 | 1/4 | **4/4** |
| 丙 最慢 | 23805 ms | **1308 ms** |
| 12 次判定墙钟 | 88236 ms | **19982 ms** |
| 调用次数 | 26 | 17 |

驳回理由现在都诚实、且限定在这一片里：「这一片里没有三条街外那家店，也没有那家店里的杯子——最近的杯子是桌上这只 wine_cup，不过一格远。」

**改完之后才看得见的两件事**——之前被"报个什么交差"盖住了：

1. **同义说法会被驳掉。**「我把桌上那杯**麦酒**端起来」——实体的 label 是 `酒杯`，而开局世界里东西**故意不带描述**（逼玩家点了才渲染），判定手里只有 label。四轮里两轮驳在名字上，理由原话是「桌上只有一只酒杯（wine_cup），那是酒杯，不是麦酒」。**玩家最自然的说法被驳掉了。**
2. **开局的距离正好卡在边界上。** 酒杯在 (1200, 400, 80)、玩家在 (1200, 300, 0)：三维欧氏 **128 厘米**，而交互范围卡说"一格以内"。判定按三维算就够不着、按格算就是一格。同一次"端起桌上的酒杯"，两轮走"成立"、两轮走"够不着"，其中一轮为它烧了 **24.9 秒**。**用户已经定过：够得着由代码换算好、提示词里直接给「够得着 N 格」——那一步还没做**（§12）。

### 14.24 判定看不见内容：属性没送到，和那只算距离的手

用户对上面那两件事的裁定是三条，都不是提示词层面的。

**一、同义说法不打补丁——是内容没送到。** 用户的判据很干脆：**描述里写着"装着麦酒的酒杯"就不会出错；如果它只是个空杯子，本就该驳回，玩家在喝不存在的麦酒。** 于是不去做别名匹配，去查内容为什么没到。

一查就清楚了：`session/StartingWorld.kt:73` 里酒杯的属性写得明明白白——

    attributes = mapOf("材质" to "深色木制", "内容物" to "半杯麦酒")

而 `spatial/RegionView.kt` 的 `describe` 只印 **label + id + 坐标**，**属性一个字都不印**。判定手里就只有一个叫"酒杯"的东西，它（正确地，因为它只知道名字）驳回了「这一片里没有麦酒」。**根不在对齐，在世界真相没有送到判定的手里。**

改法是在 `describe` 末尾印上属性，**只印属性不印 `sentences`**：那些是按句存的散文描述，是判定的**产物**不是它的输入（渲染在读它、判定在写它），而且长得多——一个桶的描述几百字，列十几样东西就装不下。

**二、距离不该由模型算，给一只手。** 用户要的是"一个计算物体与物体之间距离的工具"。实现在 `spatial/Distance.kt`（纯函数、离线可测）与 `JudgeTools.DISTANCE` 上，回给模型的是**三个数不是一个标量**：

- **格距**——地图格子上的切比雪夫距离（"一格以内""隔着三条街"说的都是它）
- **高度差**——东西在桌上、另一样在手里时格距可能是 0，而你仍然够不着
- **直线距离**——几何上的那一条

分成三个数是**不替规矩做决定**：合成一个标量就等于替它选了"一格以内"按哪种算法，而规矩是内容、会改。

**三、思考模式本来就支持工具调用。** 用户点的那份文档（`api-docs.deepseek.com/zh-cn/guides/thinking_mode#tool-calls`）描述的正是这套代码已经在跑的模式——想 → 调工具 → 再想 → 再调工具，每个子请求都带上该轮产生的 `reasoning_content`。`Judge.call()` 的查询手回路（`widen_view` / `calc` / `model_shape` / `distance`）就是按它写的，探针里那些查询轮全部成功。**没有需要打开的开关。**

### 14.27 导演的第一刀不是提示词，是钟和时间轴

2026-09-25。用户选了导演系统（§8）作为下一个切片。

第一刀没有落在提示词上，落在**确定性的那一半**：世界时钟、时间轴、快进。理由是 §8.2 把两个触发器分得很干净——**时间轴到期由代码检测，确定性、可复现**；只有剧情跑偏才要快速模型。而"跑偏"这件事在时间轴存在之前无从谈起：**没有"本来该发生什么"这个参照，偏没偏根本不是一个有答案的问题。**

于是这一轮一次模型调用都没有，全部离线可测。

#### 时间是一个整数

`WorldTime` 是**从第 1 天 00:00 起的分钟数**（`world/Clock.kt`），不是日期时间。

时间轴要能算"最早到期的时刻"（§8.1），而那种计算只用到比较与加减。日期时间那一套——时区、夏令时、闰年、月长不等——在这里一点用都没有，却会带来一整类只在边界上发作的错。开局那个世界的寿命是一个故事的长度，不是几十年。

显示与换算（第几天、什么时辰）放在同一个类里，因为它们纯粹是**同一个数的两种写法**。把"第 3 天夜里"存下来再解析回去，等于把一处换算变成两处——而"第 3 天夜里"写错一天，时间轴上的事就会在错的那天发生，那种错没有任何东西会报。

七个时辰的边界逐个钉在测试里，理由同上：一次判断错一格，日志里就会写"深夜"而实际是"早上"，而写日志这件事没有第二个人校对。

#### 时间轴是计划，不是记录

到期的事由 `Timeline.takeDueBy` **取走**，离开时间轴。

这一条不显然，但不这样就会出现一种读不出来的状态。§1.5 说**记录永不改写**；§8.2 说时间轴**可以被思考档改写**（"原来打算第三天夜里放火，现在改成第四天早上"是同一件事被重新安排）。把"改了"和"发生过"混在一张表里，`fired` 这个字段就得同时回答两个问题，而它只能回答一个。

代价是有的：**记录层还不存在**（§12 第 20 项）。到期的那些被取走之后无处可去，现在只落在会话日志里——"刚才那段时间里发生过什么"因此只活在这一局的内存里。

#### 快进只停一次

`FastForward.run(world, target)` 走到**最早到期的那一刻**就返回，哪怕目标还在很后面。

停下来意味着"该有人看一眼了"，而看过之后时间不会自己继续走。一次调用里连停两次，等于替调用方决定"没人看也接着走"——那正好是 §8.1 要防的那类漏事：玩家睡了一觉，世界里该发生的事发生了，但没有任何人被告知。

两处边界也是照着这条定的：

- **`nextDueFrom` 含"此刻"。** 导演刚放进来一件"立刻就发生"的事时，快进到任何时刻都该先在这一刻停一下；而这一刻**时钟不往前**——该动的是别的东西，不是钟。
- **没有可等的事时，一点时间都不推进。** 凭空往前推一小时会静默地制造出一段谁都没看见的时间，而那种空白在日志里和"真的无事发生"长得一模一样。界面上对应的做法是**按钮直接禁掉**，不是按下去什么也不做。

#### 钟放在 world 层

`World` 现在有三种东西：实体、`clock`、`timeline`。

时钟进 world 而不是 session，是因为**时间是世界的事实**——"现在是第几天傍晚"与"桌上有一把斧子"是同一类东西：必须存下来，而且只有一个答案。`session/` 做的是**推进**它（§11.2），不是拥有它。放在 session 层，`world/` 就会开始有"接下来做什么"，而它现在只回答"现在是什么"。

开局那一刻定在**第 1 天 18:00**。它是**内容不是配置**：开局那张酒馆写的是"深秋傍晚、屋里点着四盏油灯"，时间就得是傍晚。两处对不上，模型第一句话就会露馅。有测试钉住这一条。

#### 界面

顶栏多了一行世界时间，和一个「等到下一件事」按钮。**按钮上写的就是下一个会停的时刻**（"等到 2 天 深夜"）——玩家按下去之前就知道要等到哪儿，不必按了才知道。时间轴上没有将来时，按钮写「没有可等的」并禁用。

#### 读数

**244 测试 0 失败**，新增 26 个：`ClockTest` 6（第几天与时辰的边界）、`TimelineTest` 7（排序、同 id 覆盖、取走不重复、快照带得走）、`FastForwardTest` 9（只停一次、无事走到目标、正好落在到期时刻不算打断、不倒退、此刻到期不推钟、同刻多件一起出）、`GameSessionWaitTest` 4（开局时辰、没可等的就不推、等到第一件并说出发生了什么、再等一次轮到第二件）。

#### 还没做

- **开局时间轴是空的**（§12 第 19 项）——里面该放什么是内容，不该由代码编一个占位的事。
- **记录层**（§12 第 20 项）。
- **导演的模型段**：偏离检测（快速档，只能发现不能改）与改时间轴（思考档）。
- **导演任务队列**（§8.3.2：全局一个、串行、界面要显示"世界中…"）。

### 14.28 导演的模型段：八条规矩排出一条因果链

2026-09-25，紧接 §14.27。第二刀是**排时间轴**（思考档）。快速档的偏离检测没做——它要判断"剧情偏没偏"，而偏的参照物是时间轴里本来该有的事；时间轴不存在的时候，这个问题没有答案。

#### 只给一只手：`schedule`

`director/DirectorTools.kt` 里只有一只工具：`schedule(id, day, hour, minute, what)`，而且是**多调用**——同一轮里要排几件就调几次。

不做"一次提交整个时间轴"的理由与判定那边的一样（§4.2）：**批量对象没有逐件校验的落点**。一件 id 写重了、一件时刻排在昨天，其余几件是对的——只报"整批失败"等于让模型把已经排对的部分再排一遍。

**没有 `actors` 参数。** 结构里留了位置（`TimelineEntry.actors`），但没有任何代码读它、也没有任何提示词提到它，所以不放出去——放出去就是让人以为它能用。

#### 一件都没排 = 重试，不是成功

循环规则与判定**不一样**，这一点是刻意的。

判定那边是"这一轮没有查询手就收工"（§4.3）：它只需要一个答案，答案到手就停。导演这边是"**这一轮没有手就收工**"——它做的事是**一件一件排下去**，所以只要还在调 `schedule`，就说明还有要排的；一次模型调用排完了八件，那也是八次工具调用。

反过来，**一轮下来一只工具都没调**（模型只写了一段话说"我排好了"）不能当成功——那等于什么都没安排。重试提示写的就是这句：「一件都没排。至少排一件——一件都没排等于什么都没安排。」

#### 时间轴是假的，提交层是真的

`director/TimelinePlanner.kt` 是**与 `judge/Committer` 并列的第二个提交层**：模型写出来的东西先进 `Planned`，`problems(entries, now)` 把一批里所有毛病**一次报全**（同一批里 id 重复、空 id、空 `what`、`dueAt` 早于此刻），一条都不犯才 `apply` 进世界。

沿用判定的两条纪律（§4.6、附录 A.5）：

- **整批校验、整批提交**——模型交的这一批要么全进世界，要么一件都不进，不会留下"排了一半"的时间轴。
- **`now` 从 world 里读，不让模型填**——模型对"现在几点"没有参照系（附录 A.4）。它只能填 `day` / `hour` / `minute`，`dueAt` 由代码算。

#### 读数

**5 次排列、5 次成立，全部一次尝试成功。** 请求数 2 / 5 / 2 / 2 / 2，耗时 10964–20177 ms，每次排上 8–11 件，跨度 11–17 小时。请求数 2 就是下限（一轮排完 + 一轮收尾），甲2 的 5 次是它分了几个来回排。

排出来的东西**是一条因果链，不是一串事件**。最好的一次（甲2，开局空轴）：

> 野猫从地窖门缝钻进来 → 跳上橡木桌把头探进酒杯、把半杯麦酒舔干净 → 从桌上蹿下去时撞翻油灯，灯油泼在桌面上顺桌沿淌 → 淌开的灯油碰到还没灭的火苗，桌面先冒烟 → 烟变成火，火舌顺着四条桌腿往下舔，烟从地窖门缝往外钻 → 第二天早上货郎闻到焦味、拽开地窖门 → 把烧剩半截的桌子拖到门外、捧几把土压灭余火 → 第二天中午野猫又回到门口对着焦味嗅

八件里**每一件都是上一件的后果**。另几次是别的链子：抹布搭上油灯 → 布角冒烟 → 烧着 → 被地窖门缝灌进来的风吹旺 → 顺着桌角爬进桌面。**同一个开场世界，五次排出五条不同但都自洽的路**——油灯可以是"油尽自灭"，也可以是"被猫撞翻点着了桌子"。

`id` 的形态不统一（甲用中文「续酒」「提灯下窖」，乙用 `rag_slips_onto_lamp`），因为它只在一局之内要求唯一、要求能被 `put` 覆盖，不给人看。

#### 两件没做

- **快速档的偏离检测**（§8.2）：现在时间轴能排了，它才第一次有东西可比。
- **导演任务队列**（§8.3.2：全局一个、串行、界面显示"世界中…"）：现在导演是在界面按钮那一次 `run` 里同步跑的，那 11–20 秒界面是 busy 的（§12 第 21 项）。

### 14.29 地形接线：三种静默失败，与一条差点让框塌掉的判据

A.15 把地形定下来的时候留了两处「未接线」：地形后果没进提交层，地形也没进空间框。这一轮把两处都接上了。

#### 先修了一个更大的错：整个开局内容沉在地下一百二十八米

地面在 12800 厘米（第 256 个地形格），而 `StartingWorld` 里那张酒馆写的是 `z = 0`。**没有东西会报这个错**——厘米坐标看起来都是对的，俯视图照画，判定照跑。它只是在"地形接进来"的那一刻才会发作：所有东西都在地底。

处置：`WorldDepth` 多一个 `surfaceCm`（厘米坐标与地形格之间**唯一**的接口），开局内容与六支探针的夹具一律写成 `GROUND` 加偏移。俯视图那一层也从写死的 `0` 改成 `World.groundMetreCell()`。

探针夹具这一半比生产代码那一半重要：`RegionProbe`、`ReachProbe`、`FrameProbe` 把 `StartingWorld` 与自己抄的酒馆**混着用**，两边基准一旦不同，探针会给出一个错的框，而结果是"看起来跑通了"。

#### 第八类后果：地形进提交层

`Consequence` 在接口上分了一次叉：`EntityConsequence`（有 `targetId` 与变化等级）与 `TerrainConsequence`（有 `box`）。那两个字段不是"地形这里没填"，是**它们在这一族上不成立**：`targetId` 回答"哪一样东西的描述作废了"，而地形的改动不动任何东西自己的描述（§7.6）；变化等级是渲染决策的输入，地形不进那张表。强塞一个假 id 会让 `GameSession` 那边多一条永远匹配不上的作废项——少作废一样东西的症状是"描述偶尔过时"，不是一个报错。

提交层的校验这一轮真正的产出，是把**三种静默失败**变成了说得出口的话。三种都是"代码没报错、世界没变"，而模型下一轮只会原样再提一次：

| 写错的地方 | 不拦会怎样 | 现在会说 |
|---|---|---|
| 框整个落在世界之外 | 一格不动（`Terrain` 只动 `WorldDepth` 里的格） | 世界是 z 0..1024，这个框是 z -900..-800 |
| 框碰到世界底那层岩层 | 被静默跳过（那是"挖不穿"的实现） | 碰到了挖不动的「岩层」（bedrock），把框抬上来 |
| 材质名拼错 | 什么都不发生 | 材质表里没有「lava」。表里现在是：soil、stone… |

第三条把**整张材质表**写进理由里，是有意的：模型猜不出一个闭合词表里有哪些名字，报"没有 lava"它就只会再猜一个。

驳回理由里材质写成 **`「岩层」（bedrock）`**——id 与名字都给。id 是它必须用来填参数的那个词，名字是它在网格里看到的那个字符旁边的字；只给一个，这条消息就没法让它改得动那个框。

#### 地形进空间框

射线那一边：地形格与东西**同级**成为阻挡面，但**分开记**（`RayPoint.blockerId` / `blockerMaterial`）。地形**不进** `hitIds`，因此不进清单——它在网格里已经画过一次，再列一遍就是两份可以不一致的数据。

网格那一边：材质画在格子里、东西叠在上面，后面跟一份**按材质去重**的图例（一片 16×16 的草地是一行，不是二百五十六行）。属性与规则书在图例里，整张材质表不抄——它已经在前缀里了（`judge/MaterialView.kt`），而这份输出每一步都要重付。

#### 那条差点让框塌掉的判据

**一格米格要被地形填满才算实心**，不是"有任何一个子格"。

世界的地面铺到地形第 256 格，一个米格覆盖 2×2×2 个地形格，所以米格 128 覆盖地形 256..257——**下半格是土、上半格是空气**。按"有就算"的话，发起者自己站的那一格就是实心的，于是每一条水平射线在 t=1 就撞上地面，框塌成 3×3。

症状是"这片世界很挤"，不像一个 bug。实测：同一份夹具、同一个发起者，铺地面之前 `maxX = 15`，按错误判据铺完之后 `maxX = 11`，按正确判据铺完还是 `15`。`TerrainFrameTest.standingOnTheGroundDoesNotCollapseTheFrame` 钉住的就是它——它断言的是"铺地面**前后**一样"，而不是某个具体数字。

顺带一条同类：网格**不能**用同一条判据去问该画什么。发起者站的那一格是半格土，按实心判据它什么都不画——于是整张地面图一个字都没有。所以是两个函数：`solidTerrainAt`（整格实心吗，挡不挡射线）与 `groundMaterialAt`（脚下踩的是什么，画什么字）。两个问题长得几乎一样，答案差一整格。

#### 实测：模型读到的那个框

`FrameProbe`（离线，不需要密钥）现在带上地形了。开局酒馆、玩家什么也没勾：

```
范围 x 9..15（7 格），y 0..5（6 格）；层 127..131；射线长 3（未扩大）

      x= 9  10 11 12 13 14 15
  y=0             ,
  y=1       ,  ,  ,  ,  ,
  y=2       ,  ,  ,  ,  ,
  y=3    ,  ,  ,  @  ,  ,  ,
  y=4       ,  ,  c  ,  ,
  y=5       ,  ,  e  ,  ,
```

**框没有变小**（7 格，与铺地形之前逐格相同），层范围 127..131 是因为往下第一格就是土、往上第三格才到顶。图例一行「`  , 土`」。

#### 开局那块地

归 `StartingWorld.ground`：以玩家为心、半径 [HARD_RADIUS_CELLS]（64 格 = 32 米，A.16 那个硬性圈）、**画成圆**，圈里每一列从第 0 格铺到地面。三层剖面：一格岩层、石到七成深、上面是土。

它是**内容不是配置**——A.16 那条"没有代码默认剖面"说的是生成，而开局这一圈还没有生成器可调。生成器接上之后它该被换掉。

`generated` 还没标：那是"探索过 = 既定事实"的落点，要等生成器才有东西读它。

#### 没做的

- **生成器**（A.16：按 chunk、读区划、一次调用产出地形与物体、四只手）。这是这一层剩下的那一块，也是唯一能让"挖"以外的地形改动有意义的那个东西。
- **俯视图不画地形**（§12 第 32 项）。材质的 `color` 已经在表里，`MapPane` 还只画点和网格。
- **地点的范围**（A.13）：`tavern_hall` 没有形状，于是它自己那一格在框外——每一条读数的尾巴上都能看到"酒馆大厅 3 格"。

### 14.30 生成器定形：它不再自己找缺口，而是听导演的话

（2026-09-26 定，**本轮开工**）

生成器这一刀开工前把前沿问了一遍，六轮下来它换了个形状。下面每一条都是问答里定下来的，并附上被它推翻的那一版。

**两条是本轮按推荐默认走的**（面板在那一轮被打断，没有落库）：范围参数的两种口径，与「判定不能触发生成」。它们可以随时推翻。

#### 硬性圈不再承诺「每格都有材质」

A.16 原文的判据是「从第 0 格铺到地面（默认第 256 格）每一格都有材质」。字面照做的话，**任何低于第 256 格的地面都违规**——悬崖下面那一片、沟壑、洞穴全在违规之列。而用户的裁定是：

> 不能用代码审查，可能导演需要前面是悬崖

所以定下来的是：**硬性圈只承诺「这些 chunk 生成过」**，长什么样不管。「脚下别踩空」写进提示词当规矩，代码不查。文档里「完整」这个词换掉。

#### 地形以 chunk 为最小生成单位，缺口永远是整块

> 地形以 chunk 为最小生成单位，不会有厘米级的地形缺口

所以「哪儿还没有地形」这件事**没有中间状态**：一块 chunk 要么有、要么没有。缺口清单是 chunk 列表，不是月牙。

这也把「模型一次想生成多大就生成多大」那句限定住了：它决定的是**一次铺多大**，不是**哪儿算缺**。

#### 处理哪些地块由导演给，而导演与判定可以改任何地块

> 地形处理哪些地块是导演/判断给的，导演和判断可以修改任何地块

这条推翻了「生成器自己看缺口、自己决定范围」那一版。连带两条：

- **不设来源字段。** 问来源那次用户答的是「不需要区分，就是预先准备好的地块，和生成出来的等价」。所以 `Terrain.generatedChunks` 的语义从「生成器长的」变成「**这块地已经有地形了**」——开局那片地也要标上。
- **判定能改地形，但不能触发生成。** 它已经有三只框选手，改已有地形够用；要往荒野里长出新东西（烧过的林子长回来），它报给导演。理由：生成是几十秒的调用，而判定那一步已经在 3 秒量级。

#### 一次调用的形态

| 东西 | 定下来的 |
|---|---|
| 上游 | **先叫醒导演**，导演决定生成要求，再调地形系统。§8.5 思考档的工具表里本来就写着「生成地图与 NPC」（design.md:695），§11.2 也早已画出 `generate/` 模块（design.md:803）——这不是新加一层 |
| 导演那只手 | `grow_terrain(requirement: String)`，**一段自由文本**；缺口清单、区划、材质表、预设清单都由代码附在工具结果里 |
| 范围 | 缺口用 **chunk 编号**（代码列出来，通常几块到几十块）；自由生成用**方位 + 块数**（「北 4 块」），代码换算成 chunk 框。两种口径分开，因为一个有清单、一个没有 |
| 物品 | `make_object` **一只走到底**：先按 brief 查预设库，没命中就**根据导演的要求**给物品生成体提要求（与 `model_shape` 同形——`ShapeModeler.model(brief)` 按 brief 查缓存，造完 `learn` 进生成包），再放上去 |
| 提交 | 一次调用产出的**全部后果整批原子提交**（与判定同形） |
| 接壤 | 把**相邻已生成地块的边缘剖面**给它——接缝是一眼看出的东西，而它本来看不到旁边长什么样 |
| 缓存池 | 新开 `SystemId.GENERATOR`，思考开着 |

#### 表格那只手重做成两只

A.15 早就写了地形有**两个写入口**：三只框选 + 一只表格（design.md:2203）。A.16 又说表格不给生成器（理由是「一片 32 块的缓冲圈用表格写就是几千个字符」）。用户把它改成了：

> 表格的工具改成框选一个区域，返回这个区域内的地形，然后以这个框为最大边界输入表格修改，还应该有个工具，可以框选查看地形

于是：

- `look_terrain(框)` —— 框选**查看**地形，返回一张表。
- `edit_terrain(框, 表)` —— **表格必须与框严格同尺寸**，每格都写，`.` 就是挖空。框是最大边界，超出即驳回。
- 框的大小按**字符预算**限（渲染出来 ≤ 8000 字符，约 20×20×20 格），不按格数——表格的代价是字符，框选的代价是段数。
- 语法：**抽一个共用的分层字符网格**，两端各自定义「层头单位」与「字符含义」（形状那边是厘米 + 质点，地形这边是地形格号 + 材质）。A.11 那条「读写同一种表示法」说的是同一个东西的读与写，不是所有表都长一样。

#### 还有一条：一片怎么写进后果

`TerrainLimits(maxCells = 4096)` 挡住的不只是生成器——**一块 chunk 是 16×16×256 = 65536 格**，一次铺满就超限十六倍。用户选的是**按段数算**：新增 `maxRuns`，格数上限放宽到百万量级只当安全网。

理由与 §14.26 那条同源：按列分段之后，格数早就是存储的实现细节了，**段数才是真实的写入量**。而逼模型把小框拼对，是又一次「油灯坐标」式的错误来源。

### 14.31 生成器第一次真跑：协议全对，而 34 分钟里它不是主角

（2026-09-26 实测，探针 `spike/TerrainGenProbe.kt`）

拿 §14.30 那套跑了一次真的：从零长起 `(6,0)` 与 `(6,1)` 两块 chunk（镇东官道那一段），要求由探针充当导演给。

#### 协议这一边，一处不错

| 读数 | 值 |
|---|---|
| 耗时 | **2 041 675 ms（34 分 2 秒）** |
| 生成器自己的请求 | **25 次** |
| 用量 | prompt 47 074（**命中 46 848**、未命中 226）、completion **956**（其中思维链 370） |

一次尝试、干净收工、55 条后果落库，而**生成器自己一共只吐了 956 个 token**。缓存命中 46 848/47 074——六只手的 schema 加材质表加规矩那一整段前缀几乎全部命中，`SystemId.GENERATOR` 这个池的隔离是有效的。

#### 地形确实读懂了那句话

| 列 | 剖面 |
|---|---|
| (100,5) | soil 240..255 → grass 256..256（北边，路面高度） |
| (104,8) | soil 240..256（踩实了的土） |
| (100,20) | soil 240..253 → grass 254..254（往南低两格） |
| (108,18) | soil 240..254 → grass 255..255 |

要求里「往南那一片地势略低一点」在数值上是真的：北边地面 256，南边落到 254。三处 `soil → water`（`97..104 × 21..26`、`106..111 × 24..30`、`98..103 × 28..30`，都挖在 z 254 那一格）就是「更湿」那半句。

#### 34 分钟里它自己占的不到一分钟

25 次请求、956 个输出 token——按 §14.22 那条 `墙钟 ≈ 0.4~0.7 秒 + 输出 token ÷ 200` 算，它的账是几十秒。

剩下三十分钟全在 `make_object`。这一片一共放了 **21 件**东西：

| 件 | 数 |
|---|---|
| 橡树（`n_oak` 6 + `s_oak` 5） | 11 |
| 垂柳 | 3 |
| 路石 | 4 |
| 湿地灌木 | 1 |
| 芦苇丛 | 2 |

它们带着的体素点阵**加起来 5436 个 `PointCluster`**，平均一件 259 个。

根因是 §14.30 写下时就知道、当轮没去动的那一条：**预设库的出厂包是空的**（`PresetLibrary()` 的 builtin 是一张空表）。于是 `byBrief` 一次都没命中过，21 件东西件件走「现造」，而建模探针量过**单件 2–100 秒**。21 × 97 秒 ≈ 34 分钟：账在这里合上了。

**这不是生成器写错了，是它把预设库那个缺口放大了。**一件东西第一次出现时慢一下，与一片林子四十分钟，是同一件事在两个尺度上的样子。而 `make_object` 的设计里本来就有解药——预设清单会进 user 那一面（`TerrainGenerator.kt:460`），模型照着清单里现成的 brief 逐字抄就能命中；**清单是空的，解药就没得吃**。所以「出厂预设从哪来」现在是生成路径上最贵的一环，已记成 §12 第 36 项。

#### 这一轮逼出来的两个协议 bug

都由这次真跑撞出来，各有一条回归测试：

1. 助手消息不能带**空数组**的 `tool_calls`：`Invalid 'messages[N].tool_calls': empty array. Expected an array with minimum length 1`。
2. 把它折成「字段整个不出现」之后，同一处立刻换成另一种拒法：`Invalid assistant message: content or tool_calls must be set`——那条消息**两样都没有**了。

两次说的是同一件事：**「一句话没说、一只手没动」的那一轮不该存在于历史里**。根因在 `judge/ShapeModeler.kt`：它把这一轮记进历史写在 `calls.isEmpty()` 判断**之前**（那半句 `messages += raw.assistant()` 现在挪到了判断之后）。另外在 `ChatMessage.toWire` 上加了一条本地守卫，让这类消息在离开进程之前就炸，而不是跑到端点换一段 SSE 里的错误载荷——那一刻整条请求已经废了，而它可能带着几十个回合的历史。

### 14.32 第二道关：属性与关键词搜索，以及第一批出厂件

（2026-09-28 实测与实现。设计见 A.14；探针 `spike/PresetSweep.kt`）

§14.31 把账算清之后，第 36 项解药看起来很简单：**把出厂包填上**。但先说一个当轮才看明白的数字。

#### 34 分钟里只有两种东西，而它们是同一棵橡树

回头看 §14.31 那张表：21 件东西里 **11 件是橡树**。而 `make_object` 的缓存键是那句要求、**逐字比对**——11 次里模型每次写的要求都略微不同，于是 11 次全部落空、11 次现场建模。

所以病根不是"库是空的"那一条。**库里就算有东西，模型也无从知道它叫什么，更没有理由去抄。**这与 A.2「说话必须是显式动作」是同一条思路：看不见的东西，模型不会去用。

用户因此改的方向是**检索本身**，不是"多扫几条进来"：对物体做属性总结（一个类别 + 一串标签），然后按关键词搜。见 A.14「三个身份，两道关」。

#### 第一批：小而准的十九件

对着两处现成的内容挑的——`StartingWorld.tavern()` 里那九样东西，以及这次生成真正放到地上的那些（橡树、垂柳、灌木、石头）：

| 类别 | 件 |
|---|---|
| 树木 | `spreading_oak_tree`（4818 格）、`weeping_willow`（3640）、`rough_tree_stump`（634） |
| 灌木 / 植物 | `spreading_shrub`（2350）、`wild_grass_clump`（**全是质点**） |
| 石头 / 木材 | `angular_halfburied_boulder`（1156）、`fallen_log_150x30`（960） |
| 家具 | `oak_square_table`（816）、`wood_slat_back_shelf`（1248）、`wooden_chest_with_clasp`（644）、`wooden_chair_backrest`（173）、`three_leg_wooden_stool`（73） |
| 容器 / 餐具 / 灯具 | `wood_barrel_two_iron_hoops`（1376）、`wooden_round_plate`（33）、`dark_wood_cup`（**17**）、`pottery_oil_lamp_with_glass_chimney`（**12**） |
| 工具 / 绳索 | `short_handle_hatchet`（25）、`bound_twig_broom`（94）、`coiled_hemp_rope`（16） |

**19 件全部画成，一件没失败**，用时约 **23 分钟**（一棵橡树比一张桌子慢一个量级——4818 格对 816 格）。十九件里 **19 条都有标签**，没有一条是"没写属性"。

那个 12 格的油灯是最值得看的一条：**它是这次改动真正的成本下界**。现造一件小东西也要两分钟往上（§14.21 量过 2–100 秒），而它进包之后放一次是零请求。

#### 文件的形状：网格文本，不是序列化的 `VoxelShape`

第一版直接序列化 `List<Preset>`（`VoxelShape` 本来就是 `@Serializable`，最省事），产物 **2194 KB** 且没人看得懂——一堆坐标三元组，`{"x":195,"y":195,"z":5}` 二十几个字节，而网格文本里它是一个字符。

改成存 [ShapeGrid.render] 出来的网格文本（`world/PresetPack.kt`）之后：**81 KB**，而且一眼能看出形。`dark_wood_cup` 那条现在长这样：

```
z=0        z=5
###        ###
###        #.#
###        ###
```

这一条是用户选的（"JSON 资源文件、内容是网格文本"），而我第一版做成了第三种选项。**转格式不必重画**——那十九件是实打实花掉二十几分钟画出来的，所以 `PresetSweep` 留着一条认老格式的路径，跑一趟就把全部十九件改写了，零次模型调用。

#### 落地时的三个决定

1. **属性由建模那一步的模型一并交**（`voxel_done` 多两个参数），不是代码从 `brief` 切、也不是手写在清单里。出厂包与生成包因此走同一条路，不会出现"出厂那批搜得到、现造的搜不到"。
2. **`byBrief` 留着作第 0 道关**——免费、瞬时、不会选错。两道关问的不是同一个问题：前者是"是不是同一句话"，后者是"是不是同一类东西"。
3. **预设库挂在会话上**，判定、生成器、导演看同一份。三处各拿一份的话，"刚才造过的那张桌子"对另一处就不存在，而症状是同一件东西被反复建模。

#### 还没做的

- 包只覆盖开局那一片与酒馆。补一批只要往 `PresetSweep.BRIEFS` 里加几行再跑一次（增量：已经画过的会跳过）。
- **生成器还没接进会话**（§12 第 35 项剩下的那半：导演那一刀），所以 `find_preset` 与出厂包目前在生成器上还看不到——接线是一条参数。
- **单边两百厘米的上限**（§12 第 37 项）在下一轮里删掉了。`ShapeLimits(maxSideCm = 200)` 是默认值，于是世界里的东西一律不超过两米——一棵树只能画成树苗，十九件里那两棵树正好卡在这个上限上。用户裁定「不做大小限制」，`maxSideCm` 整个删了，只留 `maxCells` 当保险丝。

### 14.33 导演接上生成链路：九轮问答定下的形状

（2026-09-26 定，**本轮开工**）

这一刀开问时定的范围是「只接生成链路」，两级导演另开一刀。问到第八轮快速档被拉了进来——「平时导演觉得要加地图」需要一个醒着的导演。所以这一刀同时立起了两级导演的骨架，而手那一边只装了一只（切换思考），剧本标注等剧本池。

#### 触发：两条路，性质不同

硬圈缺口那条由**代码**发现，代码直接同步叫思考档，玩家等。缓冲圈那条由**快速档**发现，它叫醒思考档，后台异步跑。

两条路分开，是因为它们对玩家的意义相反：一条必须挡住玩家（他正走进一片还没有地图的地方），一条不能挡（他只是在走路）。

**圆心跟着玩家。** A.16 里两句话对不上：它说「以玩家为中心画两个圆」，又说触发点是「玩家所在的 chunk 距硬性圈边缘不到一块」——圆心在玩家身上时，玩家离边缘永远是 4 块。按前者解：硬圈是**以玩家所在 chunk 为圆心、半径 4 块的圆盘**，触发判据是「这个圆盘里有还没长地形的 chunk」。开局那块地正好是这样一个圆盘（49 块），所以开局不缺；玩家每跨越一块，圆盘移一格，露出一个月牙。

**同步那条路的账单要先说清**：硬圈跟着玩家走，所以玩家每跨越一块（8 米）就触发一次，而一次生成是几十秒。这是「硬圈内同步阻塞」的真实代价。

#### 区块坐标

**原点在玩家开局那一块的左下**——玩家开局在 (1,1)。直角坐标，横 x 纵 y。

导演默认拿到的是缓冲圈（半径 32 块）那一张字符地图：行头列头就是数轴，已生成的、硬圈缺的、缓冲圈缺的分三种字符。另给一只 `look_map(框)`，它可以查整张地图。

**缓冲圈是硬边界**，填到圈外的坐标被驳回，理由可执行。

这一条推翻了 §14.30 的「自由生成用方位 + 块数」。方位加块数是在没有清单时给模型一个参照系；而这里清单、数轴、已有区块三样都在，直接写坐标比换算一遍少一层错。

#### 一次生成调用

导演一次被叫醒可以同时要求**必需的那几块**与**缓冲圈里额外的几十块**，而那是一次调用——§14.30 那句「分两次等于让第二次重新理解一遍这里为什么是森林」仍然成立。

物品**并进同一次调用**：导演给「放什么 / 在哪一块 chunk / 默认描述」，具体落在这一块里的哪儿由**生成器在铺这块地的时候**定——它刚铺完，看得见剖面。导演手里没有地形剖面，给它一个厘米数字只会得到一个编出来的数字（「油灯坐标是编的」那一课）。

代码守的那条线是：**导演点名的那一件必须落在它说的那一块里**。落到别处不算，退回重来——判据从后果上读，不从回答里读，与「必需区块写没写进去」是同一条纪律。

导演点名的是**地标，不是清单**。一片森林里的每一棵树不该由它逐棵列出来——那是生成器在铺那几块地的时候顺手做的事。

#### 并发

并行调用地形系统的条件是**地块不重合**：地形看 chunk 集合，物品看落点所在的 chunk。提交时共用一把短锁，整批原子提交这条纪律不变。

**同一件东西不会被造两遍**：建模开始之前先把它的 id 与属性写进预设库，作为一条「正在产出」的占位；并发的第二个请求会搜到它并等它，而不是另起一次 2–100 秒的现造。

#### 「什么都不做」的合法性按来源分

硬圈缺口叫醒的那次，必需区块必须写入；没写就重试，连续重试用尽后报错——界面弹一条提示，日志里留一条 ERROR。

快速档叫醒的那次，它判断这一带还不用长，什么都不做是合法结果。

#### 两级导演：这一刀只立骨架

快速档每回合醒着，**不挡玩家**（回合提交之后在后台跑），`thinking: disabled`。快速档与思考档**共用同一段上下文**，切档只改参数，并在提示里标明当前是哪一档（§8.5）。导演的历史这一刀仍是每次叫醒新建一段；等上下文管理做出来再改成累积。

快速档这一刀只有一只手：切换思考。**它没有生成能力**——生成只有思考档能做。

#### 工作进程是一份并行任务清单

界面状态从一个字符串换成一份清单，每个在跑的活一条：「正在判定」「正在生成地形 (6,2) (7,2)」「正在生成物品 橡树」「正在改时间轴」。异步之后同时会有一条以上的活在跑，一个字符串装不下。

#### 这一刀改写与不动的旧条目

§14.30 的「自由生成用方位 + 块数」改成都用区块坐标。

§12 第 21 项（导演任务队列）由「地块不重合就并行」取代，不再是一个全局串行队列。

§14.30 的「判定不能触发生成」不变：判定只能改已经生成的区块。

### 14.34 导演的两级骨架：四个唤醒理由，四份契约

（2026-09-26 实现，提交 `d3d3a8f`）

§8.5 定的两级形状在这里落成。做完之后回头看，这一层真正的难点不是「两档」，是**「什么都没做」有
两重含义**。

#### 四个唤醒理由

导演不再有一个「排时间轴」的窄入口，而是 `wake(world, Waking)`，唤醒的理由是四种之一：

| 理由 | 谁发起的 | 档位 | 契约 |
|---|---|---|---|
| `Watching(turn)` | 快速档每回合 | 快速 | **什么都不做是合法的** |
| `Arrange` | 界面上那个按钮 | 思考 | **至少排一件** |
| `HardGap(required)` | 代码发现硬圈缺口 | 思考 | **必需的那几块必须写进地形** |
| `Called(why)` | 快速档把它叫起来 | 思考 | **什么都不做是合法的** |

「空手 = 重试」这条判据因此不能统一写。第一版很容易写成「一个工具都没调就是失败」——那是 `Arrange`
那一路的契约，把它套到 `Watching` 上，快速档每回合都会被逼着做点什么，而那正是它最该少做的事。

判据的读法也不一样：`Arrange` 看的是它交出来的东西，`HardGap` 看的是**世界状态**
（`Terrain.isGenerated`）。后者是这一层唯一一条「模型说了不算」的判据。

#### 换档：只换参数，补在末尾

快速档那一段提示里**没有地图、没有空间框、也没有时间轴**——那些是它每一回合都要付的钱，而它大多数
时候什么都不做。它拿到的只有一个数：「离内圈最近的空地还有几块远」。那个数刻意**不是坐标**：快速档
这一刀没有生成能力，知道坐标只会诱惑它去试试。

思考档接手时，那些东西补在**末尾**（一条新的 user 消息），前缀一字不动，缓存照旧命中。

两处代价，都记在这里：

- **`reasoning_content` 那条硬约束在这一层比单档时更容易破。** 两档共用历史而工具表不同，快速档那
  一轮的 assistant 消息没有思考，回传时必须是 `""`。离线测试把这一条钉住了。
- **`wake_thinking` 那只手是单向的。** §8.5 说思考档觉得稳定了会切回去，这一刀**不装**那只手：一次
  唤醒在模型沉默时就结束了，切回去意味着「这一次工作剩下的一半用便宜档跑」，而那要等导演变成一个
  跨回合长活的东西才成立（§12 第 38 项）。提前装一只没人会正确使用的手，只会让它在历史里漂移。

#### `grow_terrain` 只给「放什么 / 在哪一块 / 默认描述」

具体落在这一块里的哪儿由生成器铺地时定（§14.33 那条：导演手里没有剖面）。两个当场驳回：

- **缓冲圈以外的坐标。** 理由里带上能长的半径，因为把数字退回去是不够的——模型需要知道「远」本身
  就是它不该做的事。
- **写坏的放置行。** 一行一件，`放什么｜在哪一块｜默认描述`。坏行**一条都不丢**，退回去说清是第几行
  并给出可照抄的格式（§1.3：静默丢弃 = 死循环）。

#### 时间轴的提交挪了一层

原来 `TimelinePlanner.apply` 在 `arrangeOnce` 里。现在一次唤醒可能同时排事、长地、放东西，所以它挪到
`wake` 那一层：`once` 只收集，`wake` 整批校验、整批提交。落一半进去，剩下那一半还得让它重排一次，
而它重排时会看到一张已经变了一半的表。

#### `look_map` 与默认那段地图的区别

默认那段画的是以玩家为心的圆盘，而 `look_map` 画的是一框。`ChunkView` 因此拆出 `axes` 与 `cell`，
新增 `renderBox`：**不画圆盘、不把框外涂成空格**。「看得远不等于长得到」这条边界由 `grow_terrain`
驳回，不该由一只手悄悄掩掉——悄悄掩掉的话，模型看到的地图会说「这里什么都没有」，而真相是「这里
不归你管」。

#### 还没接的

**生成器还没有进会话。** `TerrainGenerator` 现在是被导演直接持有的（它会自己落库），但会话那一层的
两条触发器（硬圈缺口同步叫、缓冲圈异步叫）、并行调度、建模占位、以及那份并行任务清单都还没写。
接完之后出厂预设包与 `find_preset` 才真正走在生成路径上。

### 14.35 会话那一侧：两条触发路径与一份任务清单

（2026-09-26 实现，提交 `b5b8cd7`）

§12 第 41 项那一半。上一刀把导演做成能接四个理由、也能生成，缺的是**没有任何东西在正确的时机叫
它**。这一刀就是那个东西。

#### 两条路，顺序不能换

| 路 | 谁发现 | 档位 | 等不等 | 「什么都没做」 |
|---|---|---|---|---|
| 硬圈缺口 | **代码**（`requiredChunks`） | 思考 | **玩家等** | 失败 |
| 缓冲圈 | 快速档每回合 | 快速 | 后台 | 判断 |

顺序是先硬圈后缓冲圈。硬圈那一条是「世界少了一块地」，而玩家可能正站在缺口边上——那不是一次可以
稍后再说的调度。补不上时写一条 ERROR **并且置 `notice` 弹到界面上**，这是整个界面里唯一一个要玩家
自己关掉的东西：别的失败都只写日志就够（那是玩家自己那一轮没成，他本来就盯着日志），而这一条不是
——它是世界少了东西，玩家看见的是「这里什么都没有」，而且日志会被后面几十行盖掉。

#### 后台那一条逼出了那把锁

有了后台那一看之后，**世界第一次真的有两个写入者**：玩家那一轮（判定第二步）与后台那一看（它可能
一路走到生成地形，一次几十秒）。世界是一张普通的 Map，没有内部同步，两个写入者交错跑就会丢改动。

于是有了 `writes` 那把锁。它只圈住**会写世界的那一次调用**，不圈判定第一步、不圈渲染——圈得再宽
一点，后台生成会把玩家的下一次判定一起卡住。

**这一条是 §14.33「不重合才并行」的保守版，要写明白。** 那里定的是两块地不重合就允许并行，而并行
要求生成先把后果算在一个快照上、之后再提交。现在生成是**就地提交**的，所以先用一把锁把它串起来。
串起来永远是对的，只是慢。

同一个理由让第 41 项里那条「建模前先写一个正在产出的占位」**暂时没有意义**：两次建模不可能同时在
飞，就没有「第二个请求搜到占位就等它」这件事。它是为并行准备的一半，等并行真的落地再补。

#### 任务清单：一件事一行，而行里的字会改

界面上原来那个 `status` 字符串换成了 `tasks`。理由是用户那句原话级别的裁定：**工作进程是一份并行
任务清单，不是一个字符串**——判定在跑、地形在后台长、导演在看着，这三件可以同时成立，而一个字符串
只能显示其中一件。

有一处不显然的写法：**行里的字是会改的**（「跑一轮…」→「判定中…」→「算后果…」），而不是每换一步
就多一行。一件事往前走与两件事同时在跑，是两件不同的事，而后者是假的信息。

#### 注入点

会话现在有两个构造参数能塞假的进去：`judge` 与 `director`。不注入的话，这一层的三条触发路径只能拿
真 key 验——**第一版就是那样，测试静默地打到了真端点**，报回来一句「认证失败，请检查 api key」，
而那句话在测试输出里长得像一个无关的环境问题。

#### 三支测试与它们逼出来的那个写法

`GameSessionTriggerTest`：补不上要说出来、地形齐着一个字都不多说、前台与后台都在清单上而后台不挡
玩家。第二支不是重复——判据是「硬圈里有没有还没生成的块」，而开局那片地正好填满硬圈；少了它，
「没检查」与「检查了、没事」在测试里就没法区分。

第三支逼出了这一刀里最有用的一件脚手架。**后台那一条没法靠「跑完再看一眼」验**：它是排队跑的，
等它跑完时早就从清单上下来了。所以这里的假端点带一个**每次请求都会被调到的钩子**，会话状态在那个
当口被读一次——那是唯一一个确定落在「它正跑着」里头的时刻。「后台不挡玩家」在那一刻的含义很实在：
`busy` 是假的，输入框还开着。

#### 联机验收：整轮跑通了，而它逼出了一个新的先后关系

`TurnProbeSpike` 用真 key 从头跑到尾，**9 次模型调用**（2 次渲染 + 7 次判定），四件事全部成立：

```
看过了你：4 句 1724 ms → 再看：0 ms（固化命中，0 请求）
「我拿起桌上那杯麦酒」  → 酒杯挪到 (1200, 300, 12890)；你的「两手」变成「端着一只…酒杯」
「我把手里那杯麦酒放回桌上」→ 酒杯挪回 (1200, 400, 12800)；你的「两手」变成「空着」
「举起短柄斧把木桌劈成两半」→ 木桌 → 被劈成两半的橡木桌；斧刃卷了口；酒杯洒了、内容物变空
```

那次劈桌是**新加的一步之前发生的事**：探针原来的场景是「端酒杯」接着「抡斧头」，而判定把它**正确地
驳回了**——

> 你两手都端着酒杯呢……斧头是挂在腰上的，得腾出手来才能握住它抡起来，所以这一下你劈不出去。
> 先把酒放下，才谈得上举斧。

那条理由是对的：**端着酒还能劈桌子，本来就不该成立**。所以错的是探针的场景——它假设了两轮之间玩家
什么都没拿。修法是补上「放下酒杯」这一步，而不是放宽判定。

**这是一条值得记住的先后关系**：判定的玩家状态比以前厚了（属性、规则书、优先级），于是「上一步留下
了什么」开始真的影响下一步能不能做。以后写多步场景（探针、开局剧本、任何有顺序的验收）都要假定这一
条：**上一轮的状态是下一轮的前提**。

一处要说明的空白：**这一支探针没有压到后台那一看**。它调的 `runTurn` 不传 `scope`，而按设计那一条
只为界面那条路起（挂起入口传 `scope` 会把一次 `runBlocking` 拖着等一条后台协程）。所以「每回合在后台
看一眼」这条路的联机读数还没有——离线的第三支测试压的是它的接线。第一次真正跑界面时要专门看它。

### 14.36 对话：说了话，听得见的人会答

（2026-09-26 实现，提交 `04944d2`）

§5 一直只有半句话——「说」那一半没有接收方，`runTurn` 里那个参数连往下传都没传。这一刀把它接完。

#### 听者由判定裁，代码不划半径

用户对这一条的裁定是原话级别的：**「这种程度的动作应该被判定系统修正为指向声音范围内的目标」**。

于是说话的路径就是判定第一步：同一个 `beginTurn`、同一份空间框、同一段提示词，只是跑完第一步就把
那个 `Turn` 丢掉——说话没有第二步，它不产生后果。

`targetingPrompt` 里因此多了一条规矩。原来那条「报的东西也包括会被这次动作牵涉到的角色（我喊了一
嗓子——旁边那个人也算）」在实现时被发现不够用：它说的是「动作牵涉到的人」，而说话要报的是**听得见**
的人。两者在多数场合重合，但判据不同，而判据不同的两条规矩必须在提示词里分开写。

**代码这边一个字都没加。** 第 7 项（声音沿什么传播）仍然未定——现在既没有半径也没有遮挡，纯靠判定
看着空间框判。

#### 说话不走纠正预览

§4.7 的预览拦的是「判定会改错世界」。而说一句话**改不了任何东西**——它是这个回合里唯一一件不需要玩
家过目的动作。所以对齐结果与勾选不一致时这里不挂 `pending`，直接把判定报出来的人当听者。这是「预览
为什么存在」的自然推论，不是一处例外。

#### NPC 的「做」走同一条判定链路

用户裁定：**走同一套**，只是发起者换了个人。理由是硬的——判定是唯一能改世界的地方（§1），给它另开
一条通路就等于世界有了第二个规则来源。

代价是它一次「做」要花两到三次调用。**那是这一层的真实账单，不是可以省掉的。**

#### 深度钉在 1

NPC 说的话**不再唤醒别人**。少了这一条，两个话多的角色能一直接下去。更深的一层理由是历史还不累积
（§12 第 38 项）：一段只装着一句话的上下文，接不出有意义的三轮对话。等 §6 的滚动窗口做出来，这一条
该和它一起重新想。

#### 两份视野，各答一个问题

用户给样板角色视野的形状是：**「给区块为单位的粗视野，和当前所在区块的精细视野」**。

第一版只做了粗的那一份，而它画的是「有没有地形」——**实测出来是一张全是同一个字符的图**：

```
y=-03     #          （`#` = 有地形）
y=-02   #####
y=-01  #######       矮人 9×9 的视野，81 格
y=+00  #######       每一格都写着「这里有地」
y=+01 ####@####      `@` 是它自己
y=+02  #######
```

那不是错，那是空的：**图上没有一个字是矮人还不知道的**。所以这一刀把它拆成两个尺度：

| | 问的 | 一格 | 画什么 |
|---|---|---|---|
| `ChunkView.renderLandform` | 这一带是什么地方 | 八米 | 地貌（城 / 镇 / 路 / 林 / 野 / 水 / 山） |
| `ChunkDetail.render` | **我手边有什么** | **一米** | 具体哪样东西、脚下什么材质 |

合成一份是做不到的：八米一格画不下「桌上那只杯子」，而一米一格铺 32 米是 64×64——一张 4096 个字符
的图，每次唤醒都付一次。**尺度不同就该分开画**，与 §7「渲染只做一件事」是同一条。

`Landform` 因此多了一个 `glyph`：中文在等宽字体里占两列，网格会散架，而对齐是网格的全部价值。名字留
在图例里——与材质那套做法逐字相同。

`RegionView.describe` 抽成了共用的 `describeThing`：现在有两份视图要列东西，而它漂开的后果是具体的
——**属性不印，读的人手里就只剩一个光秃秃的名字**（§14.24）。

粗糙的那一份仍然保留地形缺失那两个字符（`!` 与 `.`）：它们的含意是「这里还不存在」，比「这里是什么
地方」更硬，生成器那一路靠的正是它。

#### 一次搭话的账单（联机，五场）

| 场景 | 矮人说了什么 | 请求 | 耗时 |
|---|---|---|---|
| 打个招呼 | 「嗯。……有事？」 | 6 | 8.6 s |
| 一个不太友善的请求 | 「哪儿来的？」 | 7 | 14.7 s |
| 叫它过来 | 「我不认得你。」 | 6 | 10.0 s |
| 说一句 + 擦桌子（停在预览） | —— | 1 | 0.82 s |
| 空屋子 | （没人应声） | **1** | **0.65 s** |

前三场都有同一行：`OK｜酒馆里的矮人 做了一件事——没有改变世界`。**它每被搭一次话都说一句 + 做一个
不过判定的空动作**（抬眼看一眼、哼一声），而那个空动作要跑完整的判定两步。6 次调用里有 2–3 次买的
是这个。用户裁定：**先不动，记成成本**（§12 第 43 项）——它是「意愿与裁决分开」的真实代价，不是
bug。

空屋子那一场是这一刀里最便宜也最对的一条路：判定只报发起者自己 → 没有人应声 → 1 次调用、0.65 秒。
「说一句 + 擦桌子」那一场停在预览上是**对的**：玩家只勾了木桌，而判定对齐出木桌、酒杯、抹布、你四
样（§4.7），于是挂起等确认——探针没点「应用」，所以这一场不该拿来比耗时。

#### 视野改完之后，它多说了三句，也暴露了世界里少一样东西

换掉那份全 `#` 的视野之后重跑，第一场的读数变成了：**四句话 + 两次被驳回的动作**，35 秒、16 次调用
（改之前是 1 句、7 次、11 秒）。

- **两次驳回的原因里有一次是世界错了。** 它想呷一口自己手里的酒，判定驳回了「这一片里没有哪件东西
  是「我两手捧着的那只杯子」」——**因为它手里那只杯子根本不是一样东西**：`StartingWorld` 把它的
  `两手` 写成"捧着自己那只杯子"，而世界里没有那只杯子。§1 那句「地图就是事实库」落到这一层是：
  **说得出名字的，得在图上**。玩家那把斧子、那块抹布是实体，它那只杯子也补成了实体
  （`dwarf_cup`）。
- **另一个原因是视野真的变多了。** 它看见桌上那只酒杯离自己两格，于是伸手去够——判定驳回得又准又
  好看：「离你有两格远——你一臂只够得着一格以内……想呷它，得先站起来走过去」。**这条驳回是这一刀
  最想要的那种输出**：世界在说话，而不是系统在报错。
- **四句话那一条是提示词缺了一句规矩**，加了第 6 条（一次醒来通常只说一句，最多两句；要做的事最多
  一件，被驳回了就换或者不做）。改完复跑，三场各一句：`「嗯。……有事？」`、`「哪儿来的？」`、
  `「我不认得你。」`——同一批场景，6–7 次调用、8.6 / 14.7 / 10.0 秒。

**留一条读法在这里：这一节的数字都是 n=1。** 上面那个"四句"与"一句"之间隔着一次提示词修改，而这个
样本量分不开「视野变多让它话多」与「模型本来就会偶尔话多」。要真判这一条，得把同一套场景跑五轮。

#### 「什么都没做」在这一层也是合法的

一个不想理你的矮人是一个真实的反应。把它推成「必须说点什么」，每个 NPC 都会变成同一个话多的家伙。
这一条与导演的 `Arrange`（至少排一件）**正好相反，而两条都对**，因为要的东西不一样——§14.34 已经为
同一个坑写过一次。

#### 那个坑又踩了一次

`WorldSnapshot(StartingWorld.tavern())` 看着是对的，而它漏掉**规则书、地形、区划**三样。三个都有默
认值，所以不报错，只给出一个「规则书是空的、脚下一格地都没有」的世界。第一次是规则书（§14.35 的测
试逮到），第二次是地形（`NpcProbe` 的离线那一段逮到——矮人眼里的整片地都写着「缺」）。

修法不是「下次记得写全」，是 `StartingWorld.snapshot()` 把那四样捆成一份。两次都不是逻辑错，是调用
点少写了一行。

#### 还没做的

- **悄悄话（§12 第 5 项）**：现在一说就是满屋都听得见，没有「公开 / 低声」两档。**§14.37 之后它的
  落点更清楚了**：「谁听得见」现在是代码按空间框投递的，所以两档要做的不是加一个开关，而是让判定
  在 `address` 那一栏上少报几个人。
- ~~**NPC 的记忆**：每次唤醒新建一段 messages（§12 第 38 项同一个口径）。~~ **§14.37 做了。**
- ~~**状态循环（§12 第 24 项）**：矮人现在只是「待在那儿」。~~ **§14.37 做了基线那一半。**

### 14.37 记忆与状态循环：投递总是发生，唤醒才是例外

§12 第 44 项那一刀。它从「NPC 为什么每一句都从零开始」出发，最后动了四层——**记录层、第一步的产出、
角色的提示词、一条提示词规矩**。

#### 一个缺口与另一个缺口原来是同一个

§6.1 写着「一份事件流 + 每角色的 id 列表」，而 §12 第 20 项写着「记录层还不存在」。开这一刀时才发现
**它们是同一个缺口的两种说法**：前者说的是"角色读什么"，后者说的是"发生过什么该放哪儿"，而两者要
的是同一份 append-only 的东西。于是它一次做掉两件。

用户在问「那条记录的文字由谁写」时的裁定是「**不需要记录了，导演每轮都是醒着的**」——这句话把问题
从"谁来写"改成了"要不要人写"：**不要人写**（尤其不要摘要模型），但记录要有，它存的是**原始材料**。
落到形状上就是：一条记录 = 谁、说了什么（**原话原样**）/ 做了什么、后果是哪几条。**代码拼，不经过任
何模型。** 两条理由都是硬的：措辞唯一（两份由模型写的历史迟早会在同一个事实上写出两种说法，那时没
人能回答"它当时到底收到了哪一句"），以及零成本、零漂移——而语义并没有丢，它由**后果用了哪只工具**
和**那个东西的 label** 一起承载（`Replace(oak_table → 裂成两半的木桌)` 本身就说清了一切）。

`Event` 上的 `effects` 是一个**整体**，§6.1 那条「一次提交产生的全部后果不可切开」就落在它上面：裁窗
口时不会出现"看到杯子掉在地上却没看到桌子被掀"。

#### 「指向」归判定，「投递」归代码

这一刀里最省事的一处来自用户那句话：

> 听见和看见是模型自取的，但是像大吼一嗓子明显是对周围人的指向，和同伴聊天，隔壁桌的人听见是不同的，
> 前者被判定为指向在场的人，后者是进入非指向的信息流里

它把一件含糊的事劈成了两件清楚的：

| | 谁裁 | 结果 |
|---|---|---|
| **指向**（这话冲谁说） | **判定** | 那些人被**唤醒** |
| **投递**（这一轮发生了什么谁收得到） | **代码**（`spatial/Witnesses.kt`） | 进他们的**编号列表**，不唤醒 |

于是「跟同伴闲聊」与「冲满屋子喊一嗓子」在系统里终于分得开，而 §3.2 那句「**投递总是发生，唤醒才是
例外**」第一次有了代码：投递是一个编号，唤醒才是一次调用——**氛围 NPC 能有成百个而成本零增量，全部
来源就是这条分法**。

投递那一侧的粗筛用的是**和判定同一把尺子**（同一个 `RegionBuilder.of`、默认档位）。多算一个半径就等于
世界里有了两套"附近"，而它们迟早会漂开，症状是"判定看得见它，但它没收到这件事"。框**不跟着判定扩大**
——扩大是模型为了看清某样东西而做的，粗筛不需要那么准；多投递几条不危险（收到不等于相信），少投递才
危险，而少投递那一头由「指向」兜住：被指向的人一定收得到。

#### 一次第一步两用

分栏的直接收益是**省掉一次调用**。早先说话时判定要报「谁听得见」，而那是语义判断、代码划不了半径，
所以每说一句话都得**单独再跑一次第一步**去找听者——"说+做"的一轮因此花两次，而两次之间还多出一处会
漂开的地方。

现在 `JudgeRequest` 多了 `said` 那一栏，第一步一次给出两栏：`target`（动作作用到的东西，**纠正预览比
对的仍然是它**，§4.7 一个字没动）与 `address`（这句话说给谁听）。「说+做」的一轮从两次第一步变成
一次。

#### 一条被测试逼出来的修正

第一版把「记录那句话」写在"对齐成功"那一支里。测试立刻抓住：**「说了句话 + 做了个指向不存在的东西的
动作」这一轮里，那句话连同记录一起消失了**——而它明明已经说出口了。动作对不对齐得上，改变不了"他说
过这句话"。

改法是把记录挪到**分岔之前**：无论动作走哪条路，那句话都进记录层、都投递给这一片里的人；而对齐没成
功时 `address` 那一栏没有答案，于是**没有人被指向**——投递照旧，没人醒来。

#### 状态循环：基线由代码查，唤醒时注入一行

`Cycle` 是一张周期表（`Beat(atMinute, state)`），`Entity.cycle` 挂着它。**查表是纯代码，零模型调用**
——§3.2 说氛围 NPC"平时根本不是 AI"，就是这一行代码在兜着。

两条容易被写反的地方各有一条测试钉住：

- **跨夜那一格**。23:00 打烊之后到次日 07:00 开门之前，人还在"打烊"那一格里——`stateAt` 取「不晚于
  此刻的最后一格」，早于当天第一格时取**当天最后一格**。写成"今天还没开始"是一种看起来很像、其实把
  整个作息读反的错，而它不会报任何东西。
- **同一分钟两格** = 那一刻它到底在做什么没有答案。这不是"随便取一个"能糊过去的，所以进 `problems()`。

唤醒时**注入一行**（「没人打扰的时候，你此刻本来在做什么」）：零调用指的是**查表不花钱**，而模型接管
之后必须知道基线，否则一个正在打烊的酒保会表现得像一个一直在等你来的人。

#### 待办：到点不是自动发生，而是提醒它

`Entity.todos` + 角色手上的 `plan` 那只手。它与 `Cycle` 是两样东西，分界线是**消费者不同**：循环由代
码读（所以可以有成千条），待办进提示词（所以只能属于少数几个角色）。§3.2.5 早就把它写清楚了，这一刀
只是把它实现出来。

一条线没有松：**到点不等于自动发生**。到点了它只是出现在提示词里，那件事照常要动手、照常要过判定。
松掉这条线的话，世界上会出现一批没人做过、也没有痕迹的改变。

#### 空动作：一句提示词

§12 第 43 项那笔账（每次被搭话都多烧 2–3 次调用买到一个「没有改变世界」的动作）。用户的裁定是原话级
别的：**「加上不要为了做而做，不要为了说而说」**。

于是改的是 `Npc.SYSTEM` 第 7 条，并把"一次醒来只说话、或者只回一句就结束，都是完整的反应"写进去——
手里那两只手不是任务清单，不用每轮都过一遍。不新加手、不动判定：那三条候选路里，这一条改动最小，而
另外两条各自要拆掉一处已经成立的成果（`no_change` 是 §14.19 的成果；"比划"那只手会与 §1.2 的厚度
打架）。

#### 顺手合上的两个旧缺口

- **§12 第 20 项**（时间轴到期的事没有记录层）：`waitUntilNextNow` 现在把它们写进事件流，`kind` 是
  `CLOCK`，投递范围与别处同一把尺子。一条局限写在代码里：**这是一次世界级的事，而受众只按玩家身边
  那一片算**——远处同样该知道"酒馆打烊了"的角色收不到，等时间轴上有跨地点的事时这里要重新想。
- **§14.36 那条"等滚动窗口做出来再重新想"**：窗口做出来了，而**结论没变**——NPC 说的话仍然不唤醒
  别人。挡着它的理由从"上下文太薄"换成了"成环与成本"，而后者更硬：人聊天本来就可以一直聊下去，
  没有一条自然的终止条件。代码里那段注释跟着改成了新理由。

#### 联机读数（`NpcProbe` 五场 + `TurnProbeSpike` 整场）

**n=1，所以下面每一个数都只当方向看。** §14.36 已经为同一件事写过一次。

| | 请求数（§14.36 → 现在） | 耗时 |
|---|---|---|
| 甲 打个招呼 | 6 → **5** | 8.6 s → 19.6 s |
| 乙 不太友善 | 7 → **4** | 14.7 s → 4.7 s |
| 丙 叫它过来 | 6 → **5** | 10.0 s → 8.7 s |
| 丁 说一句 + 擦桌子 | — → **4** | 9.5 s |
| 戊 空屋子 | 1 → **1** | 0.65 s → 0.53 s |

三件值得单独说的：

- **「说+做」的一轮真的只用了一次第一步。** `TurnProbeSpike` 里那一轮是：`（你什么都没勾）`
  → `对齐到：酒杯`（一次对齐同时给了动作的目标）→ 矮人当场答了话。§14.36 时那里是两次。
- **乙那一次一个动作都没做**（0 次判定调用）。而甲与丙各还有一次「做了一件事——没有改变世界」。
  **空动作少了，但没有消失**——而这是 n=1，分不开"提示词改对了"与"模型这一轮心情不同"。要判它得
  把同一批场景跑五轮（第 43 项）。
- **`TurnProbeSpike` 整场 17 次调用**，而其中一次动作花了 **129 秒**：劈桌子那条路是 `Replace` +

- **循环由谁写**：现在开局那条是手写在 `StartingWorld` 里的，而 §3.2 定的是**生成时由导演写**。
- **笔记系统（§6.3）**：角色主动写一条"这件事我得记住"，与待办是两回事（那是计划，这是记忆）。
- 悄悄话（第 5 项，落点见上）、活跃化与回归（§3.2.1）、`plan` 的**取消**（现在只能加，不能划掉）。

### 14.38 一场八轮的对话：记忆真的在工作，而空动作这一次一个都没有

§14.37 给角色装上记忆之后，`NpcProbe` 那五场就验不出什么了——**它们每一场都是一句话、一个新世界**。
于是新开一支 `spike/ConversationProbe`：**同一场对话连着跑八轮**，一次量三件未完的账（第 3、43、44 项）。

八句话是排过的：第 3 轮问它"我刚才说这酒怎么了"（要记忆）、第 4 轮问它的名字（人设里有，**不该靠
记忆**，作对照）、第 6 轮问"我说过我叫什么吗"、第 7 轮问"那我姓什么"（**玩家从没说过**——答"不知道"
才对，这是照妖镜）、第 8 轮回到第 2 轮那个话头。窗口 12 条，第 6 轮装满，第 7 轮开始挤掉最早的。

#### 读数

**八轮一共 23 次调用**，逐轮是 3、3、3、2、4、3、3、2 —— **中位 3**。§14.36 那五场是每场 4–7 次。

**这一整场里一次空动作都没有。** §14.36 的账单是"每次被搭话，7 次调用里有 2–3 次买的是一个没有改变
世界的动作"；这里八轮 23 次里**零个**。「不要为了做而做，不要为了说而说」那句提示词第一次有了读数。

**记忆确实在工作，而且是逐字的。** 三轮里看得出三种：

- 第 3 轮（要记忆）：`你说淡。这话我记着。`——它引用了第 2 轮的原话。
- 第 6 轮（不该有）：`没。你光顾着问我的了。`——**不编**。
- 第 7 轮（更不该有）：`你名字都没说全，问我姓什么？我又不是算命的。`——不编，而且带着人设那份脾气
  （人设写着"不熟的人搭话，你先看他一眼，再决定理不理"）。

**两次「没什么反应」（第 4、8 轮）**：它一次工具都没调。第 4 轮问名字它不答，那是人设里"问三句答
一句"的效果；第 8 轮那句"接着刚才那句"它没接。**那是它的权利**（一次唤醒只说话、或者什么都不说，
都是完整的反应），但如果这种沉默变多，第 4 条规矩要重新看。

#### 三件要说清楚的

- **窗口这一轮没被压到边界。** 第 7、8 轮时最早的几轮已经出窗（第 8 轮时第 1 轮的"你好啊"没了），
  而那两轮它都没反应——**沉默不能归因于窗口**，那只是一次自愿的沉默。所以**窗口 N 仍然没有量出来**：
  要量它，得让对话长到"出窗的内容是它必须记得的东西"。§6.1 那句"观察它在多少轮之后开始重复或自相
  矛盾"，这一支探针还差得远。
- **n=1。** 23 次调用里零个空动作是好消息，但 §14.36 那 2–3 次也是在一个场次里数出来的。要把它变成
  结论，得把同一支探针跑五遍，看零是不是稳定。
- **它从来没用过 `plan`。** 八轮里没有一次安排将来的事——而那是这一刀新给它的第二只手。可能是这八句
  话里本来就没什么可安排的（**探针的场景问题**，不是工具的问题）；要验它，得给它一件真需要隔夜的事。

## 附：空间与物体

这一节是 v0.1 定稿之后补的，尚未并入正文，等它自己稳定下来再重排编号。

### A.1 空间用坐标，不用区域树

**地形和物体有精确坐标**，能解析成俯视图，也能转成文字准确描述给模型。

「分层区域树、不引入坐标」的提案已被推翻。推翻的理由是它混淆了两个独立的轴：

| 轴 | 由什么解决 |
|---|---|
| **空间精度**（东西在哪、隔多远） | **坐标** |
| **描述精度**（杯子上的划痕） | 懒生成 + 固化 + 细化只叠加 |

「无限精度」指的是后者，不是前者。

### A.2 一份数据，两个投影

坐标数据是唯一的源，两个投影都是**确定性的、不需要模型**：

- **投影 A**：俯视图（图形，给玩家）
- **投影 B**：文本网格（给模型）

这与正文 §4.4「地图是数据的视图，不经过任何模型」是同一条原则——模型和玩家看到的是同一份真相同一个源。

**表示法已定：体素。**

| 参数 | 结论 |
|---|---|
| 离散 vs 连续 | **离散**——体素天然是整数坐标 |
| 维度 | **3D** |
| 给模型的格式 | **按层切片的 ASCII 网格 + 物体清单**：网格让模型看出形状与空间关系，清单给它 id 与精确坐标 |

体素带来的三个好处：

1. **「在桌上」变成几何事实**——杯子的体素落在桌子顶面的体素上方，不需要额外字段去声明这个关系。
2. **俯视图天然可解析**——沿 z 切片就是俯视图。
3. **材质有地方放**——每个体素带材质，描述层就有据可依。

代价是规模：

- **必须稀疏存储**（只存非空体素），否则一个 100×100×20 的世界就是 20 万格。
- **给模型的网格必须是局部视窗**，不能是全图。一个 40×40 的 1 米网格已是 1600 字符量级。
- 主视图要**按层切片**：体素是 3D 的，"俯视"必须指定看哪一层，默认角色所在层。

### A.3 物体与物体之间的关系

**物体可以包含物体**：桌子是物体，桌上的酒杯是物体。

而世界模型因此只有**两个**组件，不是一个多出来的"关系表"：

1. **坐标**——空间位置，精确。**「在桌上」「在盒子里」都是它**：酒杯的体素落在桌子顶面的体素上方。
2. **描述**——懒生成、固化、可细化。

早先这里还有第三个组件叫「关系」，由 `Entity.parent` 承担。**它已经删了**（2026-09-24，见 A.13）——A.5 那句「**关系不存成事实**」本来就是对的，是那个字段在跟它打架。判定的 `reparent` 工具跟着一起没了：没有关系要存，也就没有"换归属"这个动作；把杯子从桌上拿起来是一次 `Move`。

### A.4 空间与物体不由代码模拟，由模型处理

现实无法用代码模拟。把桌子掀了，杯子该滚到哪、会不会碎、酒洒成什么形状——**这不是规则能写尽的**，只能由模型推理。

所以这一层的设计目标不是"适合代码计算"，而是：**适合模型修改、不易出错、又能被俯视角解析**。

代码在这里只有一件事要管：**守住结构合法性**，不守物理。

### A.5 结构：一张实体表 + 针对性编辑

每个物体一行：

| 字段 | 内容 |
|---|---|
| `id` | 稳定标识，其他字段和工具参数都引用它 |
| `类型` | 名词（桌、酒杯、门） |
| `坐标` | 精确坐标 |
| `背景` | 这样东西自己的渲染背景（生成时由导演写给道具组）。**不沿任何链继承**（A.13） |
| `属性` | 结构化键值（杯子里有没有酒、门开没开） |
| `描述` | 固化文字，走正文 §7 的渲染规则 |

**模型不重写整张表，只发针对性编辑**：新增、移动、改属性、删除。

这一条是"不易出错"的关键。重写整张表意味着 token 爆炸，而且**每次改动都可能顺手改坏别处，改坏的后果还不可检测**。针对性编辑让"改动范围"和"意图"一一对应，代码才有东西可校验。

**俯视图画地面上那一层的东西**，摆在别的东西上面的一律在观察窗口里展开。这条规则是纯结构的，不需要判断语义——但它的判据**已经从「`parent` 为不为空」换成了「米格在哪一层」**（`parent` 没了，见 A.13）。

### A.6 分工线

| 情形 | 谁判 | 结果 |
|---|---|---|
| **结构非法**（id 不存在、坐标越界、新 id 撞车、批量提交失败） | **代码** | 协议内失败，**退回模型重试**，不给玩家看 |
| **物理不合理**（够不着、搬不动、位置被占着） | **模型** | 世界内驳回，写成话告诉玩家 |

这条分工正好落实正文 §4.3 的两层驳回。

**关系不存成事实。**「酒杯在桌上」由**坐标共位 + 层**表达，语义关系由模型推理——不做代码推导的场景图，那会逼着代码去理解物理。

### A.7 一致性靠纪律，不靠机制

模型维护世界，就没人守着一致性了：模型忘了把杯子移走，杯子就会飘在已经被掀翻的桌子上。这是这套方案的代价，靠四条兜住：

1. **一次意图 = 一次提交**（正文 §4.1）。判定模型裁定"掀桌子"时，必须在**同一次提交里给出桌子和杯子的全部编辑**——这是纪律，不是机制。
2. 代码守结构、不守物理，所以它**不会**因为"杯子还挂在桌上"而报错——它根本不知道那不合理。
3. **矛盾在读取时暴露**：被改动的物体描述会失效并重新渲染，届时模型读到的是"桌子已翻、杯子仍在桌上"这个不一致的状态，由它自己纠正。
4. 另加一个**开发期自检工具**（列出坐标重叠、越界、没有形状的东西），不进游戏。

### A.8 无限精度的一条纪律

**每次只看一层。**

容器可以嵌套得很深（口袋里的盒子里的戒指），但每次观察只展开被看的那一层。**嵌套本身也靠坐标**——戒指在盒子里，就是它的坐标落在盒子的形状里（`parent` 已删，A.13）。这样"无限精度"是无限的，而每次生成的成本是常数。

### A.9 物体与体素表

**实体表是真相，体素是它的形状语言。** 每个物体有**自己单独的一份**体素模型，标识它放进世界会占用多少体素；**具体操作的单位仍然是物体**，不是体素。

**不能互相引用。** 引用会让形状变成可变共享状态：打破一个杯子，所有引用同一形状的杯子一起碎。而且这种 bug 平时不出现——只在有人编辑了共享形状时才炸，排查代价极高。

所以：**预设库是工厂，不是引用。** 从小屋预设生成一个具体小屋，是把形状**拷贝**一份，再改尺寸与材质；之后这个小屋与预设再无关系，改它不影响任何别的物体。管理因此变成局部的——每个物体的形状只属于它自己。

代价是存储：一千个杯子就是一千份形状。但这个代价很便宜——体素是稀疏的，一个杯子几十到几百格，几千个物体的量级仍然只有几 MB。

### A.10 建模：把雕刻隔离出去

生成系统新增一个**建模**功能，用来生成新物品的体素模型。

它比"禁止雕刻"更好，因为雕刻没有被禁掉，而是被**隔离**了：

- **低频**：只在需要新形状时发生，不是每次操作都能雕
- **专门**：有独立的工具与校验，不混进普通动作
- **产物归属**：生成结果直接成为**那个物体自己的**模型（按 A.9，实例化即拷贝）

已定的四个参数：

| 参数 | 结论 |
|---|---|
| 输出格式 | **分层 ASCII 网格**——模型画图，代码解析（见 A.11） |
| 适用范围 | **通用形状服务**：物品、角色、地形块都调它，代码只写一份 |
| 最低粒度 | **5 厘米**（2026-09-24 从 1 厘米改的）。比它更小的东西用**质点**：一颗蓝莓画不成一个 5 厘米的方块，但它可以算作那个格里的一个质点，**一格最多 10 个**。坐标一律厘米整数，见附录 A.13 |
| 产物去向 | **是一条预设**，进**单独的生成预设包**（2026-09-24 改的，见 A.14）。原先写的是"先存单局缓存、被重复用到时提升进全局缓存"——**那条被推翻了**：产物不是缓存条目，是与出厂预设**同一层级**的东西 |

**"缓存"这个词后来被换掉了。** 用户 2026-09-24 的裁定是：建模的产物**就是一条预设**，与出厂预设同一层级，只是进**单独的生成预设包**，不混进默认预设。这不只是叫法——预设是**世界内容**的一部分（存档要带走它），而缓存不是。要的 API 与数据形状在 A.14。

于是普通操作永远只面对"放置 / 变换 / 替换 / 破坏"，可靠性不被雕刻污染；而世界又不会缺形状。

建模的合法性仍按 A.6 的分工线：**代码校验结构**（体素是否连续、包围盒是否合理、是否为空），**模型负责好看与合理**。

### A.11 读写同一种表示法

体素进出模型用的是**同一种文本形式**：切片 ASCII 网格。

- **读世界**：给模型一层层的地形网格
- **写形状**：让模型画出分层网格（就像它画像素画那样），代码解析成体素表

模型只需要学一种表示法。而且这比让它输出体素坐标列表可靠得多——一张 8×8 的图里画个矩形，几乎不可能画错；用坐标列表描述同一张桌子，几乎不可能不出错。

### A.12 判定看到的那一片

框是怎么来的：**发起者 + 这次动作指向的东西**作中心，往十个扇区各打若干条射线；射线打到的东西是参考点，打空就按射线长截断，那个端点也算参考点。所有参考点围成凸包，**凸包必然包含中心**。

模型看到两个投影：一张**发起者所在层**的 ASCII 网格（参差——框外的格子留空，边缘的形状本身就是信息），加一份带 id 与坐标的清单，别的层上的东西在清单里单独列。

（2026-09-26 追加：网格里从此还画**地形**——用材质的显示字符，实体叠在上面；**清单里不列地形**。同一天定的还有"地形格与实体同级成为阻挡面"，见 A.15。）

三条定下来的：

- **一格 = 1 米。** 这句话写进判定看到的那段文字（`shared/src/commonMain/kotlin/io/github/k1midi0/infinitesimal/spatial/RegionView.kt` 的开头一行）——「够不够得着」要算的时候，模型得有个参照。
- **框外一样都不提。** 早先那里有一行「框外还有 N 样东西；最近的是「X」，在东南 4 格外」，删掉了。它给出的是**假目标**：取「最近的那样」时，最近的那常常是发起者**自己所在的房间**——房间的坐标落在参差凸包的角上，于是模型读到「酒馆大厅在西北 3 格外」。它不但没用，还骗走了一次扩大；而真正在框外的第二样东西（靠在墙上的扫帚、井边那只粗陶杯）永远排不上号，模型于是拿手边的同类顶替。判定**不需要**知道框外有什么：要看的东西在框外就调 `widen_view`，扩完还不在，那才是「这里没有」。没被指向的东西本来也不该被判。
- **射线数按 k² 长**（密度守恒）：第 k 档每个扇区 `round(6Ωk²/π)` 条。整体抬一档 24 → 92 → 216；只抬一个扇区 24 → 30。扩大一次是 k 加一，不是长度翻倍（§14.11）。

`widen_view` **不封顶**，只记数。模型到底会不会填方向量过两次：框外那行还在时，13 次扩大里 8 次填了真方向（§14.12）；删掉那行之后模型很少再扩，20 次判定里只扩了 3 次、3 次都填了词（§14.16）。**引用时注意取的是哪一批——13/8 是删行以前的。**

### A.13 单位、体素与质点

这一节是 2026-09-24 定下来的，它改掉了 A.2 与 A.10 里的几处数字，其余照旧。

#### 世界坐标一律厘米

**这一条是承重的。** 以前坐标是米，于是 `z` 退化成了一个"第几层"的编号：桌面上的酒杯写 `z=1`，谁也说不清 1 是什么。改成厘米之后，酒杯就是 `z=80`——**「在桌上」从一个编号变成了一个几何事实**，而那正是 A.2 当初要的东西。

米没有消失，它降级成**一条视图**：空间框（射线、包围框、俯视图网格）仍按 1 米格走（A.12），那个格子就是 100 厘米。所以世界里只有一套坐标，米格是它的粗分辨率。换算是**一处**（`shared/src/commonMain/kotlin/io/github/k1midi0/infinitesimal/spatial/Cells.kt` 的 `metreCell`），不是散在每一条 `abs()` 里。

**负数要单独往下取整**：Kotlin 的 `/` 向零截断（`-50 / 100 == 0`），而物理上 -50 厘米在地面以下那一格里。有测试钉住这一条。

#### 最小体素 5 厘米，更小的用质点

- **实心体素边长 5 厘米**（原来是 1 厘米）。一张 2×1×0.8 米的桌子是 200×100×80 厘米，按 5 厘米分就是 40×20×16 个格——表层稀疏存下来是几千个格，而不是 160 万个。
- **比 5 厘米还小的东西用质点**：一颗蓝莓画不成一个 5 厘米的方块，但它可以算作那个格里**一个质点**。**一格最多装 10 个**；超过十个就该升一档去用体素，而不是让一个格无限装。
- **实心与质点互斥**：一个格要么实心（满了），要么装着 1–10 个质点（空腔里的东西）。两者同时成立在物理上说不通，代码里也就没有它的位置。桶壁是实心格、桶里的水是水质点——两者在不同的格上。

于是形状只有两种占用方式，数据形状是 `VoxelShape(solid: List<Voxel>, pointMass: List<PointCluster>)`（`shared/src/commonMain/kotlin/io/github/k1midi0/infinitesimal/world/Voxel.kt`）。

#### 读数与网格

- **判定清单里的坐标印厘米**。格子那层粗粒度留给网格，精度留在清单里——"够不够得着"要算的正是它。
- **形状的最小球是网格，第 r 行就是 y = r×5 厘米，第 c 个字符就是 x = c×5 厘米**：
  ```
  z=0
  ####
  #..#
  z=5
  ####
  ####
  ```
  `z=<厘米>` 是每层必需的头（全空的层可以整层省掉，所以层间距不能靠顺序猜）；`#` 实心、`.` 空、`1`–`9` 该格几个质点、`+` 十个；**同一层每行必须一样长**（模型少画几个字符是最常见的画错，而它除了"行不一样长"没有别的症状）。解析与写出都在 `shared/src/commonMain/kotlin/io/github/k1midi0/infinitesimal/world/ShapeGrid.kt`。
- 因为网格隐含"最小角在原点"，`VoxelShape` 的包围盒最小角**必须是 (0,0,0)**，而 `Entity.x/y/z` 的含义因此是确定的：**那样东西最小角在世界里的厘米坐标**。

**形状是它的碰撞体积，不是它的画**（用户 2026-09-24 明确）。这一条决定"空腔"该不该画：**能表达、且真的占地方的腔才画**。口径 8 厘米的杯子在 5 厘米的精度下画不出腔（壁厚不到一格），实心柱体就是正确的；60 厘米的桶腔宽到能装东西，就该挖空——而模型自己分得清这两者（§14.21 第九节实测），**提示词里不需要也不该有"空心的东西要挖空"这条规矩**（曾经加过，已删）。

#### 建模缓存

**缓存键是那句要求**（用户 2026-09-24 定的），产物是**一条预设**——不是一份加速表。完整形状见 A.14。早先写的"先存单局缓存、被重复用到时提升进全局缓存"已被推翻。

#### 关系不存成事实：`parent` 已删

2026-09-24 的裁定：**不用存位置关系，世界里本身就有位置关系**（坐标）。要存的是**物品背景**——生成时导演给"道具组"的要求，用来控制渲染风格（酒馆里那只酒杯与皇宫里那只酒杯肯定不一样）。

于是删掉的东西：`Entity.parent`、`World.childrenOf`、`World.backgroundChainOf`、`Consequence.Reparent`、判定的 `reparent` 工具、以及 `Committer` 里那整套成环校验（父存在、不自环、不成环）。"把杯子从桌上拿起来"从此是一次 `Move`；"斧子挂在腰间"是它的坐标与玩家重合。

留下的：**`Entity.background` 改成每样东西自己那一份**，不再沿链从地点继承。地点实体上仍然可以写"这里是什么地方"，但那句话只属于那个地点——某样东西要在渲染时带上场景，得由**生成它的那一步**把该带的写进它自己那份里。

副作用一处：`spatial/RegionView.kt` 的网格以前靠层号把"桌上的酒杯"与"桌边的木桌"分开，现在两者是同一个米格，所以改成**一格画最靠下的那一个**（它是一张"地上有什么"的图），发起者永远是 `@`。俯视图（`ui/GameScreen.kt`）同理：地面上的 = 米格层 0 的，摆在上面的 = 米格层非 0 且米格与某个地面东西重合的。

### A.14 预设库：工厂、两个包、缓存键是那句要求

2026-09-24 定的。A.9 只说了"预设库是工厂，不是引用"，这一节说的是**这个库长什么样**。

#### 只有生成新东西时才建模

用户原话：**物品本身就有建模**，不是"用到才建"。只有**生成新物品**时才需要建模——可能是导演改剧本要树上结个果子，也可能是判定诞生了新物品（桌子被劈开）。**谁需要谁调用。**

所以建模是一只**查询类的手**（与 `widen_view`、`calc` 同类：调用它这一轮接着往下走，结果灌回来再问一次）。它挂在判定的**第二步**，因为第一步还不知道会生出什么新东西。

#### 三个身份，两道关

| | 是什么 | 用在哪 |
|---|---|---|
| `name` | 短名字，例如 `half_oak_table` | 判定引用形状时的把手，也是 `make_object` 点名用的词 |
| `brief` | **当初那句要求** | **第一道关**：逐字匹配的缓存键 |
| `category` + `tags` | **属性总结**：一个类别、一串标签 | **第二道关**：关键词检索 |

前两个分开，是因为两者要的东西相反：要求写给人看会啰嗦成一段话，而要求写成名字又会丢掉"这是被劈开的、
断面粗糙的橡木方桌"里那些决定形状的词。

**第一道关仍然是那句要求**（用户定的）。这条规则有个好性质——要求写得越具体，命中越准；而要求写得
含糊时，本来也不该复用一份形状。**空要求不当键**：它会与任何别的空要求相等，等于"所有没写要求的建模
共用一份形状"。

**但实测证明它不够**（§14.31）：一次生成里同一个东西被造了 11 遍，因为模型每次写的要求都略微不同，
11 次全部落空、11 次现场建模，一次生成因此烧掉 34 分钟。病根不是"库里是空的"那一条——**就算库里有
东西，模型也无从知道它叫什么，更没有理由去抄**。这与 A.2「说话必须是显式动作」是同一条思路：看不见
的东西，模型不会去用。

于是有了**第二道关**（2026-09-28 定，用户改的方向）：按属性做关键词检索。两道关问的不是同一个问题
——前者是"是不是同一句话"，后者是"是不是同一类东西"。

#### 属性由建模那一步的模型写

`category` 与 `tags` 不是代码从 `brief` 里切出来的，也不是手写在出厂清单里的（用户定的）：**建模那一
步的模型一并交**。它刚画完那件东西，最清楚它是什么；而这样一来**出厂包与生成包走同一条路**，不会
出现"出厂那批搜得到、现造的搜不到"。

切词法（从 `brief` 切 bigram）免费、无新来回，但「一棵高大的橡树」切出来的 bigram 噪声大，而且类别
词（`树木`）未必出现在那句要求里——而它正是人会说出来的词。

**形状与属性一起交、一起存。**分开两处存的话，同一份形状会有两个来源，而它们迟早对不上。命中缓存那条
路上属性来自库里那条老预设，**不是重新问一遍模型**：同一份形状本来就该有同一份属性，再问一次只会让两次
调用给出两个略略不同的类别。

属性的形状是**一个类别 + 一串标签**，不是一张固定字段表：类别用于粗筛（"我要一棵树"），标签用于细搜
（"橡树"）。固定字段表搜起来更准，但很多物件填不满，空字段在提示词里就是噪声。

#### 检索怎么打分

分词用从 Pulsus 搬来的 `queryTerms`（中文 bigram）。切错方向的代价不对称：**多一条候选只是清单里多一
行，而少一条是一样东西静默地搜不到**。

一个词落在 `category` 或 `tags` 上算 **2 分**，落在名字或那句要求上算 **1 分**。分成两档是因为这两处的
词性不同：属性是**专门为搜索写的**，而那句要求是为了画图写的，里面全是修饰词（"被雷劈过的"、
"断面粗糙的"）——同一个词出现在前者，比出现在后者说明的问题多得多。

同一个词只算一次，取它的最高那一档。**空查询返回空表而不是全部**——返回全部会让"搜不到"与"懒得搜"
长得一模一样，而这两种情况该给模型的话完全不同。

#### 第二道关是显式的一只手

`find_preset` 是一只**不落地的手**（与 `look_terrain`、`widen_view`、`calc` 同类）：调完之后这一轮接着
往下走，结果灌回去再问一次。

它为什么不能是"`make_object` 落空之后代码自动降级搜索"：那样模型对"用什么词搜"没有发言权，而它才是那个
知道自己在找什么的人。

清单里给它三样：**名字**（填进 `make_object` 的 `preset` 的就是它）、**属性**（它为什么被搜出来）、
**当初那句要求**（逐字抄的备份）。三样都给是因为它接下来有两条路可走，而两条路要的信息不一样。

搜不到时**不返回空字符串**：空字符串与"搜到了但清单是空的"长得一样，而这里真正的含义是"库里没有，你得
自己写一句要求"。

#### 出厂包是一份资源，不是源码

一批形状有几千行网格文本，写进 `.kt` 会把源码淹掉；而它同时又是**可以重扫的数据**。所以出厂包放在
`shared/src/commonMain/composeResources/files/builtin-presets.json`，由 `spike/PresetSweep` 生成。

代价是一条异步加载路径：Compose 的资源 API 是挂起的。所以 `BuiltinPresets.load()` 是 `suspend`，在进
游戏之前读一次，读到的表交给会话——**预设库挂在会话上，判定、生成器、导演看同一份**。

**读不出来时不静默退回空表**：出厂包空着是"我们还没扫"，读不出来是"打包或路径坏了"，两件事的下一步
完全不同。一条安静的 `catch` 会让"预设库怎么全在现造"这个问题查一整天。

#### 短名字不承担唯一性

它由代码**规范化**（小写、非 ASCII 换成下划线、截断到 48 字符），不为了一个不影响任何东西的把手退回去
让模型重说一遍——那要烧掉一整轮。

#### 出厂与生成分开存

`PresetLibrary` 两个包：**出厂那批**随游戏走、只读；**生成那批**是一局里长出来的，也是存档要带走的那一份。混在一起，就再也说不清"哪些是我们自己带的、哪些是模型现场编的"——而这条信息在排查一份难看的形状时正是第一个要看的。所以"进生成包"的东西一律被标成 `GENERATED`：一个字段与它所在的位置各说各话，是日后最难查的一类不一致。

#### 形状不可变，"拷贝"是白拿的

`VoxelShape` 里全是只读列表，所以"拷贝"与"共享"在这里**没有区别**，而 A.9 要的那条性质——**打破一个杯子不能让所有引用同一形状的杯子一起碎**——因此不是靠纪律维持的，而是**在数据模型上无法被违反**。改一个物体的形状永远是 `copy(shape = …)`，碰不到预设，也碰不到别的物体。

#### 它不碰世界，所以有一条顺序规则

建模只回答"画成没画成"。形状由**代码**补成一条 `Consequence.SetShape`，和模型给的那些后果**一起**走 `Committer`。绕这一圈而不是当场写进世界，是因为"这个 id 是这一批里刚 spawn 出来的、还是本来就有"，只有 `Committer` 的影子状态知道。

由此有一条不显然的顺序：**`SetShape` 必须接在模型给的后果后面**。排在前面就会撞上"世界里没有它"——而症状是"新东西没有形状"，看起来像建模失败了。有测试钉住。

#### 建模是一个独立的模型段，独占一个缓存池

它**不是判定那一轮里的一个函数**：A.10 说它是通用形状服务，物品、角色、地形块都调它。分开买到的是一件事——**判定不必为了画一张桌子而背上整段网格语法**（判定那段提示词里已经装了两步的工具、空间框、规则书、角色卡）。

它有自己的 `user_id`（`SystemId.MODELER`）：system 是几百 token 的网格语法、每次都逐字相同，是这套东西里最该命中缓存的一段。

#### 交一层算一个来回，但不算一次失败

`ShapeGrid` 的语法是**一层一层写**（`z=<厘米>` 起头），所以 `ShapeModeler` 的工具是 `voxel_floor`（交一层）而不是"一次交一整张图"：一样东西有几层就要交几层，一个四十层高的柜子因此要四十来个来回——**那是正常进度，不是错误**。

于是它数两样不同的东西：**错了几次**（`maxAttempts`，默认 3）与**问了多少来回**（`MAX_ROUNDS`，40）。混成一个计数，长东西就会被判成"画不出来"，而它其实一次都没画错。

错的只有两类，修法不同：**读不成格子**（行不一样长、字符不认识）与**格子不合理**（同一格既实心又质点、超了上限）。两类都由 `ShapeGrid.parse` **一次报全**、原样回给模型——它拿着"第几行第几个字符不对"这条信息，修得比谁都快（§1.3）。交 `voxel_done` 之后校验，不过就把问题退回去让它重交。

### A.15 地形与材质

（2026-09-26 定，**已接线**；生成器未做。接线过程与实测见 §14.29）

#### 世界是立体的，而且有底

| | 值 |
|---|---|
| 竖向范围 | **0 – 1024 地形格**（50 厘米一格）= 512 米 |
| 默认地面 | **第 256 格** = 128 米 |
| 第 0 格 | **一层不可破坏的岩层材质** |
| 256 以上 | 空中——可以往上建、往上飞，现在什么都没有 |

整套在**准备冒险时可以配置**（换一张地图就是换这几个数）。

世界从"只有一张实体表"变成**一张实体表 + 一层地形**。地形是**地下的体积**：土材质在下、石材质做地基。上面才是物体——一层薄的地板物体、地板物体上叠桌子物体、桌子物体上叠酒杯物体。

**"有物体在的地方不会有重合的地形"就是这么来的**：不是数据互斥，而是**物体在地形表面之上**。所以"先改地形再改物体"那条次序要求不需要（2026-09-26 取消）。

#### 地形格：一格一个材质，没有材质就是空

一格 = **50 厘米**，只有这一种精度（不会有 10 厘米的地形）。**"空气"不是一个材质**——挖去就是把那一格清掉，而稀疏存天然表达这件事。

#### 是按列分段存的，不是按格存的

这一条是被一笔算术逼出来的，不是优化。

**硬性圈里"从 0 格到地面都要铺满"**（A.16）——半径 32 米的硬性圈是 **12,868 个地形格**，乘上 257 层是 **330 万个格**。按格存就是一张 330 万条的 map，光 entry 开销几百 MB，**一开局就爆掉**。

而地下**是分层的，不是噪点**：一列「岩层 0、石 1–180、土 181–256」是**三段**。所以存的是 `TerrainRun(material, from, to)`，一列是一个有序的段表：

| | 32×32 的地形格，从 0 铺到 256 |
|---|---|
| 按格 | 263,168 条记录 |
| 按列分段 | **1,024 条记录** |

语义一字不变（每一格都有材质），而存储降两个数量级。只有玩家真的挖过、堆过的那几列段数才会涨；而**段与段不重叠、不相邻**（相邻同材质一律合并），所以 `dig` 留下的碎段不会无限累积。

挖空的列**当场从表里删掉**——留着它是把稀疏存的收益又还回去。

#### 两个写入口，一种表示法

- **三只框选工具**：填充、挖去、材质替换。三只都收**同一个长方体** `x1/y1/z1/x2/y2/z2`（地形格坐标）。
- **一只表格工具**：和物体建模共用 `ShapeGrid` 那套语法（A.11 那条"读写同一种表示法"）。铺一条路用框选，雕一个台阶用表格。

地形后果是**第八种 `Consequence`**，与那七种**同批**交给 `Committer` 原子提交——所以"把桌子推开、把桌底下的地挖了"要么一起生效、要么一起不生效。

#### 地形挡射线

地形格与实体**同级**成为空间框的阻挡面。

**但它不进那张 `Map<Cell3, String>`**（2026-09-26 实现时改的）。那张表是**建一次、所有射线共用**的，而它能这么做的前提是"实体是有限的一小撮"——地形不是：一列从 0 格铺到地面就是 257 格，硬性圈是三百多万格，枚举一遍等于把稀疏存的收益当场还回去。所以地形**沿着射线按需查**（`spatial/Ground.kt` 的 `solidTerrainAt`），代价是射线链上多一次判断。

判据是**整格填满**才算实心，不是"有任何一个子格"——那条判据差点让框塌成 3×3，理由见 §14.29。

这条会第一次真的动到 §14.20 那条读数：当时量出"**单层的家具挡不住射线**，所以空间框几乎总是 ±3 的方块"，而原因正是**世界里没有能挡射线的东西**。一堵石墙和一堵"墙物体"对射线、对玩家、对模型应该是同一件事。

#### 呈现：网格画字符，另配一份按材质去重的图例

地形**画在网格里**（用材质的显示字符），实体叠在上面。**实体清单里仍然不列地形**——一样东西写两遍就是两份可以不一致的数据。

但**光有字符不够**（2026-09-26 定）：模型拿到的是**完整的材质属性与规则书**，不是几个占位符号。做法是**按材质去重的一份图例**——一片 16×16 的草地是一行「`,` 草（属性…／规则…）」，不是十六行"草"。布局在网格里，性质在图例里，两者都不重复。

#### 材质表

材质是一张**独立的表**（与预设库并列，**不是**预设的一种）：

| 字段 | 用途 |
|---|---|
| `id` | 地形格里存的就是它 |
| `名字` | 给模型与玩家看的 |
| `属性` | 与实体的属性同一套（判定与导演都读） |
| `规则书` | 与实体的规则书同一套 |
| `显示`（字符 + 颜色） | 空间框的网格用它画（A.12），俯视图用它上色 |
| `可破坏` | 第 0 格那层岩层就是靠"可破坏 = 假"拦住的 |

**优先级 15**，排在**世界 10 与角色 20 之间**（§14.19 那张表因此变成：世界 10 < 材质 15 < 角色 20 < 物品 30）。

开局七种：**土 / 石 / 岩层 / 木地板 / 草 / 水 / 路面**。

### A.16 区划层、chunk，与世界怎么长出来

（2026-09-26 定，**已实现并已联机跑通**——形状按 §14.30 改过，第一次真跑的读数在 §14.31。上游那只手与触发时机在 §14.33 定下了：硬圈缺口由代码发现、同步叫思考档；缓冲圈由快速档发现、异步叫思考档。**本节下面那些「以玩家为中心画两个圆」的说法要按 §14.33 读**——圆心跟着玩家，触发判据是「这个圆盘里有还没长地形的 chunk」，而不是「距边缘不到一块」（后者在圆心跟人走时永远不成立）。）

#### 区划层：导演的涂鸦，但是世界事实

**10 米一格**。字段只有两样：**地貌**（闭合枚举：城 / 镇 / 路 / 林 / 野 / 水 / 山 …）与**备注**（导演自由文本）。

- 它是**世界事实**，落在地图上，**玩家也看得见**。
- **已探索的不能改。**
- **区划是意图，地形是事实**：生成时读区划，而两者**允许不一致**。

第三条是有代价的：地图上写着"森林"、走过去是石板路，没有任何东西会报。选它是因为另一头更重要——**导演要能随便涂**（下面那条"提前在地图上涂鸦"就是它），而地形是玩家真的踩到的东西，不能被一句备注改掉。

#### chunk：生成的最小单位，不是最大的

水平**不设上限**，世界按 chunk 按需生成。

**chunk = 16×16 地形格（8×8 米）的水平块 + 竖向整列**，稀疏存。

**地形以 chunk 为最小生成单位**：「哪儿还没有地形」没有中间状态，一块 chunk 要么有、要么没有，**不会有厘米级的缺口**。而 chunk 是"单次生成的最小单位"，不是最大的：**一次铺多大由导演定**（§14.30）。

第 0 格那层岩层**不必逐 chunk 存**——它是一句全局规则。

#### 两个同心圆

以**玩家为中心**画两个圆，**以 chunk 为单位**：

| 圈 | 半径 | 是什么 |
|---|---|---|
| **硬性圈** | **4 块 = 32 米** | 已探索。**必须有完整的地图**，是既定事实，不能改 |
| **缓冲圈** | **32 块 = 256 米** | 导演可以**自由生成**的地方 |

**「必须有」说的是「这些 chunk 生成过」，不是「每一格都填满」。** 早先那条判据写成「从第 0 格铺到地面（默认第 256 格）每一格都有材质」，字面照做会把**任何低于第 256 格的地面**判成违规——悬崖下面那一片、沟壑、洞穴全在内，而导演正需要它们（§14.30）。「脚下别踩空」因此从一条**代码判据**降成一条**提示词规矩**。

（A.15 那个「按列分段存」的理由与它无关：硬性圈半径 32 米，不论按哪种判据，它都是约 330 万个格。）

**探索过 = 既定事实。** 地图随玩家被探索逐渐生成，生成时可以定制；一旦生成过，往那里再放东西就是"凭空捏造"——这就是 §3.2.4 那条"**导演补事实 = 往地图里放实体**"的边界。**这条边界约束的是生成器**；导演与判定可以改任何地块（§14.30）。

**来源不区分。** 冒险准备阶段定下的、外部导入地形包的、生成器长出来的——三者等价，都是「这块地有地形了」，不另立来源字段。

**触发点**：玩家所在的 chunk 距离硬性圈边缘不到一块时，把**硬性圈里还没有地形的那些 chunk** 补上；缓冲圈里铺多少由导演定（§14.30）。

#### 生成：先叫醒导演，再由导演决定长什么

**生成不是被地形系统触发的，是导演调用的。** 链路：

    玩家往外走 → 叫醒导演（思考档）
               → 导演决定生成要求：grow_terrain(requirement)
               → 地形系统按这个要求在指定地块上铺地形
               → 缺的物品交 make_object 走物品系统（预设库没命中就建模）
               → 一次调用产出的全部后果整批原子提交

**没有代码默认剖面。** 一块新地方的地形与它上面的东西，都由**模型**产出——理由是"这里该长什么样"是个内容问题，而代码铺出来的荒野千篇一律。

限制它形状的几条：

- **处理哪些地块由导演给。** 缺口用 **chunk 编号**（代码列出来），自由生成用**方位 + 块数**（"北 4 块"），代码换算成 chunk 框——模型在坐标上没有参照系（「油灯坐标是编的」那一课，§14.25）。
- **地形与物体一起产出。** 一片森林是"地形铺草"加"树、灌木、也许一只野兽"；分两次调用等于让第二次重新理解一遍"这里为什么是森林"。新物体走**预设库**（§9.1：调用预设、简单修改后放进地图），所以不必为每棵树各付一次建模。
- **接壤处看得见**：相邻已生成地块的**边缘剖面**（逐列的最高材质与高度）附给它。接缝是一眼看出的东西，而它本来看不到旁边长什么样。
- **它拿的是六只手**：框选三只（fill / dig / replace）+ 表格两只（`look_terrain` 看、`edit_terrain` 改）+ 一只放物体的（`make_object`）。
- **表格那两只的用法**：先框选看，再以那个框为最大边界输表修改；表必须与框**严格同尺寸**、每格都写，`.` 是挖空；框按**字符预算**限（§14.30）。表格留给精修（雕一个台阶），铺大片仍然用框选。

#### 创建冒险阶段：导演先涂鸦

开局前，导演可以**提前在地图上涂色块和标注**：哪里是城市、哪里是道路、哪里是森林，也可以留白。那是它自己的笔记，随时可改（已探索区除外）。

这也是"区划是意图"那条的落点：**先把意图画出来，再让生成器读它。**
